# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Purpose

**extendedscreen** turns an Android tablet into a second monitor for macOS via USB-C. The macOS app (Flutter + Swift native plugins) captures the screen and streams H.264/H.265 over an ADB-reverse TCP tunnel; the Android app (same Flutter codebase, different platform role) decodes and renders frames while sending touch gestures back as mouse events (click, scroll, drag, pinch); it forwards no keyboard input. **Nothing is hardcoded to a specific tablet model**: the client reports its native panel size in the HELLO handshake and the host derives all capture/encode resolutions from the connected device. The Android client is landscape-locked (manifest + `SystemChrome` in `main()`, kept on Android 16+ by a manifest opt-out, which only works while `build.gradle.kts` pins `targetSdk` to 36; see *Native Android plugins*). A second session mode, remote control, reuses the same link to drive the Mac from the tablet, or to view and drive the tablet from the Mac (see *Session modes and stream direction*).

## Commands

```bash

# it is the only candidate); DEVICE_SERIAL does not override that (see Key settings).
flutter run -d macos

# Run on connected Android device
flutter run -d <device-id>

# Build macOS release
flutter build macos

# Analyze / lint
flutter analyze

# Run tests (test/ covers connection retry, DisplayController
# codec rebuild + HELLO panel size, the DisplayView HUD, the Home device picker, TouchGestureRecognizer,
# and the keep-Mac-cursor setting: default, persistence, InputInjectChannel pushing setKeepCursor)
flutter test
# Single file / single test by name
flutter test test/<name>_test.dart
flutter test --plain-name "<test description>"

# Regenerate the app icons from the Swift drawing script
swift tool/gen_icon.swift .

# Follow the host's capture/encode diagnostics (diag: tick/SCK/encoded/pending,
# adaptive rate changes) — public unified-log entries, also echoed to stderr.
# Full path because zsh has a `log` builtin.
/usr/bin/log stream --predicate 'subsystem == "com.example.extendedscreen"' --style compact
```

- An end-to-end session needs both sides running: the macOS host and the Android client are the same app. `.vscode/launch.json` has a compound config that launches both; its device id and `DEVICE_SERIAL` are one specific tablet's serial.
- `adb` is **not** resolved from `$PATH`. `AdbManagerPlugin.adbRun` probes `/usr/local/bin/adb`, `/opt/homebrew/bin/adb`, then `~/Library/Android/sdk/platform-tools/adb`.
- The link is TCP `127.0.0.1:7001` on both ends (`BaseConnectionManager.host`/`port`), tunnelled with `adb reverse tcp:7001 tcp:7001`.
- Tests use `SharedPreferences.setMockInitialValues`, fake `BaseConnectionManager`/`DisplayController` subclasses, or (`display_codec_test.dart`) mock handlers on the `extended_screen/video_decoder` and `nal_feed` channels. That file also fakes wakelock_plus's macOS channel and its pigeon channel; on a Linux or Windows test host wakelock_plus registers a different implementation, so it may need another fake there.
- `README.md` is the user-facing guide (setup, usage, settings, troubleshooting, plus a short how-it-works and the packet table); it does not describe the `lib/` layout or the native plugins. Where it and the code disagree, trust the code.

## Architecture

### Dual-role Flutter app, organized by feature module

The same Dart codebase runs on both sides of the link. The tree is organized **by feature module first, then by role**, with a central shared backbone (imports are `package:extendedscreen/...`):

- **`lib/shared/`** — the cross-mode backbone used by both roles *and* both feature modules:
  - `connection/` — `socket_service`, `connection_state`, the abstract `BaseConnectionManager`, plus the concrete `HostConnectionManager`, `ClientConnectionManager`, and `AdbService`. Both concrete managers call into *both* feature modules, so they live here rather than in a module; only the host branches on the mode (`SettingsService.isReverseRemote` / `effectiveDisplayMode`), while the client just follows the host's `0xF9` / `0xF8` / `0xF7` packets.
  - `models/`, `protocol/`, `services/` (logger, settings, translations), `platform/` (`permissions_channel`, `keepalive_channel`, `battery_channel`), shared `widgets/`.
  - `features/` — mode-agnostic UI shells: `splash/`, `home/` (connection screen, both roles/modes — the host also picks the `SessionMode` here via an inline selector), `settings/` (the host's control surface; on the client it shows only language, permissions and info).
- **`lib/modules/extended_screen/`** — the second-monitor streaming pipeline:
  - `host/` — `screen_capture_channel`, `input_inject_channel` (macOS capture + input injection).
  - `client/` — `video_decoder_channel` and the `display/` feature (Android decode + render). Also reused by the remote tab-controls-Mac direction.
- **`lib/modules/remote_screen/`** — the remote-control additions:
  - `host/` — `remote_video_channel` (macOS decodes the tablet stream) and the `remote_host/` feature (Mac-views-tablet UI).
  - `client/` — `android_capture_channel` (Android captures + encodes its own screen).
- **`lib/app/`** — app shell: `app.dart`, `theme/`, `routes/`, `bindings/initial_binding.dart`.

Note: because the move was structure-only (no behavior rewrite), the shared connection managers import a couple of module-owned channels (e.g. `HostConnectionManager` → `remote_screen/.../remote_video_channel`; `ClientConnectionManager` → `remote_screen/.../android_capture_channel`). These are runtime `Get.find` dependencies whose imports are type-only — a deliberate, acyclic "shared depends on module" edge.

Roles:

- **Host (macOS):** runs `adb reverse`, starts a TCP server, captures the screen via `ScreenCapturePlugin` (Swift/ScreenCaptureKit), encodes with VideoToolbox (H.264 or H.265/HEVC selectable), and streams `FRAME_DATA` packets. Injects touch/mouse/key events received from the tablet via `InputInjectPlugin`.
- **Client (Android):** dials into the ADB-reverse tunnel, decodes H.264/H.265 frames (via `VideoDecoderChannel`), renders them in `DisplayView`, and forwards user input back as packets.

### Session modes and stream direction (`lib/shared/models/session_mode.dart`)

Three host-chosen, persisted enums decide which pipeline runs. The client never chooses; it learns the mode from the host's `0xF9`.

| `SessionMode` | `RemoteDirection` | Video flows | Capture source | Input path |
|---|---|---|---|---|
| `extendedScreen` | (unused) | Mac → tablet | `DisplayMode` setting (Extend or Mirror) | tablet packets → `InputInjectPlugin` (CGEvent) |
| `remoteControl` | `tabControlsMac` | Mac → tablet | always Mirror (`SettingsService.effectiveDisplayMode`) | same as above |
| `remoteControl` | `macControlsTab` | tablet → Mac | Android MediaProjection | `HostConnectionManager.sendRemoteTap/Swipe` → `adb shell input` (no packets) |

The last row is "reverse remote" (`SettingsService.isReverseRemote`), the only case where the tablet encodes and the Mac decodes. `HostConnectionManager` and `HomeController` branch on that getter; `ClientConnectionManager` does not: it only stores the mode from `0xF9` and handles `0xF8`, `0xF7` and `0xFF` with no mode check. The host sends `0xF8` with codec/fps/bitrate, the client raises `needsScreenShare` and waits for the user to tap "Start screen sharing" on Home (MediaProjection consent has to be user-initiated from the foreground), then streams `FRAME_DATA` to the Mac, which decodes into a Flutter texture (`HostConnectionManager.remoteTextureId`).

Navigation follows the mode (`HomeController`): the client auto-opens `/display` once the link is active, except in reverse remote where it stays on Home; the host stays on Home as the capture source and only auto-opens `/remote-host` in reverse remote. The client's phase listener runs as it sets `streaming`, right after sending HELLO and before this session's `0xF9` arrives, so it sees the previous session's mode: on a switch into reverse remote it pops `/display` once `0xF9` lands, but on a switch out nothing opens `/display` until the user taps "Open View".

Inside `/display` (`display_view.dart`), the HUD bar shows for 4 s, then collapses to `_HudHandle` (a 64×48 hit area at the top centre, below any cutout via `SafeArea`) that brings it back; touches elsewhere fall through to `_TouchOverlay`. The host's `showHudOverlay` (`0xFA`) only hides the bar's stats: Back and Disconnect are always there. `_ReconnectingOverlay` (phase connecting or `error`) takes every tap and has Back (`Get.back`: the client keeps redialling and Home's phase listener reopens `/display` when the link is active again) and Disconnect (`DisplayController.onDisconnect`). Its text is one neutral `display_reconnect_hint`, because the client cannot tell a host settings restart from a lost link.

### State management — GetX

`SettingsService` is constructed and `await settings.init()`-ed in `main()` **before** `runApp` so the persisted UI language is available when `GetMaterialApp` reads `locale` at first build; `InitialBinding` only registers it if not already registered. All other services are registered as `GetxService`/permanent singletons in `InitialBinding`, which inspects the platform and registers either `HostConnectionManager` or `ClientConnectionManager` **bound to the `BaseConnectionManager` type** (`Get.put<BaseConnectionManager>(...)`) — so shared UI depends on a single interface. Controllers are scoped to routes via per-feature `*Binding` classes (`HomeBinding`, `DisplayBinding`, etc.). An `Obx` only subscribes to observables read inside its own builder: Home passes `DevicePickerCard` a snapshot (`cm.availableDevices.toList()`), because a plain widget that reads an `RxList` in its own `build` registers nothing and goes stale.

Role-specific services are registered only on their platform (`ScreenCaptureChannel`, `InputInjectChannel`, `RemoteVideoChannel`, `AdbService` on macOS; `VideoDecoderChannel`, `AndroidCaptureChannel`, `BatteryChannel` on Android). Shared code must `Get.find` them lazily behind an `isHost` check, never as an eager field.

### Localization (`lib/shared/services/app_translations.dart`)

User-facing strings are GetX translation keys resolved with `.tr` (or `.trParams({'name': value})` for `@name` interpolation) against `AppTranslations`, which holds `en` and `th` maps. Existing exceptions: the host's connect errors (`HostConnectionManager.connect()` stores `e.toString()` in `errorMessage`, so Home's error banner shows raw English such as `Exception: No ADB device detected`; the client uses the key `error_waiting_for_host`), the Settings Info values (`USB-C / ADB`, `7001`, `1.1.0`, `macOS 13+`; the version is a literal, so keep it in step with `pubspec.yaml`), codec/unit labels (`H.264`/`H.265`, `Hz`, `fps`, `ms`, `drop/s`, `Mbps`), and the Android foreground-service notification text (English literals in Kotlin). **Never hard-code UI strings** — add a key to both locale maps. This applies to enum label extensions too (`ConnectionPhaseX.label`, `EncodePresetX.label/tagline/description`, `SessionModeX`/`RemoteDirectionX.label/description`): they are getters, so they resolve the active locale at read time. The Settings permission rows do not: `SettingsController._buildPermissionList()` stores `.tr` results in `PermissionItem.label/description`, so they keep the old language after a locale switch until `refreshPermissions()` runs again — don't copy that pattern. `fallbackLocale` is `en`. The saved language (or device language: Thai if the system is Thai, else English) is resolved in `SettingsService.init()`; `SettingsService.setLocale()` persists the code and calls `Get.updateLocale()`.

### Connection lifecycle (`lib/shared/connection/`)

`BaseConnectionManager` owns the shared phase/latency observables, the packet loop with heartbeat handling, the reconnect timer, and input-send helpers. `connect()` and `autoConnect()` are abstract; `refreshDevices()`, `sendUiFlags()`, `startScreenShare()`, `onRolePacket()`, `onTeardown()` and `onLinkLost()` are overridable no-ops. `HostConnectionManager` and `ClientConnectionManager` implement the role specifics. Phases actually set on the happy path:

- Host: `disconnected → detectingDevice → portForwarding → handshaking` (server bound, waiting for the tablet to dial in) `→ configuring` (waiting for HELLO, starting the media pipeline) `→ streaming`
- Client: `disconnected → handshaking → configuring → streaming`

`error` is the state while a retry is pending. A `connect()` from `error` (tapping Connect on the tablet, picking a device on the Mac) is that retry run early: `beginConnect()` cancels `_reconnectTimer` and clears `_recovering`, so the attempt's own failure goes through `handleLinkFailure()` and arms the next retry instead of being swallowed by the `_recovering` guard. `adbConnecting` and `paused` exist in the enum (with labels and colours) but nothing sets them. `isActive` is streaming or paused; `isConnecting` is everything except disconnected/streaming/paused/error.

**Liveness.** Heartbeat every 2 s; 6 s without any packet from the peer calls `handleLinkFailure()`. An open socket proves nothing here: the ADB tunnel can accept the tablet's connection without ever delivering it to the host.

**Cancellation.** `disconnect()` bumps an attempt counter. Each `connect()` captures `currentAttempt` and `beginConnect()` up front and must check `isCancelled(attempt)` after **every** `await`, bailing through an abandon helper that only cleans up when `isLatestConnect(seq)` (a newer attempt may already own the socket or capture). Keep to this pattern when adding an `await` to either `connect()`.

**Who initiates.** The client always dials and retries until the host is up. The host's `autoConnect()` only lists devices; `HomeController._maybeAutoConnect()` (run on Home init and each app resume) connects without a tap only when permissions are granted, the phase is `disconnected`, `_userStopped` is unset (set by the Home card's Disconnect/Cancel, cleared by the next connect from Home; the remote view's Disconnect button doesn't set it), and exactly one candidate device is present (emulators are ignored when a physical device is attached).

Every link failure (socket error/close, heartbeat timeout, or a throwing connect attempt) goes through `BaseConnectionManager.handleLinkFailure()`: it stops that link's packet listener + heartbeat, runs the role's `onLinkLost()` (host: full `onTeardown()` — releases any mouse button the tablet left held (`InputInjectChannel.releaseAll()`), then capture, virtual display, adb tunnel; client: nothing, so its keep-alive service survives for background reconnects), closes the socket (server included), sets `error`, then retries after `reconnectDelay` (client 5 s, host 1 s). One host exception: a media pipeline that fails to start is only logged (`connect()` catches a throw from `_startCapture()`; the reverse-remote decoder init in `_startRemoteReceive()` swallows its own error), so the link still reaches `streaming` with no video instead of retrying. Never retry by calling `connect()` on a live session — that stacked duplicate listeners/timers and a second server socket. `SocketService` owns the raw TCP socket; `AdbService` wraps `adb` CLI calls. The **macOS host is the sole settings/control surface**: display mode, encode preset and codec are editable only on the host (the client's Settings page renders none of those controls, only language, permissions and info). Every setting change persists the value and then calls `reconnect()` (full disconnect + reconnect to the same device, debounced 350 ms in `SettingsController` so several edits in one sheet collapse into one) so the capture/encode pipeline restarts with the new value. Four things don't reconnect: the overlay/HUD toggles push `0xFA` via `sendUiFlags()`; the language picker only calls `SettingsService.setLocale()`; the "keep the Mac cursor in place" toggle is pushed to `InputInjectPlugin` by an `ever()` worker in `InputInjectChannel.onInit()`; and session mode / remote direction are picked on Home (the selectors show only while the host is neither connecting nor active), so they are just persisted and read by the next connect. On each start the host announces the active codec to the client via a `0xFC` control packet; the client's `DisplayController` rebuilds its decoder if that differs from the codec it was built with (see the `0xFC` row).

On the host, connect attempts started from Home (picking a device, or `_maybeAutoConnect()`) go through `HomeController._connect()`, which is gated by `_ensureHostPermissions()`: if Screen Recording or Accessibility is missing, it snackbars, navigates to Settings with `arguments: {'scrollTo': 'permissions'}` (`SettingsController` scrolls to the Permissions header via its `permissionsKey` `GlobalKey`) and does not connect. Attempts that call `connect()` directly skip the gate: the `handleLinkFailure()` retry, the resume reconnect in `BaseConnectionManager.didChangeAppLifecycleState`, and `reconnect()` (settings changes, the remote view's Reconnect button).

### Packet protocol (`lib/shared/models/packet_model.dart`, `lib/shared/protocol/packet_codec.dart`)

Framing lives in `Packet.serialize()` and `SocketService._tryParsePackets()`: a 17-byte header (4-byte magic `EXTD` + 1-byte type + 4-byte payload length + 8-byte timestamp in µs) followed by the payload, all big-endian. `PacketCodec` only encodes and decodes payloads (input events, heartbeat ping/pong) as hand-rolled binary. An unknown type byte parses as `CONTROL`, and a bad magic flushes the whole receive buffer.

Packet types: `FRAME_DATA` (one encoded frame as an Annex-B buffer, in whichever direction the stream runs; keyframes are prefixed with their parameter sets, so a payload can hold several NAL units despite the `nal` naming in code), `TOUCH_EVENT`, `MOUSE_EVENT`, `KEY_EVENT`, `HEARTBEAT`, `CONTROL` (`ack` and `displayConfig` are declared but unused). The Android display currently sends only `MOUSE_EVENT`: `TouchGestureRecognizer` turns touches into click, scroll (with a fling, skipped when the finger rested longer than `_flingMaxIdle`, 100 ms, before lifting), long-press drag and pinch (⌘+scroll). `DisplayController._sendMouse` always sends `MouseButton.left`, so there is no right-click. A drag is down, `MouseAction.move`s, up; extra fingers during it are ignored, and every path that ends it (lift, cancel, `_reset()`, `dispose()`) goes through `_endDrag()`, so exactly one up follows each `onDragStart`. That up is dropped if the link is already down (`sendMouse` needs an active phase); the host's `releaseAll()` on teardown covers that case. `sendTouch()`/`sendKey()` have no callers, though the host decodes and injects all three.

Control sub-commands are the first payload byte, dispatched in each manager's `onRolePacket()`:

| Byte | Direction | Meaning |
|---|---|---|
| `0x01` | client → host | HELLO: platform byte (`0x02` = Android), panel width and height (uint16 BE each, physical px, landscape), panel top refresh rate (1 byte, Hz). The size is the whole display, not the Flutter window (which can leave out the nav bar): `ClientConnectionManager._nativePanelSize()` reads `view.display.size`, falling back to `view.physicalSize` if the display is unreported or empty. The same size drives the reverse-remote capture |
| `0xFF` | viewer → encoder | Request an IDR. Client → host normally. Host → client in reverse remote is wired in Dart and Kotlin, but `RemoteVideoPlugin.swift` never raises `onRequestIdr`, so it is not sent yet |
| `0xFE` | host → client | Client replies with `0xFF`. Still handled, but nothing sends it |
| `0xFC` | host → client | Codec (`0` H.264, `1` H.265). Only `ClientConnectionManager` handles it, storing it in `SettingsService`. `DisplayController` records the codec each decoder build used (`_decoderCodec`), and an `ever(codecRx)` worker rebuilds whenever the setting differs, so a display opened before the announcement (on `streaming`, with last session's codec) still switches; the codec already running causes no rebuild. A build bumps `_decoderGen`, cancels the frame subscription, and stops after any await once superseded or closed. The native decoder ignores `initialize` while configured, so a rebuild must `dispose()` first |
| `0xFB` | host → client | Stream refresh rate (Hz) |
| `0xFA` | host → client | Performance-overlay and HUD-stats toggles (HUD off hides only the stats; Back and Disconnect stay) |
| `0xF9` | host → client | `SessionMode` index + `RemoteDirection` index |
| `0xF8` | host → client | Reverse remote: start capturing (codec, fps, bitrate in Mbps) |
| `0xF7` | host → client | Reverse remote: stop capturing |

The host waits (3 s timeout) for the HELLO before starting capture and persists the reported panel via `SettingsService.setClientPanel()` / `setClientMaxRefresh()`. The client sets its display mode from the host's `0xFB` (the slowest panel mode ≥ the stream rate, never below 60 Hz), not from its own (host-only) preset; a mid-stream `0xFB` only switches the panel mode (`setRefreshRate`, which also moves the decoder's input-queue cap) — the decoder is configured with the panel's top rate as its operating rate so it's never rebuilt for a rate change.

### Native macOS plugins (`macos/Runner/`)

| File | Purpose |
|---|---|
| `ScreenCapturePlugin.swift` | ScreenCaptureKit capture → VideoToolbox H.264/H.265 encode → `FlutterEventChannel` frame stream. Also manages `CGVirtualDisplay` (Extend mode); `createVirtualDisplay` returns whether its mode settings applied (`ScreenCaptureChannel.createVirtualDisplay` → `Future<bool>`; `_startCapture()` logs a warning on `false`). `startCapture` picks the display with `findCaptureDisplay` (see *Display modes*) and stores it in `capturedDisplayID`, which `getVirtualDisplayBounds` reports, so input maps onto the display actually shown. A main-thread `captureGeneration` counter makes a start still in flight when `stopCapture` runs fail with `CANCELLED` instead of leaving a stream and timer running. The file also defines `CaptureContentRect`, an `NSLock`-guarded singleton: `trackContentRect` (capture queue) sets it from each frame's `SCStreamFrameInfo.contentRect` × `.scaleFactor` ÷ buffer size (unscaled if the scaled rect overflows the frame) and logs `Content rect in frame:` on change; start and stop reset it to the whole frame. Requires macOS 12.3+. |
| `InputInjectPlugin.swift` | Injects mouse/keyboard events via CGEvent APIs. Requires Accessibility permission. Keeps mouse state across calls (main thread only): while a down holds `heldButton`, moves post as `.leftMouseDragged`/`.rightMouseDragged` (else `.mouseMoved`); down/up/drag set `.mouseEventClickState`, a press counting as a repeat within `NSEvent.doubleClickInterval`, same button, ≤ 24 pt (`multiClickRadius`); a down while a button is held posts that button's up first. Maps nx/ny through `CaptureContentRect` (bar taps clamp to the nearest edge) and keeps the point 1 pt inside the display bounds. `injectScroll` carries fractional wheel pixels per axis, reset when the modifier flags change, and posts each scroll with its location set to `scrollAnchor`, the point of the last move/down/up (scroll packets carry no point; the client sends a move to the gesture start or pinch centre first). macOS routes a scroll by the event's location, which a new event otherwise takes from the cursor: right after the parking move that was often the user's old position, so the first scroll of a gesture went to the window under the user's own cursor. With `setKeepCursor` on (the host's "keep the Mac cursor in place", default on), a plain move only sets `scrollAnchor` (no `.mouseMoved`). The window server still moves the cursor to every posted scroll's location (from the session tap too), so `injectScroll` posts a `.mouseMoved` back to `scrollHome` right behind each scroll on the same tap, which keeps the two in order. `scrollHome` is the cursor as read before each scroll, except a read within `staleRadius` (48 pt) of a point the cursor left in the last 0.1 s (`recentTabletPoints`: scroll anchors, and the tablet's point when a return leaves it) keeps the last value, since it may predate a move back not applied yet; a scroll that comes while a tap or drag's return is pending takes the return over (`savedCursor` becomes the home unless the user has taken the cursor), and one that comes while the user holds their own button is dropped. The visible cursor is back within a few ms, but the pointer position a physical mouse moves from can keep the anchor, and a second posted move to the same spot doesn't change it (nothing moves), so 50 ms after the last scroll `settleAfterScrolls` warps the cursor to home (`CGWarpMouseCursorPosition`, then `CGAssociateMouseAndMouseCursorPosition(1)` so the user's mouse isn't held back). Without it the next nudge of the Mac's mouse jumped the cursor to the tablet's display. A down, up or drag saves the user's cursor position first, and 0.1 s after the release with no further press, release or drag a `.mouseMoved` puts it back, unless the cursor has left `lastCursorPoint` (the user moved the mouse) or `NSEvent.pressedMouseButtons` is non-zero (the user is pressing their own button). A 0.25 s delay, with scrolls holding the cursor through their fling, felt like seconds on the device. Socket values are checked (`isFinite`, clamped scroll, `CGKeyCode(exactly:)`). `releaseAll` lets go of a held button, hands back a borrowed cursor and clears click/scroll state; `HostConnectionManager.onTeardown()` calls it first via `InputInjectChannel.releaseAll()`. `TOUCH_EVENT`s (`_injectTouch`) take the same path. |
| `AdbManagerPlugin.swift` | Runs the `adb` binary: `devices -l`, `reverse tcp:P tcp:P`, `reverse --remove-all`, and `shell input …` (reverse-remote input injection). Finds `adb` at three fixed paths, not `$PATH`. |
| `PermissionsPlugin.swift` | Checks macOS permissions (Screen Recording, Accessibility) and opens their System Settings privacy panes, over the `extended_screen/permissions` `MethodChannel`. It never prompts: the prompting calls are `ScreenCapturePlugin`'s `requestPermission` and `InputInjectPlugin`'s `requestAccessibility`, both made in `HostConnectionManager._startCapture()`. |
| `RemoteVideoPlugin.swift` | Reverse-remote direction (Mac views tablet): VideoToolbox-decodes the H.264/H.265 Annex-B stream coming *from* the tablet and exposes decoded frames to Flutter as a `FlutterTexture` (channels `extended_screen/remote_video` + binary `extended_screen/remote_nal`). Mirror image of the Android `VideoDecoderPlugin`. |
| `SocketSender.swift` | (legacy/alternative) NWConnection TCP sender; main path now goes through `SocketService` on the Dart side. |

Plugins are registered in `MainFlutterWindow.swift` against the Flutter engine. On both platforms they are hand-written (not pub plugins) on channels named `extended_screen/<name>`, each with a Dart wrapper (`*_channel.dart`, or `AdbService`). The exception is `SurfaceViewPlugin`, which has no channel or wrapper: it registers the platform-view type `extended_screen/surface_view`, which `display_view.dart` embeds with `AndroidView`. Adding a native method means touching the wrapper and the Swift/Kotlin handler; a new plugin also needs registering in `MainFlutterWindow.swift` / `MainActivity.kt`. A new Swift file is only compiled once it is added to the Runner target in `macos/Runner.xcodeproj/project.pbxproj`, which lists each source explicitly (`PBXBuildFile`, `PBXFileReference`, Runner group and Sources build-phase entries); a new Android `Service` also needs a `<service>` entry in `AndroidManifest.xml`, and a foreground service that only serves the Dart side also needs stopping with the activity (see *Native Android plugins*).

`AppDelegate` keeps the app alive after its window closes (a menu-bar item reopens it), so streaming continues with no window. The host cannot run sandboxed, since it execs `adb` and posts CGEvents; that is why neither `DebugProfile.entitlements` (Debug/Profile builds) nor `Release.entitlements` (Release builds) has an App Sandbox key.

### Native Android plugins (`android/app/src/main/kotlin/com/example/extendedscreen/plugins/`)

| File | Purpose |
|---|---|
| `VideoDecoderPlugin.kt` | `MediaCodec` H.264/H.265 hardware decode. A separate `BasicMessageChannel` with `BinaryCodec` (`extended_screen/nal_feed`) carries raw NAL data (avoids `StandardMessageCodec` overhead on the hot path); calls back into Dart via `onRequestIdr`/`onCodecError`. Decodes onto the surface from `SurfaceViewPlugin`. Frames waiting for an input buffer sit in `nalQueue`, capped by `queueCap()` = max(6, `pendingFps` ÷ 10), about 100 ms at the host's stream rate (`pendingFps` follows `initialize`/`setRefreshRate`, not the codec's operating rate). On overflow `dropForOverflow()` resumes from a keyframe (the incoming one, else the newest queued one), else clears the queue and sets `awaitingKeyframe`, which drops every frame until one passes `isKeyframeAccessUnit(au, hevc)` (top-level, no Android types; H.264 SPS/IDR, HEVC VPS/SPS/PPS/IRAP). Every new codec does the same via `restartInputFromKeyframe()`. Those waits ask for an IDR through `requestIdrThrottled()`: none without a codec, at most every 750 ms, backing off to 8 s while the codec frees no input buffers. Every discarded frame counts in `getDropCount` (the HUD's drop/s). `initialize` on a configured codec only stores the new params (`tryConfigure()` returns early), so dispose first to switch codec; `isHevc` is set by `initialize` and survives `dispose`. Queue and codec state is `@Synchronized`; all callers run on the main thread today. |
| `SurfaceViewPlugin.kt` | Registers a `PlatformView` (`DecoderSurfaceView`) so the decoder can render directly to an Android `SurfaceView` embedded in the Flutter widget tree (`DisplayView`). |
| `PermissionsPlugin.kt` | Client-side permission MethodChannel (Android counterpart to the macOS `PermissionsPlugin`). |
| `ScreenCapturePlugin.kt` | Reverse-remote direction (Mac controls tablet): owns the MediaProjection consent flow and method/event channels for capturing *this* device's screen and streaming NAL units to the Mac. Counterpart to the macOS `ScreenCapturePlugin.swift`. |
| `ScreenCaptureService.kt` | Foreground `Service` that does the heavy lifting for `ScreenCapturePlugin.kt` — MediaProjection + `MediaCodec` encoder + `VirtualDisplay` — so capture keeps running when the user switches apps. |
| `ClientKeepAlivePlugin.kt` / `ClientKeepAliveService.kt` | Foreground `Service` (counterpart Dart channel: `lib/shared/platform/keepalive_channel.dart`) that keeps the Android client process alive in the background so the display/decode session survives app-switching. |
| `BatteryStatusPlugin.kt` | Reads the tablet's own charging state and battery level via the sticky `ACTION_BATTERY_CHANGED` intent. Its Dart wrapper `BatteryChannel` (`lib/shared/platform/battery_channel.dart`, a permanent Android-only service) polls it every 10 s; Home and the `DisplayView` HUD read its `status` to show whether USB-C is actually charging, not just data-connected. |

Plugins are registered in `MainActivity.kt`. With no cached engine, `FlutterActivity` destroys its engine, and with it the Dart socket, heartbeat and reconnect timer, every time the activity is destroyed: swiped from Recents, Back on Home (Flutter calls `finish()`), or a relaunch for a configuration change missing from `configChanges`. So `MainActivity.onDestroy()` always calls `ScreenCapturePlugin.onHostDestroyed()` (stops the capture its engine started and drops the consent token; kept, the next share would skip the prompt and then, since the token is single-use on Android 14+, fail silently in the service, or on older versions reuse a dead session's consent) and, unless `isChangingConfigurations`, stops `ClientKeepAliveService`; both `<service>` entries also set `android:stopWithTask="true"`. The keep-alive therefore covers a backgrounded app (Home, app switch, screen off), not a closed one: before this, a closed app left the notification up and a process that never reconnected. A new foreground service that only serves the Dart side needs the same. The client is landscape-locked via the manifest plus `SystemChrome` in `main()`. Android 16+ ignores that lock on large screens for apps targeting API 36, so the `MainActivity` `<activity>` declares the `android.window.PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` property (`true`) to opt back in. Apps targeting 37 can no longer opt out, so `build.gradle.kts` pins `targetSdk = 36` instead of `flutter.targetSdkVersion`; don't raise it without replacing the opt-out. It does not prevent split-screen or freeform windows.

### Display modes

- **Extend:** Creates a `CGVirtualDisplay` matching the tablet resolution; ScreenCaptureKit captures that virtual display. A new one can take a moment to appear in ScreenCaptureKit's list, so `findCaptureDisplay` looks it up once and then re-polls up to 6 times, 0.25 s apart (~1.5 s); if it never shows up, capture falls back to the main display with a `WARNING` unified-log line and releases the virtual display. The fallback is not shown in the UI.
- **Mirror:** Captures the `CGMainDisplayID()` display (the one with the menu bar; the first listed one if it is missing); no virtual display created.

The encoded frame always has the panel's aspect ratio: panel-sized at a capture scale of 2.0, half-sized for `performance`, and `customWidth` wide for `custom`. A display of another shape (Mirror from a notched MacBook or a 16:9 monitor) is scaled to fit with bars, and the tablet normalizes touches over the whole frame, so `InputInjectPlugin` maps them through `CaptureContentRect` onto the picture before scaling onto the captured display's bounds.

There is no in-place mode switch: changing the mode goes through `reconnect()` like every other setting. Remote-control sessions always capture in Mirror regardless of the setting.

The only in-session rebuild is `HostConnectionManager._restartCapture()`, fired through `ScreenCaptureChannel.onCaptureRestartNeeded` when the Swift plugin invokes `onCaptureNeedsRestart` (the Mac wakes from sleep) or `onStreamStopped` (the `SCStream` stops with an error). Sleep invalidates ScreenCaptureKit, the virtual display and the VideoToolbox session, but the ADB socket survives, so after a short sleep or a display-only wake nothing else would recover. (A link that sat silent past the 6 s heartbeat timeout goes through `handleLinkFailure()` instead, which rebuilds the whole session.) The rebuild is skipped in reverse remote. It stops capture, recreates the virtual display, re-runs `_startCapture()` and forces an IDR. It does not call `releaseAll()`: the link is alive, so the tablet's mouse-up still arrives. `onDisplayBoundsChanged` (displays rearranged in System Settings) only refreshes the cached bounds that map normalized input coordinates to screen space.

### Key settings (`lib/shared/services/settings_service.dart`)

Persisted via `shared_preferences`: session mode and remote direction, display mode, last paired device serial and model name, the client's panel size and top refresh rate (from its HELLO, so presets stay correct across launches), encode preset (plus custom width/height/bitrate/refresh for the `custom` preset), codec (`h264`/`h265`; with none saved, `init()` resolves it once at launch via `SettingsService.defaultCodecFor` — H.265 for `max`, H.264 otherwise — and it does not follow later preset changes, except that selecting `max` in the picker sets and saves H.265), UI locale (`en`/`th`), performance/HUD overlay toggles, and "keep the Mac cursor in place" (`keep_mac_cursor`, default on; host only). A build-time `--dart-define=DEVICE_SERIAL=<serial>` (a default is baked in) does not pin the target device: it is only what `lastDeviceSerial` returns when no serial has been saved, and the host reads that getter only when `connect()` is called without a serial and with no active device (the Home device picker and the single-device auto-connect always pass one). If the preferred serial isn't attached, the first ADB device is used. `flutter_secure_storage`, `permission_handler`, `protobuf` and `async` are declared in `pubspec.yaml` but not imported anywhere yet.

### Encode presets (`lib/shared/models/display_config_model.dart`)

`EncodePreset` bundles resolution + scale factor + bitrate + refresh rate into five presets: `max` (the default), `quality`, `balanced`, `performance`, and `custom` (user-adjustable values persisted in settings); there is no separate frame-rate setting. `max` is native resolution at the client panel's top refresh rate (`clientMaxRefreshHz`, from the HELLO); its bitrate is `_qualityBitsPerPixel` (Quality's 20 Mbps at a fixed 2960×1848 @ 60 Hz reference) × panel pixels × top rate, clamped to 8 to 50 Mbps, so on a smaller panel it can be below Quality's fixed 20 Mbps. It passes `adaptiveFps` to the Swift encoder, which adapts over the ladder 30/45/60/90/120 plus the start rate, never above it. A saturated VideoToolbox session doesn't skip frames — `VTCompressionSessionEncodeFrame` blocks the timer thread once ~8 frames are in flight — so overload is detected as the encode queue pinned near that cap or the timer falling under 90% of its rate. After 3 s of that it drops straight to the highest rate that fits in 95% of the achieved throughput (e.g. an M3 Pro's H.264 session saturates near 50 fps at 2960×1848, so it lands on 45; HEVC sustains ~2× that), and steps back up one notch after `stepUpDelay` healthy seconds (10 s, doubling up to 5 min whenever a step-up fails within 30 s). Each change is reported via `onFrameRateChanged` so the host re-announces `0xFB`. While capturing, the plugin holds a `ProcessInfo` activity (`userInitiatedAllowingIdleSystemSleep` + `latencyCritical`) so App Nap can't throttle the usually-hidden host and stall encoding. In reverse remote (tablet encodes), `max` falls back to native @ 60 Hz / 20 Mbps. Fixed-preset resolutions are **relative to the connected client's panel** (read from `SettingsService.clientPanelWidth/Height`): logical size is always panel ÷ 2; `scaleFactor` 2.0 (quality/balanced) encodes at native panel resolution, 1.0 (performance) at half. Custom's width is the **physical encode width** (the picker labels each option as physical W×H): the desktop stays at panel ÷ 2 logical like the fixed presets, and `SettingsService.captureScaleFactor` becomes `customWidth ÷ (panel width ÷ 2)`. `customHeight` is only persisted and displayed, never used for capture: the encoded height is (panel height ÷ 2) × that scale, so it follows the panel's aspect ratio (the 1920×1200 option encodes at 1920×1198 on a 2960×1848 panel). The Swift `startCapture` multiplies logical × `scaleFactor` (clamped to even dims); `CGVirtualDisplay` is always created at logical × 2 (HiDPI). `HostConnectionManager._startCapture()` reads the active preset and applies the values to `DisplayConfigModel` at once.
