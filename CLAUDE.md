# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Purpose

**extendedscreen** turns an Android tablet into a second monitor for macOS via USB-C, or over Wi-Fi once the two have been paired over USB (see *Link types*). The macOS app (Flutter + Swift native plugins) captures the screen and streams H.264/H.265 over an ADB-reverse TCP tunnel (USB) or TLS on the LAN (Wi-Fi); the Android app (same Flutter codebase, different platform role) decodes and renders frames while sending touch gestures back as mouse events (click, scroll, drag, pinch); it forwards no keyboard input. **Nothing is hardcoded to a specific tablet model**: the client reports its native panel size in the HELLO handshake and the host derives all capture/encode resolutions from the connected device. The Android client is landscape-locked (manifest + `SystemChrome` in `main()`, kept on Android 16+ by a manifest opt-out, which only works while `build.gradle.kts` pins `targetSdk` to 36; see *Native Android plugins*). A second session mode, remote control, reuses the same link to drive the Mac from the tablet, or to view and drive the tablet from the Mac (see *Session modes and stream direction*).

- An end-to-end session needs both sides running: the macOS host and the Android client are the same app. `.vscode/launch.json` has a compound config that launches both; its device id and `DEVICE_SERIAL` are one specific tablet's serial.
- The Mac app's preferences are `~/Library/Preferences/com.example.extendedscreen.plist` (keys prefixed `flutter.`). On a Mac that ever ran a sandboxed build of this bundle id, `defaults read com.example.extendedscreen` answers from the leftover container (`~/Library/Containers/com.example.extendedscreen/…`) instead, and a `defaults write` goes there too, where the app never looks. Give `defaults` the path: `defaults read ~/Library/Preferences/com.example.extendedscreen flutter.link_type`.
- `adb` is **not** resolved from `$PATH`. `AdbManagerPlugin.adbRun` probes `/usr/local/bin/adb`, `/opt/homebrew/bin/adb`, then `~/Library/Android/sdk/platform-tools/adb`.
- The USB link is TCP `127.0.0.1:7001` on both ends (`BaseConnectionManager.host`/`port`), tunnelled with `adb reverse tcp:7001 tcp:7001`. The Wi-Fi link is TLS on the same port on the Mac's LAN address, plus UDP 7001 for discovery.
- `flutter analyze` covers Dart only (`analysis_options.yaml` excludes `android/**` and `macos/**`); Swift and Kotlin are checked only by building. It is not clean today: every `return abandon(…)` in the two `connect()` methods raises `unawaited_return_in_try_block` (14 warnings, no errors), so those are not regressions.
- The Runner target's Release configuration signs manually with a fixed `DEVELOPMENT_TEAM`, so `flutter build macos` needs that team's certificate; Debug signs ad hoc. The Android `release` build type signs with the debug key.
- Dart logs go through `LoggerService`, a `logger` instance with the package's default `DevelopmentFilter`: they print to the console, in debug builds only. In profile and release builds the Swift `esLog` lines (the `log stream` command above) are the only diagnostics, so a Dart-side failure such as capture not starting leaves no trace.
- Tests use `SharedPreferences.setMockInitialValues`, fake `BaseConnectionManager`/`DisplayController` subclasses, or (`display_codec_test.dart`) mock handlers on the `extended_screen/video_decoder` and `nal_feed` channels. That file also fakes wakelock_plus's macOS channel and its pigeon channel; on a Linux or Windows test host wakelock_plus registers a different implementation, so it may need another fake there. `wifi_link_test.dart` is the exception to fakes: it opens real loopback sockets (plain `test()`, since `testWidgets`' fake clock never completes real I/O) and gets a real certificate from `/usr/bin/openssl`, skipping those tests where that binary is missing. It runs a `HostConnectionManager` and a `ClientConnectionManager` side by side by passing each its own `SocketService` and a free port (the managers' optional `socket`/`port` constructor arguments exist for this, as does `SocketService(tlsDialTimeout:)`). A discovery test that expects an answer on each of this machine's addresses keeps only those a datagram comes back on (`_udpReachesItself`): a VPN tunnel's address is in `lanAddresses()` too and answers nothing. Several of its tests play a hostile machine on the LAN (connect and leave, skip the token, flood discovery, announce a huge packet); they take a few seconds each because they wait out real timeouts. Its `_NoAdb` fake can pretend the tunnel came up (`tunnel`) and stands in for the tablet's end of both adb broadcasts (`tablet`, normally `_fromAdb`, which calls the `extended_screen/wifi_pairing` channel as the Kotlin receiver does; `appOpen = false` makes a USB session key reach nobody, `pairings = false` a pairing). `_Stranger` is a raw socket on the Mac's USB port (anything on the tablet that dials the tunnel), and `_Tunnel` a recording proxy standing where adb's tunnel does (pass the client its port) for the tests that look at the bytes on the link. Any test that builds a `ClientConnectionManager` on the USB link has to register a `UsbSessionService`, and a fake socket that should reach `streaming` has to answer the `0xF4` hello (`display_codec_test.dart`'s `_LoopbackSocket` does). In a `testWidgets`, change `WifiPairingService.pairedHosts` once per `tester.runAsync`, with a `pump` after it: a second change inside the same `runAsync` never returns.

## Architecture

### Dual-role Flutter app, organized by feature module

The same Dart codebase runs on both sides of the link. The tree is organized **by feature module first, then by role**, with a central shared backbone (imports are `package:extendedscreen/...`):

- **`lib/shared/`** — the cross-mode backbone used by both roles *and* both feature modules:
  - `connection/` — `socket_service`, `connection_state`, the abstract `BaseConnectionManager`, plus the concrete `HostConnectionManager`, `ClientConnectionManager`, `AdbService`, the two Wi-Fi services (`WifiPairingService`, `WifiDiscoveryService`, registered on both roles) and `UsbSessionService` (the USB session handshake; an instance only on the client, where it holds the key adb delivered). Both concrete managers call into *both* feature modules, so they live here rather than in a module; only the host branches on the mode (`SettingsService.isReverseRemote` / `effectiveDisplayMode`), while the client just follows the host's `0xF9` / `0xF8` / `0xF7` packets.
  - `models/`, `protocol/`, `services/` (logger, settings, translations), `platform/` (`permissions_channel`, `keepalive_channel`, `battery_channel`, `wifi_pairing_channel`), shared `widgets/`.
  - `features/` — mode-agnostic UI shells: `splash/`, `home/` (connection screen, both roles/modes — the host also picks the `SessionMode` here via an inline selector), `settings/` (the host's control surface; on the client it shows only language, permissions and info).
- **`lib/modules/extended_screen/`** — the second-monitor streaming pipeline:
  - `host/` — `screen_capture_channel`, `input_inject_channel` (macOS capture + input injection).
  - `client/` — `video_decoder_channel` and the `display/` feature (Android decode + render). Also reused by the remote tab-controls-Mac direction.
- **`lib/modules/remote_screen/`** — the remote-control additions:
  - `host/` — `remote_video_channel` (macOS decodes the tablet stream) and the `remote_host/` feature (Mac-views-tablet UI).
  - `client/` — `android_capture_channel` (Android captures + encodes its own screen).
- **`lib/app/`** — app shell: `app.dart`, `theme/`, `routes/`, `bindings/initial_binding.dart`.

Note: because the move was structure-only (no behavior rewrite), the shared connection managers import a couple of module-owned channels (e.g. `HostConnectionManager` → `remote_screen/.../remote_video_channel`; `ClientConnectionManager` → `remote_screen/.../android_capture_channel`). These are runtime `Get.find` dependencies whose imports are type-only — a deliberate, acyclic "shared depends on module" edge.

Roles:

- **Host (macOS):** runs `adb reverse`, starts a TCP server, captures the screen via `ScreenCapturePlugin` (Swift/ScreenCaptureKit), encodes with VideoToolbox (H.264 or H.265/HEVC selectable), and streams `FRAME_DATA` packets. Injects touch/mouse/key events received from the tablet via `InputInjectPlugin`.
- **Client (Android):** dials into the ADB-reverse tunnel, decodes H.264/H.265 frames (via `VideoDecoderChannel`), renders them in `DisplayView`, and forwards user input back as packets.

### Session modes and stream direction (`lib/shared/models/session_mode.dart`)

Three host-chosen, persisted enums decide which pipeline runs. The client never chooses; it learns the mode from the host's `0xF9`.

| `SessionMode` | `RemoteDirection` | Video flows | Capture source | Input path |
|---|---|---|---|---|
| `extendedScreen` | (unused) | Mac → tablet | `DisplayMode` setting (Extend or Mirror) | tablet packets → `InputInjectPlugin` (CGEvent) |
| `remoteControl` | `tabControlsMac` | Mac → tablet | always Mirror (`SettingsService.effectiveDisplayMode`) | same as above |
| `remoteControl` | `macControlsTab` (USB only) | tablet → Mac | Android MediaProjection | `HostConnectionManager.sendRemoteTap/Swipe` → `adb shell input` (no packets) |

The last row is "reverse remote" (`SettingsService.isReverseRemote`), the only case where the tablet encodes and the Mac decodes. It needs adb for its input, so over Wi-Fi `SettingsService.effectiveRemoteDirection` is always `tabControlsMac` (the saved choice is kept for USB), `isReverseRemote` is false, and `0xF9` carries the effective direction. `HostConnectionManager` and `HomeController` branch on that getter; `ClientConnectionManager` does not: it only stores the mode from `0xF9` and handles `0xF8`, `0xF7` and `0xFF` with no mode check. The host sends `0xF8` with codec/fps/bitrate, the client raises `needsScreenShare` and waits for the user to tap "Start screen sharing" on Home (MediaProjection consent has to be user-initiated from the foreground), then streams `FRAME_DATA` to the Mac, which decodes into a Flutter texture (`HostConnectionManager.remoteTextureId`). The host's `onTeardown()` sends `0xF7`, so a Disconnect or a settings reconnect ends the capture and the next session needs the tap and the consent again. That `0xF7` is best-effort: if the link is already dead it never arrives, the client's `onLinkLost()` stops nothing, and the capture runs on into the next session, where `0xF8` raises `needsScreenShare` only while `isScreenSharing` is false. The tablet's encoder asks for a keyframe every second (`KEY_I_FRAME_INTERVAL = 1` in `ScreenCaptureService.kt`), but those keyframes come with its frames: on a still screen the next one was measured over a minute away. That matters when a capture outlives its session (above): the next session's new Mac decoder gets only pictures it cannot start from, and its view stayed black. So `_startRemoteReceive()` sends `0xFF` right after `0xF8` (through `_sendToClient`, since base `requestIdr()` needs an active phase and the session is still `configuring`), and the Mac's decoder asks again, at most once a second, while it is fed pictures it cannot decode (see the `0xFF` row). Neither makes a still tablet produce a frame: the picture appears with the tablet's next frame.

**Tablet screen off (reverse remote only).** The remote view's toggle calls `HostConnectionManager.setTabletScreenOff`, which works only in a live USB reverse-remote session once the tablet's first `FRAME_DATA` has arrived (`tabletStreaming`; before that its user still has to approve capture), remembers the choice once it has worked (`SettingsService.tabletScreenOff`; on is saved at once) and applies it again in the next session once its first frame has arrived and it is live, whichever comes last (`_darkenTabletIfChosen`, also run by a phase worker: a capture left running from the last session can send frames during `configuring`). One call at a time: `changingTabletScreen` covers the toggle and the remembered choice alike, and a call that finds `_tabletScreenSeq` moved on (teardown bumps it) changes nothing. On the Swift side a second hold for a serial whose hold is still starting gets that hold's answer, not `true` at once, and a release answers a hold still starting with `SCREEN_OFF_CANCELLED`. `AdbService.holdTabletScreenOff` → `AdbManagerPlugin` runs `ScreenPower` (`android/.../tools/ScreenPower.kt`) from the installed APK with the shell's privileges: `adb shell -T "CLASSPATH=$(pm path …) exec app_process / …ScreenPower hold"`. It turns every physical display's panel off with the hidden `SurfaceControl.setDisplayPowerMode` (tokens from `SurfaceControl`, or on API 34+ from `DisplayControl`, loaded with the whole `SYSTEMSERVERCLASSPATH` as scrcpy does since 3.1: with `services.jar` alone `libandroid_servers` aborts the process on some vendor ROMs). Everything is found before the panel is touched, and a helper started on a sleeping tablet refuses: SurfaceFlinger stops lighting the panel while PowerManager and DisplayManager still see an awake, ON display, so MediaProjection keeps getting frames (measured: `screenrecord` still produced frames 14 s into an idle period, at about 60 fps) and `adb shell input` still lands. Don't use DisplayManager's `requestDisplayPower` or `cmd display power-off` instead: those turn the logical display off and mirroring freezes (scrcpy #5530). Three things keep the panel from staying dark: the Mac renews a lease every 2 s (`keep` on the helper's stdin) and the helper lights the panel after 10 s without one (killing the Mac's adb client does not close the helper's input); adbd kills the helper outright when the Mac's side goes away, so before going dark it starts a watchdog (`ScreenPower watch`, `setsid`, fed `1`/`0` over a pipe) that lights the panel when that pipe ends with it off, and waits up to 5 s for its `ready` (said once it has found the panel itself), so no panel goes dark without one; and every path ends in `System.exit` (a process that loaded `libandroid_servers` crashes on a normal exit). The panel is only lit again while PowerManager says the device is interactive (lighting a sleeping one leaves it black, scrcpy #1667): `Panel.lightWhenAwake` waits up to 5 s for an asleep tablet to wake, because Android does not relight a panel after a sleep that short (its own switch to off never happened, so its wake switches nothing on: measured, a 0.3 s sleep left the tablet awake and dark), while after a longer one its wake-up lights the panel. While held, the helper reports `IPowerManager.userActivity` every 4 s, or the device idles and the mirror can go black. `onTeardown()` releases it; an unasked end (lease, cable, crash) comes back as `onTabletScreenRestored`, which clears `tabletScreenOff`. The helper changes no setting, so nothing outlives it. The physical power button puts the tablet to sleep, and on Android 16+ the lock screen that follows stops MediaProjection, so the capture ends too. The helper checks every 100 ms that PowerManager still reports interactive and that the lock screen has not appeared (and the last wake-up time, where `IPowerManager.getLastWakeup` exists; this Samsung build has none), so two quick presses are seen as well; it then ends, lighting the panel as above, and the Mac hears `onTabletScreenRestored`. `proguard-rules.pro` keeps `com.example.extendedscreen.tools.**`, which nothing in the app references, from R8, and the class suppresses the non-SDK-interface lint, which is about an app's own process.

Navigation follows the mode (`HomeController`): the client auto-opens `/display` once the link is active, except in reverse remote where it stays on Home; the host stays on Home as the capture source and only auto-opens `/remote-host` in reverse remote. The client's phase listener runs as it sets `streaming`, right after sending HELLO and before this session's `0xF9` arrives, so it sees the previous session's mode: on a switch into reverse remote it pops `/display` once `0xF9` lands, but on a switch out nothing opens `/display` until the user taps "Open View".

Inside `/display` (`display_view.dart`), the HUD bar shows for 4 s, then collapses to `_HudHandle` (a 64×48 hit area at the top centre, below any cutout via `SafeArea`) that brings it back; touches elsewhere fall through to `_TouchOverlay`. The host's `showHudOverlay` (`0xFA`) only hides the bar's stats: Back and Disconnect are always there. `_ReconnectingOverlay` (phase connecting or `error`) takes every tap and has Back (`Get.back`: the client keeps redialling and Home's phase listener reopens `/display` when the link is active again) and Disconnect (`DisplayController.onDisconnect`). Its text is one neutral `display_reconnect_hint`, because the client cannot tell a host settings restart from a lost link.

### Link types (`lib/shared/models/link_type.dart`)

`LinkType { usb, wifi }` is how the two sides reach each other. Unlike the session mode it is not negotiated: each device persists its own (`SettingsService.linkTypeRx`, picked on Home), the host deciding how it listens and the client where it dials. Both `connect()` methods read it once at the start and keep it in `_wifiSession` for the session.

- **USB** is everything described elsewhere in this file: `adb reverse` and plain TCP on loopback. The tunnel is not the trust boundary, adb is: each session's two ends prove to each other that they hold a key that only adb could have given the tablet app (see *A USB session authenticates in both directions too* below).
- **Wi-Fi** uses no adb at all. The host skips `detectingDevice`/`portForwarding` and goes `handshaking` (TLS server on every interface, `SocketService.startSecureServer`, plus the UDP discovery responder) `→ configuring → streaming`. `activeDevice` is a `DeviceModel` whose serial is the tablet's address; `setLastDevice` is not called.

**Pairing is over USB, through adb itself, and has no user step** (`WifiPairingService`). The host owns a `WifiIdentity`: a 16-byte host id, a 32-byte random token, and a self-signed RSA certificate made by `/usr/bin/openssl` on first use (a failed generation is retried on the next call). After every USB session reaches `streaming`, `HostConnectionManager._offerWifiPairing()` builds the pairing payload (the identity plus the Mac's current IPv4 addresses, `WifiDiscoveryService.lanAddresses()`) and gives it to `AdbService.deliverWifiPairing`, which runs `am broadcast -n com.example.extendedscreen/.plugins.WifiPairingReceiver -a com.example.extendedscreen.WIFI_PAIR --es payload '<base64url>'` in the device's shell:

- The command reaches `adb -s <serial> shell -T` on stdin (`AdbManagerPlugin`'s `shellScript`, the pipe filled before adb starts), not in its arguments: the payload holds the token, and every process on the Mac can read another's arguments.
- The manifest guards the receiver with `android.permission.DUMP`. The shell holds it; an installed app cannot, short of `adb shell pm grant` (androidx.profileinstaller guards its receiver the same way). So only adb can deliver a pairing, and `-n` means only this app receives one.
- `WifiPairingReceiver.kt` passes the bytes to Dart on `extended_screen/wifi_pairing` (`WifiPairingChannel`, registered on Android only), which calls `storePairing`. Dart's answer becomes the broadcast's result code (1 stored, 2 refused, 0 nobody took it: no engine running, or a build without the receiver); `am broadcast` prints it and `AdbService.broadcastResultCode` reads it into an `AdbDelivery`, which for a pairing the host only logs.

The name in the pairing, and in discovery replies, is `macDisplayName()` (`lib/shared/platform/host_name.dart`): the Computer Name from `/usr/sbin/scutil --get ComputerName`, else the first label of `Platform.localHostname`, cut to 64 UTF-8 bytes between characters. `Platform.localHostname` alone is whatever the current network calls the Mac (a VPN's reverse-DNS name, for one), so don't show it. The tablet shows the name it stored (`PairedHost.name`), which changes only when the next USB session pairs again.

The client stores a `PairedHost` (replacing one with the same id, keeping its `lastAddress`). `storePairing` refuses one that names an already paired host id with a different certificate or token (ids are public, and a real Mac creates all three together), and drops loopback, zero, multicast and broadcast addresses from the list. Identity and pairings live in `SharedPreferences` (`wifi_*` keys), not in `flutter_secure_storage`.

**Nothing that arrives on the link can pair.** The pairing used to travel as a `0xF6` control packet on USB sessions, which trusted the socket in both directions, and neither end knows who is on it. The tablet's "USB session" is whatever answered on its own `127.0.0.1:7001`: adb while a Mac has its tunnel up, any app on the tablet the rest of the time (the client redials every 5 s). The host's USB peer is whatever on the tablet dialled the tunnel first, and it would have been sent the token. So the host never puts a pairing on the socket, `ClientConnectionManager.onRolePacket` ignores `0xF6` on every link (don't reuse the byte), and `storePairing` must never be called with bytes that came from a packet. The session itself no longer rests on the socket either (next but one paragraph). Host and client are separately installed builds, and an old one on either side simply never pairs (the new host's broadcast finds no receiver; the new client ignores the old host's `0xF6`); pairings stored by earlier builds stay valid.

**Unpairing.** On the tablet, each paired Mac has its own row in Home's `_WifiClientCard` with a Forget button: after `showConfirmDialog` (`lib/shared/widgets/confirm_dialog.dart`) it calls `HomeController.onForgetHost` → `WifiPairingService.forget(id)`, then restarts a pending Wi-Fi dial (`_redialClient`, which leaves a stopped tablet stopped). On the Mac, Settings → Wi-Fi → Reset Wi-Fi pairing (host only, also confirmed) calls `BaseConnectionManager.resetWifiIdentity()`, a no-op on the client. The host's override runs `WifiPairingService.resetIdentity()`, which removes the four identity preferences and the memoised identity (a reset waits for a creation still in flight, and `_loadOrCreateIdentity` waits for a reset in flight, so neither can bring the old identity back). Then, if a Wi-Fi attempt or session is up, it does `disconnect()` and an unawaited `connect()`, because the TLS server still presents the old certificate and a connected tablet got in with the old token; a live USB session carries on and is handed the new identity at once (`_usbSessionSeq`). It does not go through `SettingsController`'s debounced `reconnect()`. There is one token for all tablets, so the Mac cannot revoke a single one, and a tablet keeps its entry for the old identity until it is forgotten there (after pairing again it lists the Mac twice).

**A Wi-Fi session authenticates in both directions.** The client dials with no trusted roots, so every certificate goes to `onBadCertificate`, which accepts only one equal to a paired host's DER (`WifiPairingService.hostForCert`), and it checks the peer certificate again after connecting. Its first packet is `0xF5` with that host's token. Anything on the network can complete the TLS handshake with the host, so the host treats a client as a stranger until that token passes `WifiIdentity.tokenMatches` (constant time), and the trust belongs to the connection, not to the session: `SocketService.connectionId` changes whenever a socket is installed, the host stores the id that authenticated in `_authedConnection`, and its `peerTrusted` is `_authedConnection == socket.connectionId`, on both links (a USB client earns it differently, see below). The server accepts whoever dials next the moment a client drops, before teardown has run, so a flag would let that newcomer inherit the previous client's standing. Both directions go through it:

- **Inbound:** `BaseConnectionManager._handlePacket` calls `admitPacket()` before anything else, heartbeats included. The host's override admits nothing from an untrusted peer and only looks at the one packet that can earn trust (`0xF5` over Wi-Fi, `0xF4` over USB), once per connection: no HELLO, no input, no pong. Until `SocketService.trustPeer()` the client may not even announce a payload over 1024 bytes (`_dropPeer`).
- **Outbound:** every packet the host sends goes through `_sendToClient()`, and `_forwardFrame` returns unless `peerTrusted`. Never call `socket.send` from the host directly: a capture can still be running, or just starting, when the socket already belongs to someone else.

`connect()` waits 3 s for the token and otherwise throws `LinkError('error_wifi_unpaired_client')`, which goes through `handleLinkFailure()` like any failed attempt (re-listening after 1 s). A TLS handshake that fails on the server is only logged; it must not reach `packetStream` as an error, or a port scan would tear down a live session. What a machine on the LAN can still do is get in the way: hold the single client slot for those 3 s, answer discovery with garbage, or keep idle connections open (`SecureServerSocket` has no handshake timeout). On the tablet, a TLS dial that times out (`SocketService(tlsDialTimeout:)`, 8 s) cannot be closed, because dart:io offers no way to abort a handshake: it stays open until the peer closes, so a peer that accepts and stays mute costs one socket per retry.

**A USB session authenticates in both directions too** (`UsbSessionService`). A port says nothing about who is on it. The host's USB peer is whatever dialled its loopback server: any app on the tablet, through the tunnel, or any process on the Mac, directly (which used to get the screen and injected input without either macOS permission). The tablet's peer is whatever answered on its own `127.0.0.1:7001`: adb while a Mac has its tunnel up, any app the rest of the time. So every USB attempt has a key, and it travels through adb, like a pairing:

- **Made and delivered by the host.** In `connect()`, once `adb reverse` has succeeded and the server is bound, the host makes 32 random bytes (`_usbKey`) and gives them to `AdbService.deliverUsbSessionKey`: the pairing's broadcast with the action `com.example.extendedscreen.USB_SESSION` and the payload version byte + key. The call is not awaited, because the app can dial before adb has reported. On the tablet `WifiPairingReceiver` → `WifiPairingChannel` (`usbSession`) → `UsbSessionService.accept`, which keeps the key in memory only and fires `arrivals`. The key itself is never put on the socket.
- **Proved, not sent.** The client's first packet is `0xF4`: a fresh 16-byte nonce and HMAC-SHA256(key, client label + nonce) (`package:crypto`). On a hello that verifies, the host's `admitPacket` clears `_usbKey` (one session per key, so a recorded hello opens nothing), records the connection in `_authedConnection` and answers `0xF3`: HMAC-SHA256(key, host label + nonce). It answers only then, through `_sendToClient`, so the host still sends nothing at all to a peer that has not proved itself. The client's `admitPacket` admits nothing until that answer verifies for this connection (`_trustedConnection`), gives the peer one try, and `connect()` waits 2 s for it (`_answerTimeout`, deliberately shorter than the 3 s after which a host build from before the handshake would give up on HELLO and start a capture), otherwise `LinkError('error_usb_unverified_host')`. Only after it does the client send HELLO.
- **Trust is `peerTrusted`, on both roles.** `BaseConnectionManager.peerTrusted` defaults to false; the host overrides it as above, the client with `_trustedConnection == socket.connectionId` (set after the certificate check over Wi-Fi, after the answer over USB). The base uses it for `admitPacket`'s default, for `packetStream` (so `DisplayController` is never fed a frame from an unproven peer), for the input and IDR send helpers and for the heartbeat ping; the client's reverse-capture frames check it too, since that capture can outlive its session. An unproven peer may not announce a payload over 1024 bytes on either side (`startServer(untrustedPayloadLimit:)`, `SocketService.distrustPeer()`), until `trustPeer()`.
- **A key is only for connections dialled after it arrived.** The client reads `UsbSessionService.key` before `socket.connect` and judges that connection by that key alone. A key that arrives later (`_onSessionKey`) makes it drop what it has and dial again at once (`BaseConnectionManager.restartLink()`: a link loss whose retry is immediate, so the keep-alive service is left alone), unless the user had stopped it (`disconnected`) or the dial in flight, or the live session, was made with that very key. Without this rule an app could sit in the middle: it holds port 7001 before any tunnel exists, takes the tablet's dial, closes its listener but keeps the connection, and once the Mac's tunnel is up passes everything on in both directions. With it, a key is used only on a dial that reaches adb, because the host makes the key after its own `adb reverse` and an app cannot bind the port while adb holds it. For the same reason the host must never run `adb reverse` a second time inside one attempt.
- **A hello without the right key does not fail the attempt.** From this app it means the key has not arrived: the app was opened after the host started waiting (its delivery reached nobody, result 0), or a dial and a delivery crossed. The host's `connect()` loops: `SocketService.dropClient()` (closes the client without reporting a lost link; the server keeps listening), delivers the same key again unless the app confirmed taking it within the last second, and waits for the next client, back in `handshaking`. If that delivery is not `stored` it throws `LinkError('error_usb_key_not_delivered')`. Three seconds with no hello at all (a tablet build from before the handshake opens with HELLO), or more than 8 keyless hellos in one attempt, throw `LinkError('error_usb_unverified_client')`. Both go through `handleLinkFailure()`, and the retry makes a new key.

Nothing falls back to trusting the socket. A new host with an old tablet build: the key reaches nobody, the old client's HELLO is not admitted, and every 5 s redial ends in `error_usb_unverified_client` on the Mac while the tablet's display opens and closes. An old host with a new tablet build: no key ever arrives, the old host ignores the keyless hello, the client hangs up after 2 s with `error_usb_unverified_host` and tries again every 5 s; the old host re-listens each time and never starts a capture. What is left: whatever can run adb on the Mac is inside the boundary (it can deliver a key of its own, re-point the tunnel, or read `am`'s arguments in the tablet's shell, where the key is visible to the shell user and to no app); another app on the tablet can still get in the way (dial the tunnel first and hold the single client slot for up to 3 s per attempt); and after the handshake the link is as before, plain TCP that only adb and loopback protect.

**Finding the Mac** (`ClientConnectionManager._findWifiHost`): one `WifiDiscoveryService.probe()` sends `EXTD?` on UDP 7001 to 255.255.255.255, to each interface's /24 broadcast, and directly (`directTargets`) to every address a paired Mac might have: the one typed on Home (`SettingsService.wifiHostAddress`), each `PairedHost.lastAddress`, and each `PairedHost.addresses` entry from pairing. The Mac replies unicast with id, name and TCP port, and the first reply from a paired host id is dialled. The direct targets are what reach a Mac on another subnet (a tablet behind a mesh router doing NAT, as on the development network), and probing them all is why a stale typed address does not hide a Mac that answers elsewhere. With no reply a known address is dialled anyway (UDP can be filtered where TCP is not), a different one on each attempt, starting with the typed one; with no address either it throws `LinkError('error_wifi_host_not_found')`, and with no pairing at all `LinkError('error_wifi_not_paired')` without probing. The typed address is stored through `SettingsService.normalizeHostAddress` (trimmed, a copied `:port` removed, anything that is not an IPv4 address or host name stored as empty). Discovery replies are not trusted: they only say where to dial. `WifiDiscoveryService(udpPort:, broadcast:)` lets tests run it on a free loopback port without broadcasting. Two dart:io behaviours shape `WifiDiscoveryService`, and both have bitten:

- A datagram that can't be sent does not throw: it is reported as an error on the socket's stream, and the socket is closed. So `probe()` gives each target a socket of its own (one unreachable target must not cost the replies to the others), and the host's responder binds itself again 1 s after an error.
- A read handler is called again, from a microtask, for as long as a datagram waits on an open socket. A handler that returns without `receive()`-ing it spins for ever and freezes the whole app, because microtasks run before the event loop gets the turn that would close the socket. On an ordinary network the Mac answers the broadcast, the subnet broadcast and its own address at once, so several of the probe's sockets hold a reply at the moment the first one decides it. `probe()` therefore binds all its sockets before sending, and `finish()` closes every one of them synchronously the instant the probe is decided (first paired reply, or 64 datagrams read); never `await` between deciding and closing. The responder, which must keep reading, handles 32 datagrams and then switches `readEventsEnabled` off until a `Timer.run`, sends at most 20 replies a second, and is stopped as soon as a client authenticates (the next listen starts it again).

**Pacing.** The two TLS entry points put `SocketService` in paced mode: every write goes through a queue and one `flush()` at a time (an `IOSink` rejects `add()` while a flush is pending, so nothing may write to a paced socket directly, and `disconnect()` uses `destroy()` because `close()` throws then). `isCongested` is true when data queued more than 120 ms ago has not been flushed; `sendFrame()` then returns false. `HostConnectionManager._forwardFrame` drops frames from that point until the link has drained and `isKeyframeAccessUnit` (`lib/shared/protocol/annexb.dart`, the Dart twin of the Kotlin function) sees a keyframe, asking the encoder for an IDR at most every 500 ms. `_startCapture()` also caps `SO_SNDBUF` (`limitSendBuffer`, macOS only) at 400 ms of the bitrate, re-applied whenever the adapted bitrate changes: room for a keyframe (a smaller buffer, 100 ms as it once was, kept every keyframe on a link near the rate waiting past the congestion limit, so frames were refused), and no more, since the kernel's own buffer would otherwise hide a slow link for seconds and is latency the adapter can no longer cut at its floor. Over USB none of this runs: `sendFrame()` is `send()`.

**Bitrate adaptation (Wi-Fi only).** Dropping frames is the last resort; before that the encoder is fitted to the link. `_startCapture()` ends with `_startBitrateAdaptation()`: a 50 ms timer feeds `BitrateAdapter` (`lib/shared/connection/bitrate_adapter.dart`, pure arithmetic; its class comment is the reference) with the link's queue, `SocketService.unackedBytes` (bytes queued in Dart plus, on macOS, the kernel's `SO_NWRITE`: TCP data the tablet has not acknowledged; `_pump` flushes one packet at a time so a flush under way is not counted twice), taken at its low point (`_queueTrough`, read before each frame write, since a 50 ms timer sits on one phase of a 60 fps frame cycle), less one round trip of stream (`inFlight`: the heartbeat's lowest round trip of the last 30 s, 10 ms until measured, capped at 40 ms; `beginConnect()` resets `latencyMs` so a USB session's round trip is not taken for the Wi-Fi one's). It judges the smallest queue over 400 ms, so keyframe bursts don't count: a standing queue over 30 ms cuts towards 85% of what the link delivered (at most halving per step, one step per 800 ms); a refused frame cuts at once (60%, or towards the delivered rate if the window measured the link); a window in which the link carried next to nothing for 200 ms (a stall, a roam) is not judged at all. It climbs only while the stream used at least 60% of its budget over the last 1.2 s, longer than the 1 s keyframe interval (an idle screen sends little more than a keyframe a second, which fills most of a 400 ms window by itself and proves nothing about headroom), 2 s after a cut, 15% a second up to just below where the link gave out (what it delivered, remembered for 30 s and forgotten once a 5%-per-2 s probe passes it by 15%); never above the preset's bitrate, never below max(2 Mbps, preset ÷ 8). After a refusal `_forwardFrame` resumes only once `unackedBytes` is under `_resumeBelow` (~30 ms of stream): resuming with the kernel buffer still full got the resuming keyframe refused in turn. A change goes to `ScreenCaptureChannel.setBitrate` → `ScreenCapturePlugin.swift`, which leaves it in `requestedBitrate` for the timer thread to apply (`kVTCompressionPropertyKey_AverageBitRate`) before its next encode: no new session, no keyframe. The host's Home chip shows the current rate (`BaseConnectionManager.streamBitrate`, null on the client and over USB). `_stopBitrateAdaptation()` is synchronous and runs before the first await of `onTeardown()`, again inside its `_exclusive` block, and in `_restartCapture()` (the rebuilt encoder starts at the preset again); `adaptingBitrate` is the test hook. `test/bitrate_adapter_test.dart` drives the adapter, partly through a fluid model of a link with the host's send buffer, refusal and resync and an encoder with quarter-second keyframes, busy or idle (`simulate`); `wifi_link_test.dart` runs host and tablet through `_SlowLink`, a clock-paced leaky bucket on a `RawSocket` (a tick the isolate runs late must not slow the link), with `_Encoder` keeping its average around 250 ms keyframes and starting its GOP again on a forced keyframe. On a link near capacity the rate does not sit still: it moves in a band mostly below the link, because a keyframe's backlog drains only at what the link has to spare, with now and then a probe a step above. The tablet, for its part, holds a low-latency Wi-Fi lock while a Wi-Fi session streams (`KeepAliveChannel.setLowLatencyWifi`, `WifiLatencyLock` in `ClientKeepAlivePlugin.kt`), so its radio doesn't doze between frames.

On Home the host's link selector sits with the other idle-only selectors, and over Wi-Fi the device picker gives way to a card with the Mac's addresses, which stays up while the host listens (that is when the address is needed) and goes once a session is live; `ConnectionCard` then offers Connect (start listening), and `_maybeAutoConnect()` starts listening by itself under its usual conditions. On the client the selector shows whenever no session is live, and choosing a link or submitting an address restarts the pending dial (`HomeController._redialClient`) unless the user had stopped it. Two rules keep one touch from meaning two things, since `onConnectTap` decides Connect or Cancel from the phase when the finger comes up: nothing may change the phase on pointer-down (the address field's `onTapOutside` only saves), and `ConnectionCard`'s button is keyed by its label, so when the phase changes under a finger anyway (an auto-connect on app focus) the button is replaced and the touch does nothing.

### State management — GetX

`SettingsService` is constructed and `await settings.init()`-ed in `main()` **before** `runApp` so the persisted UI language is available when `GetMaterialApp` reads `locale` at first build; `InitialBinding` only registers it if not already registered. All other services are registered as `GetxService`/permanent singletons in `InitialBinding`, which inspects the platform and registers either `HostConnectionManager` or `ClientConnectionManager` **bound to the `BaseConnectionManager` type** (`Get.put<BaseConnectionManager>(...)`) — so shared UI depends on a single interface. Controllers are scoped to routes via per-feature `*Binding` classes (`HomeBinding`, `DisplayBinding`, etc.). An `Obx` only subscribes to observables read inside its own builder: Home passes `DevicePickerCard` a snapshot (`cm.availableDevices.toList()`), because a plain widget that reads an `RxList` in its own `build` registers nothing and goes stale.

Role-specific services are registered only on their platform (`ScreenCaptureChannel`, `InputInjectChannel`, `RemoteVideoChannel`, `AdbService` on macOS; `VideoDecoderChannel`, `AndroidCaptureChannel`, `BatteryChannel`, `UsbSessionService`, `WifiPairingChannel` on Android). Shared code must `Get.find` them lazily behind an `isHost` check, never as an eager field.

### Localization (`lib/shared/services/app_translations.dart`)

User-facing strings are GetX translation keys resolved with `.tr` (or `.trParams({'name': value})` for `@name` interpolation) against `AppTranslations`, which holds `en` and `th` maps. Existing exceptions: the host's USB connect errors (`HostConnectionManager.connect()` stores `e.toString()` in `errorMessage`, so Home's error banner shows raw English such as `Exception: No ADB device detected`; a new failure should throw `LinkError(key)` instead, whose `toString()` is the translation, as the Wi-Fi errors and the USB handshake's `error_usb_*` do; the client uses the key `error_waiting_for_host`, or a `LinkError`'s), the Settings Info values (`USB-C / ADB` or `Wi-Fi / TLS`, `7001`, `1.1.0`, `macOS 13+`; the version is a literal, so keep it in step with `pubspec.yaml`, and `macOS 13+` is one too and does not match the real floor, see *Native macOS plugins*), codec/unit/link labels (`H.264`/`H.265`, `Hz`, `fps`, `ms`, `drop/s`, `Mbps`, `USB-C`, `Wi-Fi`), and the Android foreground-service notification text (English literals in Kotlin). **Never hard-code UI strings** — add a key to both locale maps. This applies to enum label extensions too (`ConnectionPhaseX.label`, `EncodePresetX.label/tagline/description`, `SessionModeX`/`RemoteDirectionX`/`LinkTypeX.label/description`): they are getters, so they resolve the active locale at read time. The Settings permission rows do not: `SettingsController._buildPermissionList()` stores `.tr` results in `PermissionItem.label/description`, so they keep the old language after a locale switch until `refreshPermissions()` runs again — don't copy that pattern. `fallbackLocale` is `en`. The saved language (or device language: Thai if the system is Thai, else English) is resolved in `SettingsService.init()`; `SettingsService.setLocale()` persists the code and calls `Get.updateLocale()`.

### Connection lifecycle (`lib/shared/connection/`)

`BaseConnectionManager` owns the shared phase/latency observables, the packet loop with heartbeat handling, the reconnect timer, and input-send helpers. `connect()` and `autoConnect()` are abstract; `refreshDevices()`, `sendUiFlags()`, `startScreenShare()`, `onRolePacket()`, `onTeardown()` and `onLinkLost()` are overridable no-ops. `HostConnectionManager` and `ClientConnectionManager` implement the role specifics. Phases actually set on the happy path:

- Host: `disconnected → detectingDevice → portForwarding → handshaking` (server bound, session key handed to adb, waiting for the tablet to dial in) `→ configuring` (waiting for the client's proof, then for HELLO, starting the media pipeline) `→ streaming`. Over Wi-Fi it starts at `handshaking`, and the proof is the pairing token; there the packet loop and the proof/HELLO waiters are set up before `startSecureServer`, because the awaits between bind and `waitForClient` (the discovery responder reads the Computer Name from a process) are long enough for a tablet dialling a known address to send its token, and `packetStream` is a broadcast stream that drops what nobody listens for. Over USB a hello without the key sends it back to `handshaking` within the same attempt.
- Client: `disconnected → handshaking` (dialling; over USB also waiting for the Mac's answer to its hello) `→ configuring → streaming`

`error` is the state while a retry is pending. A `connect()` from `error` (tapping Connect on the tablet, picking a device on the Mac) is that retry run early: `beginConnect()` cancels `_reconnectTimer` and clears `_recovering`, so the attempt's own failure goes through `handleLinkFailure()` and arms the next retry instead of being swallowed by the `_recovering` guard. `adbConnecting` and `paused` exist in the enum (with labels and colours) but nothing sets them. `isActive` is streaming or paused; `isConnecting` is everything except disconnected/streaming/paused/error.

**Liveness.** Heartbeat every 2 s; 6 s without any packet from the peer calls `handleLinkFailure()`. An open socket proves nothing here: the ADB tunnel can accept the tablet's connection without ever delivering it to the host.

**Cancellation.** `disconnect()`, `handleLinkFailure()` and `restartLink()` all bump an attempt counter: any of them ends the session a `connect()` in flight was building. Each `connect()` captures `currentAttempt` and `beginConnect()` up front and must check `isCancelled(attempt)` after **every** `await`, bailing through an abandon helper that only cleans up when `isLatestConnect(seq)` (a newer attempt may already own the socket or capture; the host's `_abandon` checks again after each of its own awaits). Keep to this pattern when adding an `await` to either `connect()`. The bump in `handleLinkFailure()` is what stops an attempt whose link already failed from waking later (on a timeout, typically) and failing a second time into the retry that replaced it; the host's `onTeardown()` also completes the proof and HELLO waits, and the client's `onLinkLost()` the wait for the Mac's answer, so such an attempt finds out at once. (`return abandon()` in the two `connect()` methods is what `flutter analyze` warns about; the cancellation checks added for the USB handshake use `await abandon(); return;`, which does not.) `handleLinkFailure()` remembers the value it bumped to and, after its awaits, arms no retry if a `disconnect()` has bumped it again: a Cancel pressed while a lost link is still being torn down (the host's teardown can wait a second or two behind a capture start) stays cancelled. `SocketService` has the same idea one level down: `_dialGen` makes a dial that finishes after a `disconnect()` or another dial drop its socket instead of installing it, and `_bind` ignores events from a socket that is no longer the current one.

**The host's media pipeline is a queue.** `_startCapture` / `_startRemoteReceive`, `_restartCapture` and the stop in `onTeardown()` run through `_exclusive()`, one after the other. A session can end while its capture is still starting; the stop then runs right after that start instead of beside it, so it always wins. `_startCapture(attempt)` returns after any of its awaits once `isCancelled(attempt)`, leaving the cleanup to that queued stop. Don't start or stop capture outside the queue.

**Who initiates.** `SplashController` (route `/`) calls `autoConnect()` once, from `onInit` (not `onReady`, which waits for a frame), and replaces itself with `/home` 2 s later. The client always dials and retries until the host is up, and over USB dials at once when adb delivers a session key (the host has just started an attempt), so it no longer waits out its 5 s retry after the Mac connects or reconnects for a settings change. The host connects without a tap through `BaseConnectionManager.connectIfUnambiguous()`: only when the phase is `disconnected` and exactly one candidate device is present (emulators are ignored when a physical device is attached); over Wi-Fi the device condition does not apply, connecting only means listening. Two callers, both checking Screen Recording and Accessibility first (`PermissionsChannel.hostGranted()`): the host's `autoConnect()` at launch, and `HomeController._maybeAutoConnect()` (Home init and each app resume), which also does nothing while `_userStopped` is set (by the Home card's Disconnect/Cancel, cleared by the next connect from Home; the remote view's Disconnect button doesn't set it). The launch call is what connects a Mac app started behind other windows, at login or hidden: the macOS embedder reports such an app as `AppLifecycleState.hidden` (`FlutterEngine.mm`, on occlusion), the framework then draws no frames, and the `/home` route the splash pushed is not built, so Home's controller does not exist until the window is shown. Nothing on the host's connection path may wait for a frame or a built route. One layer down, `FlutterViewController` launches the engine only in `viewWillAppear`, so an app launched hidden (`open -j`, a login item set to hide) would not even run `main()` until its window was shown: `MainFlutterWindow.awakeFromNib` therefore runs the engine itself (`engine.run(withEntrypoint: nil)`) after registering the plugins.

Every link failure (socket error/close, heartbeat timeout, or a throwing connect attempt) goes through `BaseConnectionManager.handleLinkFailure()`: it stops that link's packet listener + heartbeat, runs the role's `onLinkLost()` (host: full `onTeardown()` — releases any mouse button the tablet left held (`InputInjectChannel.releaseAll()`), then capture, virtual display, adb tunnel; client: only lets go of a dial still waiting for the Mac's answer, so its keep-alive service survives for background reconnects), closes the socket (server included), sets `error`, then retries after `reconnectDelay` (client 5 s, host 1 s). One host exception: a media pipeline that fails to start is only logged (`connect()` catches a throw from `_startCapture()`; the reverse-remote decoder init in `_startRemoteReceive()` swallows its own error), so the link still reaches `streaming` with no video instead of retrying. Never retry by calling `connect()` on a live session — that stacked duplicate listeners/timers and a second server socket. `restartLink()` is the one other way a session is replaced: the same teardown as a link failure, followed by `connect()` at once (the client uses it when a new USB session key arrives). It does nothing while a `disconnect()` is still tearing down (`_stopping`): `disconnect()` sets `disconnected` only at its end, so a key arriving during the tablet's teardown used to start a link that outlived the user's Disconnect. `SocketService` owns the raw TCP socket; `AdbService` wraps `adb` CLI calls. Over USB `SocketService.send()` is fire-and-forget (`Socket.add` with `tcpNoDelay`, errors swallowed, no flush or backpressure), and the server takes one client and destroys any further connection. Nothing on the sending side reacts to a slow USB link: frames queue in the socket, Max's adaptive rate only measures encoder load, and the one relief is the client decoder's queue cap (see `VideoDecoderPlugin.kt`). Wi-Fi sockets are paced instead (see *Link types*). The **macOS host is the sole settings/control surface**: display mode, encode preset and codec are editable only on the host (the client's Settings page renders none of those controls, only language, permissions and info). Every setting change persists the value and then calls `reconnect()` (full disconnect + reconnect to the same device, debounced 350 ms in `SettingsController` so several edits in one sheet collapse into one) so the capture/encode pipeline restarts with the new value. Four things don't reconnect: the overlay/HUD toggles push `0xFA` via `sendUiFlags()`; the language picker only calls `SettingsService.setLocale()`; the "keep the Mac cursor in place" toggle is pushed to `InputInjectPlugin` by an `ever()` worker in `InputInjectChannel.onInit()`; and session mode / remote direction are picked on Home (the selectors show only while the host is neither connecting nor active), so they are just persisted and read by the next connect. On each start the host announces the active codec to the client via a `0xFC` control packet; the client's `DisplayController` rebuilds its decoder if that differs from the codec it was built with (see the `0xFC` row).

On the host, connects the user starts on Home (the Connect button, picking a device) go through `HomeController._connect()`, which is gated by `_ensureHostPermissions()`: if Screen Recording or Accessibility is missing, it snackbars, navigates to Settings with `arguments: {'scrollTo': 'permissions'}` (`SettingsController` scrolls to the Permissions header via its `permissionsKey` `GlobalKey`) and does not connect. The two automatic connects through `connectIfUnambiguous()` (the host's `autoConnect()` at launch and `_maybeAutoConnect()`) only check the permissions (`PermissionsChannel.hostGranted()` / `missingPermissions`) and never snackbar or navigate; the launch one takes `currentAttempt` first and stands down if a Cancel, Disconnect or retry came while it waited (adb's first call can take seconds; over Wi-Fi it does not wait for adb at all, and `adb devices -l` is ended after 10 s). Everything else calls `connect()` directly and skips the gate: the `handleLinkFailure()` retry, the resume reconnect in `BaseConnectionManager.didChangeAppLifecycleState`, and `reconnect()` (settings changes, the remote view's Reconnect button). In reverse remote, Home opens `/remote-host` from a phase worker and also on its first frame when the session is already live (the launch can get there before Home exists).

### Packet protocol (`lib/shared/models/packet_model.dart`, `lib/shared/protocol/packet_codec.dart`)

Framing lives in `Packet.serialize()` and `SocketService._tryParsePackets()`: a 17-byte header (4-byte magic `EXTD` + 1-byte type + 4-byte payload length + 8-byte timestamp in µs) followed by the payload, all big-endian. `PacketCodec` only encodes and decodes payloads (input events, heartbeat ping/pong) as hand-rolled binary. An unknown type byte parses as `CONTROL`, a bad magic flushes the whole receive buffer, and a header announcing more than `SocketService.maxPayloadBytes` (16 MB) drops the peer (`_dropPeer`, reported like a close by the peer). A pong echoes only the ping's nine bytes. There is no version negotiation, and host and client are separately installed builds, so a wire change needs both rebuilt (the USB handshake was such a change: a build from before it and one from after refuse each other, see *Link types*). The only tolerance is for older, shorter payloads (`decodeMouse` without the modifiers byte, `_onHello` without the size or the rate). Enums travel as `.index`: `MouseAction`, `MouseButton` and `TouchAction` in input payloads (`InputInjectPlugin.swift` switches on the raw integers) and `SessionMode`/`RemoteDirection` in `0xF9`, so append to them and never reorder.

Packet types: `FRAME_DATA` (one encoded frame as an Annex-B buffer, in whichever direction the stream runs; keyframes are prefixed with their parameter sets, so a payload can hold several NAL units despite the `nal` naming in code), `TOUCH_EVENT`, `MOUSE_EVENT`, `KEY_EVENT`, `HEARTBEAT`, `CONTROL` (`ack` and `displayConfig` are declared but unused). The Android display currently sends only `MOUSE_EVENT`: `TouchGestureRecognizer` turns touches into click, scroll (with a fling, skipped when the finger rested longer than `_flingMaxIdle`, 100 ms, before lifting), long-press drag and pinch (⌘+scroll). `DisplayController._sendMouse` always sends `MouseButton.left`, so there is no right-click. A drag is down, `MouseAction.move`s, up; extra fingers during it are ignored, and every path that ends it (lift, cancel, `_reset()`, `dispose()`) goes through `_endDrag()`, so exactly one up follows each `onDragStart`. That up is dropped if the link is already down (`sendMouse` needs an active phase); the host's `releaseAll()` on teardown covers that case. `sendTouch()`/`sendKey()` have no callers, though the host decodes and injects all three.

Control sub-commands are the first payload byte, dispatched in each manager's `onRolePacket()`:

| Byte | Direction | Meaning |
|---|---|---|
| `0x01` | client → host | HELLO (sent once the peer is trusted: after `0xF5` over Wi-Fi, after the `0xF4`/`0xF3` exchange over USB): platform byte (`0x02` = Android), panel width and height (uint16 BE each, physical px, landscape), panel top refresh rate (1 byte, Hz). The size is the whole display, not the Flutter window (which can leave out the nav bar): `ClientConnectionManager._nativePanelSize()` reads `view.display.size`, falling back to `view.physicalSize` if the display is unreported or empty. The same size drives the reverse-remote capture |
| `0xFF` | viewer → encoder | Request an IDR. Client → host normally. Host → client in reverse remote: once as the host starts receiving (`_startRemoteReceive()`, after `0xF8`), and whenever `RemoteVideoPlugin.swift` raises `onRequestIdr` (a decoder fed pictures it cannot decode, at most once a second). The tablet passes it to its encoder (`PARAMETER_KEY_REQUEST_SYNC_FRAME`), so its next frame is a keyframe; with no capture running it does nothing |
| `0xFE` | host → client | Client replies with `0xFF`. Still handled, but nothing sends it |
| `0xFC` | host → client | Codec (`0` H.264, `1` H.265). Only `ClientConnectionManager` handles it, storing it in `SettingsService`. `DisplayController` records the codec each decoder build used (`_decoderCodec`), and an `ever(codecRx)` worker rebuilds whenever the setting differs, so a display opened before the announcement (on `streaming`, with last session's codec) still switches; the codec already running causes no rebuild. A build bumps `_decoderGen`, cancels the frame subscription, and stops after any await once superseded or closed. The native decoder ignores `initialize` while configured, so a rebuild must `dispose()` first |
| `0xFB` | host → client | Stream refresh rate (Hz) |
| `0xFA` | host → client | Performance-overlay and HUD-stats toggles (HUD off hides only the stats; Back and Disconnect stay) |
| `0xF9` | host → client | `SessionMode` index + `RemoteDirection` index |
| `0xF8` | host → client | Reverse remote: start capturing (codec, fps, bitrate in Mbps) |
| `0xF7` | host → client | Reverse remote: stop capturing |
| `0xF6` | nobody sends it | Was Wi-Fi pairing on USB sessions; the client now ignores it on every link (see *Link types*). The byte is still the first one of the pairing payload that adb delivers: `0xF6`, version byte, host id (16), token (32), name (1-byte length + UTF-8), certificate (uint16 BE length + DER), then the Mac's IPv4 addresses (count byte + 4 bytes each, at most 8; a payload may end at the certificate). Built and parsed by `WifiPairingService` |
| `0xF5` | client → host | Wi-Fi sessions only, first packet: the paired host's token (32 bytes) |
| `0xF4` | client → host | USB sessions only, first packet (the hello): nonce (16) + HMAC-SHA256(session key, client label + nonce) (32). The HMAC is left out when no key has been delivered; such a hello only tells a waiting host that the app is there. Built and checked by `UsbSessionService` |
| `0xF3` | host → client | USB sessions only, the answer to a hello that proved the key: HMAC-SHA256(session key, host label + nonce) (32). Nothing else from the peer is admitted by the client before it |

The host waits (3 s timeout) for the HELLO before starting capture and persists the reported panel via `SettingsService.setClientPanel()` / `setClientMaxRefresh()`. The client sets its display mode from the host's `0xFB` (the slowest panel mode ≥ the stream rate, never below 60 Hz), not from its own (host-only) preset; a mid-stream `0xFB` only switches the panel mode (`setRefreshRate`, which also moves the decoder's input-queue cap) — the decoder is configured with the panel's top rate as its operating rate so it's never rebuilt for a rate change.

A new Swift file is only compiled once it is added to the Runner target in `macos/Runner.xcodeproj/project.pbxproj`, which lists each source explicitly (`PBXBuildFile`, `PBXFileReference`, Runner group and Sources build-phase entries); a new Android `Service` also needs a `<service>` entry in `AndroidManifest.xml`, and a foreground service that only serves the Dart side also needs stopping with the activity (see *Native Android plugins*).

`AppDelegate` keeps the app alive after its window closes (a menu-bar item reopens it), so streaming continues with no window. The host cannot run sandboxed, since it execs `adb` and posts CGEvents; that is why neither `DebugProfile.entitlements` (Debug/Profile builds) nor `Release.entitlements` (Release builds) has an App Sandbox key. `Info.plist` carries `NSLocalNetworkUsageDescription` for the Wi-Fi link: macOS 15+ asks the user before the app may talk to the local network. Extend also rests on a private API: `CGVirtualDisplay` and its descriptor, settings and mode classes are not in the public SDK, so they are declared by hand in `macos/Runner/CGVirtualDisplay.h` and reach Swift through `Runner-Bridging-Header.h`. ### Display modes

- **Extend:** Creates a `CGVirtualDisplay` matching the tablet resolution; ScreenCaptureKit captures that virtual display. A new one can take a moment to appear in ScreenCaptureKit's list, so `findCaptureDisplay` looks it up once and then re-polls up to 6 times, 0.25 s apart (~1.5 s); if it never shows up, capture falls back to the main display with a `WARNING` unified-log line and releases the virtual display. The fallback is not shown in the UI.
- **Mirror:** Captures the `CGMainDisplayID()` display (the one with the menu bar; the first listed one if it is missing); no virtual display created.

The encoded frame always has the panel's aspect ratio: panel-sized at a capture scale of 2.0, half-sized for `performance`, and `customWidth` wide for `custom`. A display of another shape (Mirror from a notched MacBook or a 16:9 monitor) is scaled to fit with bars, and the tablet normalizes touches over the whole frame, so `InputInjectPlugin` maps them through the session's `CaptureContentRect` onto the picture before scaling onto the captured display's bounds.

There is no in-place mode switch: changing the mode goes through `reconnect()` like every other setting. Remote-control sessions always capture in Mirror regardless of the setting.

The only in-session rebuild is `HostConnectionManager._restartCapture()`, fired through `ScreenCaptureChannel.onCaptureRestartNeeded` when the Swift plugin invokes `onCaptureNeedsRestart` (the Mac wakes from sleep) or `onStreamStopped` (the `SCStream` stops with an error). Sleep invalidates ScreenCaptureKit, the virtual display and the VideoToolbox session, but the ADB socket survives, so after a short sleep or a display-only wake nothing else would recover. ScreenCaptureKit also stops the stream the moment the displays go to sleep (measured), so a rebuild runs then and fails: the virtual display can't be made and no display is found. The wake is what recovers: the plugin forwards every wake once any session exists, whether or not a stream is running (it used to forward only while one was, so a display sleep left the tablet frozen for good), and Dart rebuilds whichever session is still connected. Its two notifications (system and display wake) send one `onCaptureNeedsRestart`, 1.2 s after the last of them (`wakeGeneration`). A start that fails after making its encoder stops at once, releasing the encoder and App Nap's hold. A request that arrives while a rebuild runs gets a round of its own after it (`_restartAgain`), for the session that asked. (A link that sat silent past the 6 s heartbeat timeout goes through `handleLinkFailure()` instead, which rebuilds the whole session.) The rebuild is skipped in reverse remote. It stops capture, recreates the virtual display, re-runs `_startCapture()` and forces an IDR. It does not call `releaseAll()`: the link is alive, so the tablet's mouse-up still arrives. `onDisplayBoundsChanged` (displays rearranged in System Settings) only refreshes the cached bounds that map normalized input coordinates to screen space.

### Key settings (`lib/shared/services/settings_service.dart`)

Persisted via `shared_preferences`: session mode and remote direction, link type (`link_type`, per device) and the client's typed Mac address (`wifi_host_address`), display mode, last paired device serial and model name, the client's panel size and top refresh rate (from its HELLO, so presets stay correct across launches), encode preset (plus custom width/height/bitrate/refresh for the `custom` preset), codec (`h264`/`h265`; with none saved, `init()` resolves it once at launch via `SettingsService.defaultCodecFor` — H.265 for `max`, H.264 otherwise — and it does not follow later preset changes, except that selecting `max` in the picker sets and saves H.265), UI locale (`en`/`th`), performance/HUD overlay toggles, and "keep the Mac cursor in place" (`keep_mac_cursor`, default on; host only). A build-time `--dart-define=DEVICE_SERIAL=<serial>` (a default is baked in) does not pin the target device: it is only what `lastDeviceSerial` returns when no serial has been saved, and the host reads that getter only when `connect()` is called without a serial and with no active device (the Home device picker and the single-device auto-connect always pass one). If the preferred serial isn't attached, the first ADB device is used. `crypto` is a direct dependency for the USB handshake's HMAC-SHA256. `flutter_secure_storage`, `permission_handler`, `protobuf` and `async` are declared in `pubspec.yaml` but not imported anywhere yet (`flutter_secure_storage_macos` is the plugin behind the "do not support Swift Package Manager" warning on every macOS build).

### Encode presets (`lib/shared/models/display_config_model.dart`)

`EncodePreset` bundles resolution + scale factor + bitrate + refresh rate into five presets: `max` (the default), `quality`, `balanced`, `performance`, and `custom` (user-adjustable values persisted in settings); there is no separate frame-rate setting. `max` is native resolution at the client panel's top refresh rate (`clientMaxRefreshHz`, from the HELLO); its bitrate is `_qualityBitsPerPixel` (Quality's 20 Mbps at a fixed 2960×1848 @ 60 Hz reference) × panel pixels × top rate, clamped to 8 to 50 Mbps, so on a smaller panel it can be below Quality's fixed 20 Mbps. It passes `adaptiveFps` to the Swift encoder, which adapts over the ladder 30/45/60/90/120 plus the start rate, never above it. A saturated VideoToolbox session doesn't skip frames — `VTCompressionSessionEncodeFrame` blocks the timer thread once ~8 frames are in flight — so overload is detected as the encode queue pinned near that cap or the timer falling under 90% of its rate. After 3 s of that it drops straight to the highest rate that fits in 95% of the achieved throughput (e.g. an M3 Pro's H.264 session saturates near 50 fps at 2960×1848, so it lands on 45; HEVC sustains ~2× that), and steps back up one notch after `stepUpDelay` healthy seconds (10 s, doubling up to 5 min whenever a step-up fails within 30 s). Each change is reported via `onFrameRateChanged` so the host re-announces `0xFB`. While capturing, the plugin holds a `ProcessInfo` activity (`userInitiatedAllowingIdleSystemSleep` + `latencyCritical`) so App Nap can't throttle the usually-hidden host and stall encoding. In reverse remote (tablet encodes), `max` falls back to native @ 60 Hz / 20 Mbps. Fixed-preset resolutions are **relative to the connected client's panel** (read from `SettingsService.clientPanelWidth/Height`): logical size is always panel ÷ 2; `scaleFactor` 2.0 (quality/balanced) encodes at native panel resolution, 1.0 (performance) at half. Custom's width is the **physical encode width** (the picker labels each option as physical W×H): the desktop stays at panel ÷ 2 logical like the fixed presets, and `SettingsService.captureScaleFactor` becomes `customWidth ÷ (panel width ÷ 2)`. `customHeight` is only persisted and displayed, never used for capture: the encoded height is (panel height ÷ 2) × that scale, so it follows the panel's aspect ratio (the 1920×1200 option encodes at 1920×1198 on a 2960×1848 panel). The Swift `startCapture` multiplies logical × `scaleFactor` (clamped to even dims); `CGVirtualDisplay` is always created at logical × 2 (HiDPI). `HostConnectionManager._startCapture()` reads the active preset and applies the values to `DisplayConfigModel` at once.
