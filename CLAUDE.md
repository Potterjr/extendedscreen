# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Purpose

**extendedscreen** turns an Android tablet into a second monitor for macOS via USB-C, or over Wi-Fi once the two have been paired over USB (see *Link types*); over USB in Extended screen the Mac drives several tablets at once, each its own session with its own virtual display, sharing the Mac's encoder (see *Hub and sessions*). The macOS app (Flutter + Swift native plugins) captures the screen and streams H.264/H.265 over an ADB-reverse TCP tunnel (USB) or TLS on the LAN (Wi-Fi); the Android app (same Flutter codebase, different platform role) decodes and renders frames while sending touch gestures back as mouse events (click, scroll, drag, pinch); it forwards no keyboard input. **Nothing is hardcoded to a specific tablet model**: the client reports its native panel size in the HELLO handshake and the host derives all capture/encode resolutions from the connected device. The Android client is landscape-locked (manifest + `SystemChrome` in `main()`, kept on Android 16+ by a manifest opt-out, which only works while `build.gradle.kts` pins `targetSdk` to 36; see *Native Android plugins*). A second session mode, remote control, reuses the same link to drive the Mac from the tablet, or to view and drive the tablet from the Mac (see *Session modes and stream direction*).

- An end-to-end session needs both sides running: the macOS host and the Android client are the same app. `.vscode/launch.json` has a compound config that launches both; its device id and `DEVICE_SERIAL` are one specific tablet's serial.
- The Mac app's preferences are `~/Library/Preferences/com.example.extendedscreen.plist` (keys prefixed `flutter.`). On a Mac that ever ran a sandboxed build of this bundle id, `defaults read com.example.extendedscreen` answers from the leftover container (`~/Library/Containers/com.example.extendedscreen/…`) instead, and a `defaults write` goes there too, where the app never looks. Give `defaults` the path: `defaults read ~/Library/Preferences/com.example.extendedscreen flutter.link_type`.
- `adb` is **not** resolved from `$PATH`. `AdbManagerPlugin.adbRun` probes `/usr/local/bin/adb`, `/opt/homebrew/bin/adb`, then `~/Library/Android/sdk/platform-tools/adb`.
- The USB link: the tablet dials its own `127.0.0.1:7001` (`BaseConnectionManager.host`/`port`); on the Mac each tablet's session listens on a loopback port of its own (bound to port 0), and `adb -s <serial> reverse tcp:7001 tcp:<that port>` joins the two, so `adb reverse --list` shows `tcp:7001 tcp:5xxxx`. The Wi-Fi link is TLS on 7001 on the Mac's LAN address, plus UDP 7001 for discovery.
- `flutter analyze` covers Dart only (`analysis_options.yaml` excludes `android/**` and `macos/**`); Swift and Kotlin are checked only by building. It is not clean today: every `return abandon(…)` in the two `connect()` methods raises `unawaited_return_in_try_block` (14 warnings, no errors), so those are not regressions.
- The Runner target's Release configuration signs manually with a fixed `DEVELOPMENT_TEAM`, so `flutter build macos` needs that team's certificate; Debug signs ad hoc. The Android `release` build type signs with the debug key.
- Dart logs go through `LoggerService`, a `logger` instance with the package's default `DevelopmentFilter`: they print to the console, in debug builds only. In profile and release builds the Swift `esLog` lines (the `log stream` command above) are the only diagnostics, so a Dart-side failure such as capture not starting leaves no trace.
- Tests use `SharedPreferences.setMockInitialValues`, fake `BaseConnectionManager`/`DisplayController` subclasses, or (`display_codec_test.dart`) mock handlers on the `extended_screen/video_decoder` and `nal_feed` channels. That file also fakes wakelock_plus's macOS channel and its pigeon channel; on a Linux or Windows test host wakelock_plus registers a different implementation, so it may need another fake there. `wifi_link_test.dart` is the exception to fakes: it opens real loopback sockets (plain `test()`, since `testWidgets`' fake clock never completes real I/O) and gets a real certificate from `/usr/bin/openssl`, skipping those tests where that binary is missing. It runs a `HostConnectionManager` and a `ClientConnectionManager` side by side by passing each its own `SocketService` and a free port (the managers' optional `socket`/`port` constructor arguments exist for this, as does `SocketService(tlsDialTimeout:)`; the hub hands its socket and port to the session it makes). Over USB the free port is the tablet's side: `_NoAdb.reverseForward` (with `tunnel`) binds it with a `_Forwarder` that joins each connection to the Mac port the rule names, as adb does, re-pointed by a later reverse and closed by `removeForward`. A discovery test that expects an answer on each of this machine's addresses keeps only those a datagram comes back on (`_udpReachesItself`): a VPN tunnel's address is in `lanAddresses()` too and answers nothing. Several of its tests play a hostile machine on the LAN (connect and leave, skip the token, flood discovery, announce a huge packet); they take a few seconds each because they wait out real timeouts. Its `_NoAdb` fake can pretend the tunnel came up (`tunnel`) and stands in for the tablet's end of both adb broadcasts (`tablet`, normally `_fromAdb`, which calls the `extended_screen/wifi_pairing` channel as the Kotlin receiver does; `appOpen = false` makes a USB session key reach nobody, `pairings = false` a pairing). `_Stranger` is a raw socket on the tablet's USB port (anything on the tablet that dials the tunnel), and `_Tunnel` a recording proxy standing where adb's tunnel does (pass the client its port) for the tests that look at the bytes on the link. Any test that builds a `ClientConnectionManager` on the USB link has to register a `UsbSessionService`, and a fake socket that should reach `streaming` has to answer the `0xF4` hello (`display_codec_test.dart`'s `_LoopbackSocket` does). In a `testWidgets`, change `WifiPairingService.pairedHosts` once per `tester.runAsync`, with a `pump` after it: a second change inside the same `runAsync` never returns. `host_hub_test.dart` and `multi_usb_test.dart` run the hub, or `HostSession`s built directly with one `PipelineQueue`, `TabletTunnels` and `EncodeBudget` as the hub keeps them, against tablets stood in for in-process: `FakeTablet` speaks the tablet's half of a USB session (the keyed hello, HELLO with its panel, pongs) and `SynthAdb` plays adb for them (`lib/shared/connection/debug/synthetic_tablet.dart`; it answers `listDevicesOrNull`, which `listDevices` goes through, so an adb fake that should list for the hub overrides that one, and `listingFails` makes it answer null; two real `ClientConnectionManager`s cannot share one process, both would take the one `UsbSessionService`). `FakeTablet` keeps what the Mac announced (`codec`, `rate` and every `rates` entry, `mode`, from `0xFC`/`0xFB`/`0xF9`) and its frames (`frames`, `frameStream`), sends `sendMouse` and `requestKeyframe` (`0xFF`), and `dialWith(port, key)` says hello on a connection of its own beside its session (anything that can reach a port); like the app, a key delivered again while it dials or is connected with that key changes nothing. `SynthAdb` can close a tablet's app (`appOpen[serial] = false`: a key reaches nobody) and hold its key deliveries (`deliveryGates[serial]`), unplug a tablet (`unplugged`), list a tablet under an adb transport id (`transports`), fail a listing (`listingFails`), delay reverses and removals (`reverseDelays`, `removeDelay`), and records `reverses`, `listings`, `keys`, `keysDelivered` and `pairingsDelivered`. A test's `SynthAdb(tablets)` answers every serial itself; `SynthAdb.routing(tablets)`, the app's, answers only `synth-` serials and hands every other call to the real `AdbService` channel (its test mocks `extended_screen/adb`). `multi_usb_test.dart` leaves the capture channel's real `framesFor` demux in place behind a mocked `extended_screen/frames` stream, tagging frames as Swift does, and its capture fake hands every `setFrameRateCeiling` back to that session's `frameRateChanged`, as Swift's `onFrameRateChanged` would, and answers `getHostInfo` with its `hostInfo` once `hostInfoGate` (if set) completes; its learned-capacity tests pass the hub a short `capacityWindow`; its tests read each session's `nativeId` and never assume one. The hub test's retry-timing test uses `testWidgets` for the fake clock, which works there because nothing touches a real socket. `multi_usb_test.dart`'s `_Capture` keeps each started capture's encoder rate as Swift does (`_Encoder`): a ceiling below the running rate is reported at once, a raised one only for a fixed-rate encoder, while a Max one stays put until the test plays its recovery (`recover`), so a hub test cannot pass on a raise Swift never reports; its learning tests feed `onEncoderStats` through the real channel (`feedStats`). Hubs built in tests pass `hostGranted:` (the permission check the auto-connect policy makes; without it the unmocked permissions channel answers false) and `devicePollInterval:` (null: no poll; a poll starts only with `autoConnect()` and is ended with `stopPolling`, which a test with a poll adds as a tear-down). A hub given `socket:` hands it to the first session it makes only (until that session has ended); every other session gets a `SocketService` of its own. Home's host body casts the manager to the hub, so every host-role Home test uses a hub subclass: `home_wifi_test.dart`'s `_FakeHub` (with the `_Recording` mixin the client fake shares, so Home's stops meet the real pause), `home_device_picker_test.dart`'s `_FakeHostManager` (it lists the devices itself) and `home_sessions_test.dart`'s `_Hub` (records `connect`, `disconnect` and `disconnectSession`); their sessions are `adopt`ed or put in `sessions`, never connected. `HomeController` itself reaches the hub only behind a type check (`onFocus`), because `host_launch_test.dart` runs it over a plain `BaseConnectionManager`. A Home test that switches language sets `Get.locale` and pumps a new (non-const) `HomeView`: `Get.updateLocale`'s reassemble leaves a widget test's scheduler mid-frame.

## Architecture

### Dual-role Flutter app, organized by feature module

The same Dart codebase runs on both sides of the link. The tree is organized **by feature module first, then by role**, with a central shared backbone (imports are `package:extendedscreen/...`):

- **`lib/shared/`** — the cross-mode backbone used by both roles *and* both feature modules:
  - `connection/` — `socket_service`, `connection_state`, the abstract `BaseConnectionManager`, plus the concrete `HostConnectionManager` (the host's hub) and `HostSession` (one per tablet), `PipelineQueue`, `ClientConnectionManager`, `AdbService`, the two Wi-Fi services (`WifiPairingService`, `WifiDiscoveryService`, registered on both roles) and `UsbSessionService` (the USB session handshake; an instance only on the client, where it holds the key adb delivered). Both roles call into *both* feature modules, so they live here rather than in a module; only the host branches on the mode (each `HostSession`'s `spec`, a `SessionSpec` snapshot of the settings), while the client just follows the host's `0xF9` / `0xF8` / `0xF7` packets. `debug/synthetic_tablet.dart` (`FakeTablet`, `SynthAdb`, `SyntheticTablets` and the `synthTabletCount`/`synthTablets` build flag) serves the tests and, in a debug build with `SYNTH_TABLETS`, the app (see *Synthetic tablets* under *Hub and sessions*); no profile or release build contains it.
  - `models/`, `protocol/`, `services/` (logger, settings, translations), `platform/` (`permissions_channel`, `keepalive_channel`, `battery_channel`, `wifi_pairing_channel`), shared `widgets/`.
  - `features/` — mode-agnostic UI shells: `splash/`, `home/` (connection screen, both roles/modes — the host also picks the `SessionMode` here via an inline selector), `settings/` (the host's control surface, with a Tablets card for Maximum tablets and the Encoder line; on the client it shows only language, permissions and info).
- **`lib/modules/extended_screen/`** — the second-monitor streaming pipeline:
  - `host/` — `screen_capture_channel`, `input_inject_channel` (macOS capture + input injection), and `debug/`, the Loopback preview (`/loopback-preview`, debug builds with synthetic tablets only).
  - `client/` — `video_decoder_channel` and the `display/` feature (Android decode + render). Also reused by the remote tab-controls-Mac direction.
- **`lib/modules/remote_screen/`** — the remote-control additions:
  - `host/` — `remote_video_channel` (macOS decodes the tablet stream) and the `remote_host/` feature (Mac-views-tablet UI).
  - `client/` — `android_capture_channel` (Android captures + encodes its own screen).
- **`lib/app/`** — app shell: `app.dart`, `theme/`, `routes/`, `bindings/initial_binding.dart`.

Note: because the move was structure-only (no behavior rewrite), the shared connection managers import a couple of module-owned channels (e.g. `HostSession` → `remote_screen/.../remote_video_channel`; `ClientConnectionManager` → `remote_screen/.../android_capture_channel`). These are runtime `Get.find` dependencies whose imports are type-only — a deliberate, acyclic "shared depends on module" edge.

Roles:

- **Host (macOS):** runs `adb reverse`, starts a TCP server, captures the screen via `ScreenCapturePlugin` (Swift/ScreenCaptureKit), encodes with VideoToolbox (H.264 or H.265/HEVC selectable), and streams `FRAME_DATA` packets. Injects touch/mouse/key events received from the tablet via `InputInjectPlugin`.
- **Client (Android):** dials into the ADB-reverse tunnel, decodes H.264/H.265 frames (via `VideoDecoderChannel`), renders them in `DisplayView`, and forwards user input back as packets.

### Session modes and stream direction (`lib/shared/models/session_mode.dart`)

Three host-chosen, persisted enums decide which pipeline runs. The client never chooses; it learns the mode from the host's `0xF9`.

| `SessionMode` | `RemoteDirection` | Video flows | Capture source | Input path |
|---|---|---|---|---|
| `extendedScreen` | (unused) | Mac → tablet | `DisplayMode` setting (Extend or Mirror) | tablet packets → `InputInjectPlugin` (CGEvent) |
| `remoteControl` | `tabControlsMac` | Mac → tablet | always Mirror (`SettingsService.effectiveDisplayMode`) | same as above |
| `remoteControl` | `macControlsTab` (USB only) | tablet → Mac | Android MediaProjection | `HostSession.sendRemoteTap/Swipe` (through the hub) → `adb shell input` (no packets) |

The last row is "reverse remote" (`SettingsService.isReverseRemote`), the only case where the tablet encodes and the Mac decodes. It needs adb for its input, so over Wi-Fi `SettingsService.effectiveRemoteDirection` is always `tabControlsMac` (the saved choice is kept for USB), `isReverseRemote` is false, and `0xF9` carries the effective direction. `HostSession` (through its `spec`) and `HomeController` branch on that getter; `ClientConnectionManager` does not: it only stores the mode from `0xF9` and handles `0xF8`, `0xF7` and `0xFF` with no mode check. The host sends `0xF8` with codec/fps/bitrate, the client raises `needsScreenShare` and waits for the user to tap "Start screen sharing" on Home (MediaProjection consent has to be user-initiated from the foreground), then streams `FRAME_DATA` to the Mac, which decodes into a Flutter texture (`HostConnectionManager.remoteTextureId` (the focused session's, mirrored)). The host's `onTeardown()` sends `0xF7`, so a Disconnect or a settings reconnect ends the capture and the next session needs the tap and the consent again. That `0xF7` is best-effort: if the link is already dead it never arrives, the client's `onLinkLost()` stops nothing, and the capture runs on into the next session, where `0xF8` raises `needsScreenShare` only while `isScreenSharing` is false. The tablet's encoder asks for a keyframe every second (`KEY_I_FRAME_INTERVAL = 1` in `ScreenCaptureService.kt`), but those keyframes come with its frames: on a still screen the next one was measured over a minute away. That matters when a capture outlives its session (above): the next session's new Mac decoder gets only pictures it cannot start from, and its view stayed black. So `_startRemoteReceive()` sends `0xFF` right after `0xF8` (through `_sendToClient`, since base `requestIdr()` needs an active phase and the session is still `configuring`), and the Mac's decoder asks again, at most once a second, while it is fed pictures it cannot decode (see the `0xFF` row). Neither makes a still tablet produce a frame: the picture appears with the tablet's next frame.

**Tablet screen off (reverse remote only).** The remote view's toggle calls `HostConnectionManager.setTabletScreenOff`, which hands it to the focused `HostSession.setTabletScreenOff`. That works only in a live USB reverse-remote session once the tablet's first `FRAME_DATA` has arrived (`tabletStreaming`; before that its user still has to approve capture), remembers the choice per tablet once it has worked (`SettingsService.tabletScreenOffFor(serial)`, key `tablet_screen_off.<serial>`; on is saved at once) and applies it again in the next session once its first frame has arrived and it is live, whichever comes last (`_darkenTabletIfChosen`, also run by a phase worker: a capture left running from the last session can send frames during `configuring`). One call at a time: `changingTabletScreen` covers the toggle and the remembered choice alike, and a call that finds `_tabletScreenSeq` moved on (teardown bumps it) changes nothing. On the Swift side a second hold for a serial whose hold is still starting gets that hold's answer, not `true` at once, and a release answers a hold still starting with `SCREEN_OFF_CANCELLED`. `AdbService.holdTabletScreenOff` → `AdbManagerPlugin` runs `ScreenPower` (`android/.../tools/ScreenPower.kt`) from the installed APK with the shell's privileges: `adb shell -T "CLASSPATH=$(pm path …) exec app_process / …ScreenPower hold"`. It turns every physical display's panel off with the hidden `SurfaceControl.setDisplayPowerMode` (tokens from `SurfaceControl`, or on API 34+ from `DisplayControl`, loaded with the whole `SYSTEMSERVERCLASSPATH` as scrcpy does since 3.1: with `services.jar` alone `libandroid_servers` aborts the process on some vendor ROMs). Everything is found before the panel is touched, and a helper started on a sleeping tablet refuses: SurfaceFlinger stops lighting the panel while PowerManager and DisplayManager still see an awake, ON display, so MediaProjection keeps getting frames (measured: `screenrecord` still produced frames 14 s into an idle period, at about 60 fps) and `adb shell input` still lands. Don't use DisplayManager's `requestDisplayPower` or `cmd display power-off` instead: those turn the logical display off and mirroring freezes (scrcpy #5530). Three things keep the panel from staying dark: the Mac renews a lease every 2 s (`keep` on the helper's stdin) and the helper lights the panel after 10 s without one (killing the Mac's adb client does not close the helper's input); adbd kills the helper outright when the Mac's side goes away, so before going dark it starts a watchdog (`ScreenPower watch`, `setsid`, fed `1`/`0` over a pipe) that lights the panel when that pipe ends with it off, and waits up to 5 s for its `ready` (said once it has found the panel itself), so no panel goes dark without one; and every path ends in `System.exit` (a process that loaded `libandroid_servers` crashes on a normal exit). The panel is only lit again while PowerManager says the device is interactive (lighting a sleeping one leaves it black, scrcpy #1667): `Panel.lightWhenAwake` waits up to 5 s for an asleep tablet to wake, because Android does not relight a panel after a sleep that short (its own switch to off never happened, so its wake switches nothing on: measured, a 0.3 s sleep left the tablet awake and dark), while after a longer one its wake-up lights the panel. While held, the helper reports `IPowerManager.userActivity` every 4 s, or the device idles and the mirror can go black. `onTeardown()` releases it; an unasked end (lease, cable, crash) comes back as `onTabletScreenRestored`, which the hub routes by serial to that session, clearing its `tabletScreenOff`. The helper changes no setting, so nothing outlives it. The physical power button puts the tablet to sleep, and on Android 16+ the lock screen that follows stops MediaProjection, so the capture ends too. The helper checks every 100 ms that PowerManager still reports interactive and that the lock screen has not appeared (and the last wake-up time, where `IPowerManager.getLastWakeup` exists; this Samsung build has none), so two quick presses are seen as well; it then ends, lighting the panel as above, and the Mac hears `onTabletScreenRestored`. `proguard-rules.pro` keeps `com.example.extendedscreen.tools.**`, which nothing in the app references, from R8, and the class suppresses the non-SDK-interface lint, which is about an app's own process.

Navigation follows the mode (`HomeController`): the client auto-opens `/display` once the link is active, except in reverse remote where it stays on Home; the host stays on Home as the capture source and only auto-opens `/remote-host` in reverse remote. The client's phase listener runs as it sets `streaming`, right after sending HELLO and before this session's `0xF9` arrives, so it sees the previous session's mode: on a switch into reverse remote it pops `/display` once `0xF9` lands, but on a switch out nothing opens `/display` until the user taps "Open View".

Inside `/display` (`display_view.dart`), the HUD bar shows for 4 s, then collapses to `_HudHandle` (a 64×48 hit area at the top centre, below any cutout via `SafeArea`) that brings it back; touches elsewhere fall through to `_TouchOverlay`. The host's `showHudOverlay` (`0xFA`) only hides the bar's stats: Back and Disconnect are always there. `_ReconnectingOverlay` (phase connecting or `error`) takes every tap and has Back (`Get.back`: the client keeps redialling and Home's phase listener reopens `/display` when the link is active again) and Disconnect (`DisplayController.onDisconnect`). Its text is one neutral `display_reconnect_hint`, because the client cannot tell a host settings restart from a lost link.

### Link types (`lib/shared/models/link_type.dart`)

`LinkType { usb, wifi }` is how the two sides reach each other. Unlike the session mode it is not negotiated: each device persists its own (`SettingsService.linkTypeRx`, picked on Home), the host deciding how it listens and the client where it dials. The client's `connect()` reads it once at the start and keeps it in `_wifiSession`; on the host the hub reads it when it connects and makes a session for that link, whose `link` is fixed for its life (a change while that session waits to retry ends it and connects on the new link, `_onLinkTypeChanged`).

- **USB** is everything described elsewhere in this file: `adb reverse` and plain TCP on loopback. The tunnel is not the trust boundary, adb is: each session's two ends prove to each other that they hold a key that only adb could have given the tablet app (see *A USB session authenticates in both directions too* below).
- **Wi-Fi** uses no adb at all. The host skips `detectingDevice`/`portForwarding` and goes `handshaking` (TLS server on every interface, `SocketService.startSecureServer`, plus the UDP discovery responder) `→ configuring → streaming`. `activeDevice` is a `DeviceModel` whose serial is the tablet's address; `setLastDevice` is not called.

**Pairing is over USB, through adb itself, and has no user step** (`WifiPairingService`). The host owns a `WifiIdentity`: a 16-byte host id, a 32-byte random token, and a self-signed RSA certificate made by `/usr/bin/openssl` on first use (a failed generation is retried on the next call). After every USB session reaches `streaming` (a synthetic tablet's excepted), `HostSession._offerWifiPairing()` builds the pairing payload (the identity plus the Mac's current IPv4 addresses, `WifiDiscoveryService.lanAddresses()`) and gives it to `AdbService.deliverWifiPairing`, which runs `am broadcast -n com.example.extendedscreen/.plugins.WifiPairingReceiver -a com.example.extendedscreen.WIFI_PAIR --es payload '<base64url>'` in the device's shell:

- The command reaches `adb -s <serial> shell -T` on stdin (`AdbManagerPlugin`'s `shellScript`, the pipe filled before adb starts), not in its arguments: the payload holds the token, and every process on the Mac can read another's arguments.
- The manifest guards the receiver with `android.permission.DUMP`. The shell holds it; an installed app cannot, short of `adb shell pm grant` (androidx.profileinstaller guards its receiver the same way). So only adb can deliver a pairing, and `-n` means only this app receives one.
- `WifiPairingReceiver.kt` passes the bytes to Dart on `extended_screen/wifi_pairing` (`WifiPairingChannel`, registered on Android only), which calls `storePairing`. Dart's answer becomes the broadcast's result code (1 stored, 2 refused, 0 nobody took it: no engine running, or a build without the receiver); `am broadcast` prints it and `AdbService.broadcastResultCode` reads it into an `AdbDelivery`, which for a pairing the host only logs.

The name in the pairing, and in discovery replies, is `macDisplayName()` (`lib/shared/platform/host_name.dart`): the Computer Name from `/usr/sbin/scutil --get ComputerName`, else the first label of `Platform.localHostname`, cut to 64 UTF-8 bytes between characters. `Platform.localHostname` alone is whatever the current network calls the Mac (a VPN's reverse-DNS name, for one), so don't show it. The tablet shows the name it stored (`PairedHost.name`), which changes only when the next USB session pairs again.

The client stores a `PairedHost` (replacing one with the same id, keeping its `lastAddress`). `storePairing` refuses one that names an already paired host id with a different certificate or token (ids are public, and a real Mac creates all three together), and drops loopback, zero, multicast and broadcast addresses from the list. Identity and pairings live in `SharedPreferences` (`wifi_*` keys), not in `flutter_secure_storage`.

**Nothing that arrives on the link can pair.** The pairing used to travel as a `0xF6` control packet on USB sessions, which trusted the socket in both directions, and neither end knows who is on it. The tablet's "USB session" is whatever answered on its own `127.0.0.1:7001`: adb while a Mac has its tunnel up, any app on the tablet the rest of the time (the client redials every 5 s). The host's USB peer is whatever on the tablet dialled the tunnel first, and it would have been sent the token. So the host never puts a pairing on the socket, `ClientConnectionManager.onRolePacket` ignores `0xF6` on every link (don't reuse the byte), and `storePairing` must never be called with bytes that came from a packet. The session itself no longer rests on the socket either (next but one paragraph). Host and client are separately installed builds, and an old one on either side simply never pairs (the new host's broadcast finds no receiver; the new client ignores the old host's `0xF6`); pairings stored by earlier builds stay valid.

**Unpairing.** On the tablet, each paired Mac has its own row in Home's `_WifiClientCard` with a Forget button: after `showConfirmDialog` (`lib/shared/widgets/confirm_dialog.dart`) it calls `HomeController.onForgetHost` → `WifiPairingService.forget(id)`, then restarts a pending Wi-Fi dial (`_redialClient`, which leaves a stopped tablet stopped). On the Mac, Settings → Wi-Fi → Reset Wi-Fi pairing (host only, also confirmed) calls `BaseConnectionManager.resetWifiIdentity()`, a no-op on the client. The hub's override runs `WifiPairingService.resetIdentity()`, which removes the four identity preferences and the memoised identity (a reset waits for a creation still in flight, and `_loadOrCreateIdentity` waits for a reset in flight, so neither can bring the old identity back), then each session's `identityWasReset()`. There, if a Wi-Fi attempt or session is up, the session does `disconnect()` and an unawaited `connect()` of its own, because the TLS server still presents the old certificate and a connected tablet got in with the old token; a live USB session carries on and is handed the new identity at once (`_usbSessionSeq`). It does not go through `SettingsController`'s debounced `reconnect()`. There is one token for all tablets, so the Mac cannot revoke a single one, and a tablet keeps its entry for the old identity until it is forgotten there (after pairing again it lists the Mac twice).

**A Wi-Fi session authenticates in both directions.** The client dials with no trusted roots, so every certificate goes to `onBadCertificate`, which accepts only one equal to a paired host's DER (`WifiPairingService.hostForCert`), and it checks the peer certificate again after connecting. Its first packet is `0xF5` with that host's token. Anything on the network can complete the TLS handshake with the host, so the host treats a client as a stranger until that token passes `WifiIdentity.tokenMatches` (constant time), and the trust belongs to the connection, not to the session: `SocketService.connectionId` changes whenever a socket is installed, the host stores the id that authenticated in `_authedConnection`, and its `peerTrusted` is `_authedConnection == socket.connectionId`, on both links (a USB client earns it differently, see below). The server accepts whoever dials next the moment a client drops, before teardown has run, so a flag would let that newcomer inherit the previous client's standing. Both directions go through it:

- **Inbound:** `BaseConnectionManager._handlePacket` calls `admitPacket()` before anything else, heartbeats included. The host's override admits nothing from an untrusted peer and only looks at the one packet that can earn trust (`0xF5` over Wi-Fi, `0xF4` over USB), once per connection: no HELLO, no input, no pong. Until `SocketService.trustPeer()` the client may not even announce a payload over 1024 bytes (`_dropPeer`).
- **Outbound:** every packet the host sends goes through `_sendToClient()`, and `_forwardFrame` returns unless `peerTrusted`. Never call `socket.send` from the host directly: a capture can still be running, or just starting, when the socket already belongs to someone else.

`connect()` waits 3 s for the token and otherwise throws `LinkError('error_wifi_unpaired_client')`, which goes through `handleLinkFailure()` like any failed attempt (re-listening after 1 s). A TLS handshake that fails on the server is only logged; it must not reach `packetStream` as an error, or a port scan would tear down a live session. What a machine on the LAN can still do is get in the way: hold the single client slot for those 3 s, answer discovery with garbage, or keep idle connections open (`SecureServerSocket` has no handshake timeout). On the tablet, a TLS dial that times out (`SocketService(tlsDialTimeout:)`, 8 s) cannot be closed, because dart:io offers no way to abort a handshake: it stays open until the peer closes, so a peer that accepts and stays mute costs one socket per retry.

**A USB session authenticates in both directions too** (`UsbSessionService`). A port says nothing about who is on it. The host's USB peer is whatever dialled its session's loopback server: any app on the tablet, through the tunnel, or any process on the Mac, directly (the port being that session's own says which tablet the tunnel came from, not who dialled it) (which used to get the screen and injected input without either macOS permission). The tablet's peer is whatever answered on its own `127.0.0.1:7001`: adb while a Mac has its tunnel up, any app the rest of the time. So every USB attempt has a key, and it travels through adb, like a pairing:

- **Made and delivered by the host.** In the session's `connect()`, once its server is bound (on a port of its own) and `adb reverse` has pointed the tablet's 7001 at it, the host makes 32 random bytes (`_usbKey`) and gives them to `AdbService.deliverUsbSessionKey`: the pairing's broadcast with the action `com.example.extendedscreen.USB_SESSION` and the payload version byte + key. The call is not awaited, because the app can dial before adb has reported. On the tablet `WifiPairingReceiver` → `WifiPairingChannel` (`usbSession`) → `UsbSessionService.accept`, which keeps the key in memory only and fires `arrivals`. The key itself is never put on the socket.
- **Proved, not sent.** The client's first packet is `0xF4`: a fresh 16-byte nonce and HMAC-SHA256(key, client label + nonce) (`package:crypto`). On a hello that verifies, the host's `admitPacket` clears `_usbKey` (one session per key, so a recorded hello opens nothing), records the connection in `_authedConnection` and answers `0xF3`: HMAC-SHA256(key, host label + nonce). It answers only then, through `_sendToClient`, so the host still sends nothing at all to a peer that has not proved itself. The client's `admitPacket` admits nothing until that answer verifies for this connection (`_trustedConnection`), gives the peer one try, and `connect()` waits 2 s for it (`_answerTimeout`, deliberately shorter than the 3 s after which a host build from before the handshake would give up on HELLO and start a capture), otherwise `LinkError('error_usb_unverified_host')`. Only after it does the client send HELLO.
- **Trust is `peerTrusted`, on both roles.** `BaseConnectionManager.peerTrusted` defaults to false; the host overrides it as above, the client with `_trustedConnection == socket.connectionId` (set after the certificate check over Wi-Fi, after the answer over USB). The base uses it for `admitPacket`'s default, for `packetStream` (so `DisplayController` is never fed a frame from an unproven peer), for the input and IDR send helpers and for the heartbeat ping; the client's reverse-capture frames check it too, since that capture can outlive its session. An unproven peer may not announce a payload over 1024 bytes on either side (`startServer(untrustedPayloadLimit:)`, `SocketService.distrustPeer()`), until `trustPeer()`.
- **A key is only for connections dialled after it arrived.** The client reads `UsbSessionService.key` before `socket.connect` and judges that connection by that key alone. A key that arrives later (`_onSessionKey`) makes it drop what it has and dial again at once (`BaseConnectionManager.restartLink()`: a link loss whose retry is immediate, so the keep-alive service is left alone), unless the user had stopped it (`disconnected`) or the dial in flight, or the live session, was made with that very key. Without this rule an app could sit in the middle: it holds port 7001 before any tunnel exists, takes the tablet's dial, closes its listener but keeps the connection, and once the Mac's tunnel is up passes everything on in both directions. With it, a key is used only on a dial that reaches adb, because the host makes the key after its own `adb reverse` and an app cannot bind the port while adb holds it. For the same reason the host must never run `adb reverse` a second time inside one attempt.
- **A hello without the right key does not fail the attempt.** From this app it means the key has not arrived: the app was opened after the host started waiting (its delivery reached nobody, result 0), or a dial and a delivery crossed. The host's `connect()` loops: `SocketService.dropClient()` (closes the client without reporting a lost link; the server keeps listening), delivers the same key again unless the app confirmed taking it within the last second, and waits for the next client, back in `handshaking`. If that delivery is not `stored` it throws `LinkError('error_usb_key_not_delivered')`. Three seconds with no hello at all (a tablet build from before the handshake opens with HELLO), or more than 8 keyless hellos in one attempt, throw `LinkError('error_usb_unverified_client')`. Both go through `handleLinkFailure()`, and the retry makes a new key.

Nothing falls back to trusting the socket. A new host with an old tablet build: the key reaches nobody, the old client's HELLO is not admitted, and every 5 s redial ends in `error_usb_unverified_client` on the Mac while the tablet's display opens and closes. An old host with a new tablet build: no key ever arrives, the old host ignores the keyless hello, the client hangs up after 2 s with `error_usb_unverified_host` and tries again every 5 s; the old host re-listens each time and never starts a capture. What is left: whatever can run adb on the Mac is inside the boundary (it can deliver a key of its own, re-point the tunnel, or read `am`'s arguments in the tablet's shell, where the key is visible to the shell user and to no app); another app on the tablet can still get in the way (dial the tunnel first and hold the single client slot for up to 3 s per attempt); and after the handshake the link is as before, plain TCP that only adb and loopback protect.

**Finding the Mac** (`ClientConnectionManager._findWifiHost`): one `WifiDiscoveryService.probe()` sends `EXTD?` on UDP 7001 to 255.255.255.255, to each interface's /24 broadcast, and directly (`directTargets`) to every address a paired Mac might have: the one typed on Home (`SettingsService.wifiHostAddress`), each `PairedHost.lastAddress`, and each `PairedHost.addresses` entry from pairing. The Mac replies unicast with id, name and TCP port, and the first reply from a paired host id is dialled. The direct targets are what reach a Mac on another subnet (a tablet behind a mesh router doing NAT, as on the development network), and probing them all is why a stale typed address does not hide a Mac that answers elsewhere. With no reply a known address is dialled anyway (UDP can be filtered where TCP is not), a different one on each attempt, starting with the typed one; with no address either it throws `LinkError('error_wifi_host_not_found')`, and with no pairing at all `LinkError('error_wifi_not_paired')` without probing. The typed address is stored through `SettingsService.normalizeHostAddress` (trimmed, a copied `:port` removed, anything that is not an IPv4 address or host name stored as empty). Discovery replies are not trusted: they only say where to dial. `WifiDiscoveryService(udpPort:, broadcast:)` lets tests run it on a free loopback port without broadcasting. Two dart:io behaviours shape `WifiDiscoveryService`, and both have bitten:

- A datagram that can't be sent does not throw: it is reported as an error on the socket's stream, and the socket is closed. So `probe()` gives each target a socket of its own (one unreachable target must not cost the replies to the others), and the host's responder binds itself again 1 s after an error.
- A read handler is called again, from a microtask, for as long as a datagram waits on an open socket. A handler that returns without `receive()`-ing it spins for ever and freezes the whole app, because microtasks run before the event loop gets the turn that would close the socket. On an ordinary network the Mac answers the broadcast, the subnet broadcast and its own address at once, so several of the probe's sockets hold a reply at the moment the first one decides it. `probe()` therefore binds all its sockets before sending, and `finish()` closes every one of them synchronously the instant the probe is decided (first paired reply, or 64 datagrams read); never `await` between deciding and closing. The responder, which must keep reading, handles 32 datagrams and then switches `readEventsEnabled` off until a `Timer.run`, sends at most 20 replies a second, and is stopped as soon as a client authenticates (the next listen starts it again).

**Pacing.** The two TLS entry points put `SocketService` in paced mode: every write goes through a queue and one `flush()` at a time (an `IOSink` rejects `add()` while a flush is pending, so nothing may write to a paced socket directly, and `disconnect()` uses `destroy()` because `close()` throws then). `isCongested` is true when data queued more than 120 ms ago has not been flushed; `sendFrame()` then returns false. `HostSession._forwardFrame` drops frames from that point until the link has drained and `isKeyframeAccessUnit` (`lib/shared/protocol/annexb.dart`, the Dart twin of the Kotlin function) sees a keyframe, asking the encoder for an IDR at most every 500 ms. `_startCapture()` also caps `SO_SNDBUF` (`limitSendBuffer`, macOS only) at 400 ms of the bitrate, re-applied whenever the adapted bitrate changes: room for a keyframe (a smaller buffer, 100 ms as it once was, kept every keyframe on a link near the rate waiting past the congestion limit, so frames were refused), and no more, since the kernel's own buffer would otherwise hide a slow link for seconds and is latency the adapter can no longer cut at its floor. Over USB none of this runs: `sendFrame()` is `send()`.

**Bitrate adaptation (Wi-Fi only).** Dropping frames is the last resort; before that the encoder is fitted to the link. `_startCapture()` ends with `_startBitrateAdaptation()`: a 50 ms timer feeds `BitrateAdapter` (`lib/shared/connection/bitrate_adapter.dart`, pure arithmetic; its class comment is the reference) with the link's queue, `SocketService.unackedBytes` (bytes queued in Dart plus, on macOS, the kernel's `SO_NWRITE`: TCP data the tablet has not acknowledged; `_pump` flushes one packet at a time so a flush under way is not counted twice), taken at its low point (`_queueTrough`, read before each frame write, since a 50 ms timer sits on one phase of a 60 fps frame cycle), less one round trip of stream (`inFlight`: the heartbeat's lowest round trip of the last 30 s, 10 ms until measured, capped at 40 ms; `beginConnect()` resets `latencyMs` so a USB session's round trip is not taken for the Wi-Fi one's). It judges the smallest queue over 400 ms, so keyframe bursts don't count: a standing queue over 30 ms cuts towards 85% of what the link delivered (at most halving per step, one step per 800 ms); a refused frame cuts at once (60%, or towards the delivered rate if the window measured the link); a window in which the link carried next to nothing for 200 ms (a stall, a roam) is not judged at all. It climbs only while the stream used at least 60% of its budget over the last 1.2 s, longer than the 1 s keyframe interval (an idle screen sends little more than a keyframe a second, which fills most of a 400 ms window by itself and proves nothing about headroom), 2 s after a cut, 15% a second up to just below where the link gave out (what it delivered, remembered for 30 s and forgotten once a 5%-per-2 s probe passes it by 15%); never above the preset's bitrate, never below max(2 Mbps, preset ÷ 8). After a refusal `_forwardFrame` resumes only once `unackedBytes` is under `_resumeBelow` (~30 ms of stream): resuming with the kernel buffer still full got the resuming keyframe refused in turn. A change goes to `ScreenCaptureChannel.setBitrate` → `ScreenCapturePlugin.swift`, which leaves it in `requestedBitrate` for the timer thread to apply (`kVTCompressionPropertyKey_AverageBitRate`) before its next encode: no new session, no keyframe. The host's Home chip shows the current rate (`BaseConnectionManager.streamBitrate`, null on the client and over USB). `_stopBitrateAdaptation()` is synchronous and runs before the first await of `onTeardown()`, again inside its `_exclusive` block, and in a rebuild's `stopPipelineOp()` (the rebuilt encoder starts at the preset again); `adaptingBitrate` is the test hook. `test/bitrate_adapter_test.dart` drives the adapter, partly through a fluid model of a link with the host's send buffer, refusal and resync and an encoder with quarter-second keyframes, busy or idle (`simulate`); `wifi_link_test.dart` runs host and tablet through `_SlowLink`, a clock-paced leaky bucket on a `RawSocket` (a tick the isolate runs late must not slow the link), with `_Encoder` keeping its average around 250 ms keyframes and starting its GOP again on a forced keyframe. On a link near capacity the rate does not sit still: it moves in a band mostly below the link, because a keyframe's backlog drains only at what the link has to spare, with now and then a probe a step above. The tablet, for its part, holds a low-latency Wi-Fi lock while a Wi-Fi session streams (`KeepAliveChannel.setLowLatencyWifi`, `WifiLatencyLock` in `ClientKeepAlivePlugin.kt`), so its radio doesn't doze between frames.

Home (`home_view.dart`) is two bodies: `_ClientBody`, the tablet's, and `_HostBody`, which takes the manager as the hub (`HostConnectionManager`; there is no host layout over a plain manager). The host body is one `Obx` that reads every session's phase and grant (the facade follows only the focused one): the permission banner first, then by link. Over Wi-Fi it is the one session through the facade, laid out as before several tablets existed: `ConnectionCard` (Connect while `disconnected` starts listening; its stop is `onConnectTap`, which pauses the auto-connect), the selectors, a card with the Mac's addresses, which stays up while the host listens (that is when the address is needed) and goes once a session is live, then `DeviceInfoCard`, the open-remote button and `LatencyChip` while live and the error banner in `error`; `_maybeAutoConnect()` starts listening by itself under its usual conditions. Over USB it shows one `SessionCard` (`lib/shared/widgets/session_card.dart`) per session, sorted by key, or with none the facade's `ConnectionCard` and error banner (looking for a device, "No ADB device detected"); then the selectors; then the add panel, always on screen: `DevicePickerCard` titled `home_add_tablet`, its header `home_tablets_count` (USB sessions of `cap`, whatever their phase, so it says slots in use, not tablets connected) plus `home_encoder_load` (`budget.load`, codec) while any session has a `granted` capture, listing `hub.freeDevices` (empty: `home_all_attached_connected` once sessions exist). A tile is disabled (dimmed, no tap, the reason under its serial) unless a pick could go ahead (`canAdd`, or with `cap` 1 the replace of a lone session that is neither connecting nor live, as before) and `budget.wouldFit` the config the next connect would ask for (`captureConfigFor(clientPanelFor(serial) ?? lastClientPanel, SessionSpec.of(settings, usb))`); the reason is `home_disconnecting` while a hub `disconnect()` ends every session (`hub.endingAll`, an observable twin of `_endingAll`, which `canAdd` reads too; the sessions leave `sessions` at once while the facade keeps the last phase it mirrored, so the facade card is drawn `disconnected` meanwhile, with no Disconnect for a session that has gone), `home_remote_single` in remote control with a session, else `home_at_limit`. The mode, direction and link selectors show only while neither the facade nor any session is connecting or live and there is at most one session. The app bar shows the session mode with at most one session, else the app's name and `home_appbar_tablets`. A `SessionCard` is an `InkWell` whose tap focuses its session (`HomeController.onFocus` → `hub.focus`; with several sessions the focused one, `hub.focusedKey`, has an accent border), with its own `Obx` over that session alone: the model (else the serial), link and mode chips, a `ConnectionCard` with its one action, `ConnectionSteps` while connecting, `LatencyChip` (with the Wi-Fi bitrate) and the announced fps while live, `session_granted`/`session_granted_shared` from `granted`, an error line (`session_unplugged` for `error_device_gone`, else the `errorKey` translated at build, else `errorMessage`, else the `notice`; computed in build so a language switch reaches it), and the open-remote button in a live reverse-remote session. Its actions: Disconnect while live and Cancel while connecting or with `retryPending` both go to `onSessionStop(key)` → `disconnectSession(key, userStopped: true)`, which stops that tablet alone and does not pause the auto-connect; Retry (`common_retry`, `ConnectionCard.onRetry`) in `error`, whether no retry is armed (the encoder refused it) or one waits out its backoff (up to 10 s ±20% over USB; Retry runs it now), goes to `onSessionRetry(key)`, the same permission-gated `_connect(serial: key)` as a pick, which the hub turns into that session's `connect()`, and Cancel beside it to `onSessionStop(key)`, so a refused tablet's card, and its place under `cap`, can always be let go. On the client the selector shows whenever no session is live, and choosing a link or submitting an address restarts the pending dial (`HomeController._redialClient`) unless the user had stopped it. Two rules keep one touch from meaning two things, since `onConnectTap` decides Connect or Cancel from the phase when the finger comes up: nothing may change the phase on pointer-down (the address field's `onTapOutside` only saves), and `ConnectionCard`'s buttons are keyed by their labels (`'<key>/<label>'` on a session card, `actionKeyPrefix`, so cards never share a key), so when the phase changes under a finger anyway (an auto-connect on app focus, a link that fails) the button is replaced and the touch does nothing. The add panel's tiles are keyed by serial (`device/<serial>`) for the same reason: its list changes under a finger when a tablet is plugged in or connects by itself, and an unkeyed tile kept the press while taking the next device's tap. The Loopback preview's Start/Stop is keyed by serial and meaning.

### Hub and sessions (host)

The host holds several tablets over USB in Extended screen, up to `cap`, and one otherwise. `HostConnectionManager` is the hub, registered as before (`Get.put<BaseConnectionManager>(HostConnectionManager(), permanent: true)`, so every `Get.find` and `RemoteHostController`'s cast still work). It runs no link of its own (no packet loop, heartbeat or retry). Each tablet's link is a `HostSession` (`host_session.dart`): what used to be the whole host manager, with its own copy of the base state machine (phase, attempt counters, `_recovering`, retry, heartbeat), so cancelling or failing one session never touches another.

- **The hub owns** `sessions` (an `RxMap` by key: the adb serial over USB, `wifi` for the one Wi-Fi session), the focused session, the device list, the app-lifecycle observer (the only one: `detached` ends every session and the device poll, other states go to each session, which applies the base rule with its own `_recovering`, and a resume also runs the auto-connect policy), the one `PipelineQueue`, the one `EncodeBudget` (`budget`, see *Encode budget* below), and the native plugins' single-slot callbacks. It routes those: `AdbService.onTabletScreenRestored` by serial; `ScreenCaptureChannel.onCaptureRestartNeeded` to the session with that native id, or for a wake (null) to every session, or with two or more sessions able to rebuild (`canRebuild`) to its own one-operation rebuild of them all (see *Display modes*); `onDisplayBoundsChanged` to every session; `onFrameRateChanged`, `onCaptureMismatch`, `onCaptureMatched` and `RemoteVideoChannel.onRequestIdr` by native id (a decoder with a listener of its own, `RemoteVideoChannel.listenIdr(id, f)`, the Loopback preview's, never reaches that slot). A session never assigns them, and accepts them only from the start of its capture or decoder until its teardown (`_captureWired` / `_remoteWired`, set and cleared where the callbacks used to be assigned and nulled).
- **The facade.** The hub's `phase`, `errorMessage`, `errorKey`, `activeDevice`, `latencyMs`, `refreshRateHz`, `streamBitrate`, `remoteTextureId`, `tabletStreaming`, `tabletScreenOff` and `changingTabletScreen` follow the focused session through `ever` workers (`_focus`). Each is the hub's own Rx for its whole life, because Home's workers and the remote view hold on to them. GetX notifies synchronously, so after `await hub.connect()` the hub already shows `streaming`. The session a pick connects is focused (`hub.connect` starts its `connect()` first and focuses it in the same synchronous step, so the hub's phase goes straight to the session's connecting one, never through a new session's `disconnected`); `focus(key)` focuses another, and `focusedKey` (an `RxnString`, set in `_focus` and cleared in `_unfocus`) is the focused key for the UI. When the focused session ends, the hub refocuses at once, before anything is awaited: the most recently focused session left (`_recent`), or with none, `disconnected` and no error (`_refocus`), except during a hub `disconnect()`, where it keeps the last values it mirrored until the base sets `disconnected` at the end, as before. `availableDevices` is not mirrored: only the hub's own listings set it (see *Who initiates*), and a session's listing while it connects is its own.
- **The cap.** `hub.cap` is `min(settings.maxTablets, budget.estimate.tabletCap ?? 8)` over USB in Extended screen, else 1: Wi-Fi has one listener, and in remote control `setTabletScreenOff`, `sendRemoteTap/Swipe`, `remoteTextureId` and Home's `/remote-host` worker all go to the focused session. Each session gets it as its budget-admission `cap` callback. `usbSessionCount` counts every USB session whatever its phase (a refused one too); `canAdd` says a pick of a tablet with no session would add one (USB, under the cap, no hub `disconnect()` running).
- **Choosing** (`hub.connect({serial})`). Nothing while a hub `disconnect()` ends sessions (`_endingAll`) or a link change ends them (`_linkChange` in `_choosing`). With `cap` 1 and at most one session it is the old single manager's rule: only while the hub's phase is neither connecting nor live, and one pick at a time (any key in `_choosing`). Otherwise per key: `_choosing` is a set of the keys being picked, from the call until that key's session has started connecting (`_anyDevice` while a pick without a serial looks for a device, then the device it settles on too); a key already being picked, or whose session is connecting or live, is refused, while one in `error` is its retry run early (the user's Retry for a refused one), on the same session and native id. A key still ending (`_endingKeys`) is waited for, then connected anew; `TabletTunnels` orders the two sessions' adb calls. A new key is refused once `usbSessionCount >= cap`, counted after every await, so lowering Maximum tablets under the live count stops nothing and only refuses new ones; the replace path never runs while more than one session exists. Over Wi-Fi the hub uses the `wifi` session. Over USB it takes, in order: `serial`; the focused session's own device (with cap 1 always; otherwise only when it waits in `error`), so a retry run early keeps the session and its native id; the last-used device if attached; the first attached (otherwise only devices with no session, mDNS duplicates dropped). With nothing attached and no session it makes none (one would be fixed to a device that may never come): it shows `error` with "No ADB device detected" and looks again every second (`_lookAgain`), taking whichever tablet appears; with sessions, it just adds nothing. With cap 1, picking another device ends the focused session first, showing a connecting phase throughout (`_endSession(showing:)`), as the old single manager did. An injected test socket goes to one session at a time (`_injectedHolder`, until that session has ended); the others get their own.
- **Ending a session** (`_endSession`) takes it out of reach before anything is awaited: out of `sessions`, unfocused and refocused (the hub resets the mirrored device and reverse-remote values itself), in `_endingKeys` until it has ended, and `retire()`d, so its `connect()` refuses from then on, whoever calls it. Only then come its `disconnect()`, `dispose()` and `ScreenCaptureChannel.disposeSession` in the queue. Without this, a second pick or a pick right after Cancel could take the ending session or make a second one, and the stray session kept capturing after Disconnect. The synchronous refocus is load-bearing for the cap-1 replace: the pick's connecting phase is set there, so the hub never reads idle mid-pick. `disconnectSession(key, {userStopped})` ends one session this way and nothing else: it does not bump the hub's attempt, so another tablet's pick in flight carries on; with `userStopped` the key joins `stoppedDevices`.
- **Each tablet's adb rule** (`TabletTunnels`, in `host_session.dart`): the hub `claim`s a tablet for each new session, a session's `adb reverse` and `--remove` for that tablet run one at a time in order, and only the newest session for a tablet may remove its rule or release its screen hold. A session's counters are its own, so `_abandon`'s `isLatestConnect` cannot see a newer session for the same tablet; without this an ended session whose adb call returned late removed the new session's rule.
- **The other hub calls.** `disconnect()` ends every session (the base `disconnect()` runs the hub's `onTeardown`). `setTabletScreenOff`, `sendRemoteTap/Swipe` and `adaptingBitrate` go to the focused session (`adopt(session)` focuses one without connecting it, for tests). `reconnect()` (a settings change, the remote view's Reconnect) runs the base `reconnect()` of every session that is connecting, live or in `error` and not `refused`, in parallel: each the same object, so the same native id, and one waiting out its backoff restarts at once (its `activeDevice` survives the lost link). `retryNow(key)` runs a session's pending retry now, only in `error` and not `refused`. `sendUiFlags()` goes to every session. A link-type change does nothing while any session is connecting or live (or a pick or `disconnect()` is under way); otherwise it ends the sessions on the other link and connects on the new one only if one of them had `retryPending` (never for a refused one, which has none). `connectIfUnambiguous` is overridden by the auto-connect policy (see *Who initiates*). `stoppedDevices` is an in-memory `RxSet`; `allowDevice([key])` takes the key out of it (no key: the `wifi` session over Wi-Fi) and ends the pause that `pauseAutoConnect()` sets (`autoConnectPaused`); `freeDevices` is the device list without mDNS duplicates and devices that have a session; `anyActive` and `anyConnecting` look at every session. The base class has no-op `disconnectSession`, `retryNow`, `pauseAutoConnect` and `allowDevice`, so shared UI can call them on the client.
- **A session is fixed for its life.** It keeps the same `key`, `link`, USB `serial`, `nativeId`, `vdSerial` and `vdName` through its retries and reconnects. The last two are its virtual display's serial number and name, which the hub gives it when it makes it: over USB `SettingsService.vdSerialFor(key, taken:` the live USB sessions' serials`)` and `vdNameFor(key, model:` the device list's model`)`, so the migrated tablet keeps serial 1 and `Extended Screen` and a new one gets an FNV serial and `Extended Screen – <model>`; over Wi-Fi 1 and `Extended Screen`, as every display had before. Once the session is live over USB it calls `settings.rememberDevice(serial, model:, vdSerial:)` (which also writes `last_device`/`last_device_name`), so a new tablet's serial is saved only then. Its retries look for its own device and no other; while it is not listed they fail with `LinkError('error_device_gone')`, also when nothing at all is listed (it was the only tablet), so the device poll retries it at once when it comes back; only a listing adb could not make at all fails with "No ADB device detected". It reads `spec` (a `SessionSpec`: mode, effective direction and display mode, taken at the start of each connect attempt; before its first, the live settings) instead of the settings' mode getters. It reads `panel` (a `ClientPanel`: this attempt's HELLO, else `SettingsService.clientPanelFor(key)`, else `lastClientPanel`) for the capture config (`SettingsService.captureConfigFor(panel, spec)`), the reverse-remote rate and bitrate (`refreshRateFor(panel)`, `captureBitrateFor(panel)`), the remote texture and remote taps. It is never `Get.put`, so it adds no lifecycle observer and its `onInit` never runs. When the hub ends it, the hub calls `dispose()`, which drops its phase worker, any share of the encode budget and its budget listener.
- **Encode budget.** Every session's capture shares the Mac's encoder through the hub's `EncodeBudget` (`lib/shared/connection/encode_budget.dart`, pure; its class comment is the reference), made with `EncoderEstimate.conservative` and re-estimated from the chip once `hostInfoReady` (`ScreenCaptureChannel.getHostInfo`, at once without the plugin) has it; a new estimate never ends anyone. The hub keeps the `HostInfo` it estimated from in `hostInfo` (an `Rxn`, set after the estimate, so it is the one thing to watch), which Settings' Encoder line shows (`SettingsController.encoderSummary`: the chip if known, the codec, and `budget.capacity(codec)` in Mpx/s, all engines, marked `settings_encoder_measured` once a learned value is above the estimate (`isLearned`), else `settings_encoder_estimated`; a dash without a hub). **Learned capacity.** The estimate was low on the measuring M3 Pro itself (one Tab S10 Ultra ran 2960×1848 at 120 fps with H.265, 656 Mpx/s, with no overload, so Home said `encoder 119%` and a second tablet pushed it to 45 fps), so `budget.capacity(codec)` is max(estimate, `learned(codec)`), and the hub moves `learned` from two signals. Raise: while every admitted session whose encoder adapts (Max, `adaptiveFps`, the only one that reports overload) runs at its ceiling (`granted.fps`, once `captured` is set) for an unbroken `capacityWindow` (10 s; a constructor argument for tests), what they encode is a proven lower bound (`EncodeBudget.provenLoad`; fixed-rate sessions count for nothing, mixed codecs prove nothing), and `raiseCapacity` lifts the codec's capacity just enough that it fits the budget's own rule (total ≤ 85%, the largest session ≤ one engine's share); a proven load never lowers it. A rate granted is not a rate encoded, so the window also needs evidence (`_encodedThrough`): each adapting session's encoder reports once a diag second (`onEncoderStats {session, encoded, captured}`: frames VideoToolbox handed back without error, and SCK frames, both per second), and the window passes only if every adapting session reported, averaged at least 95% of its granted rate encoded, and had SCK frames in at least half of its seconds. Without it a sleep-invalidated encoder (it refuses every frame, so ticks stay on target and nothing is pending: Swift looks healthy) or an idle desktop (the timer re-encodes one frame, the cheapest work there is) taught a lone tablet's 120 fps load for good; a window without the evidence just starts again. The window is a `Timer` restarted by every budget notification and every change of a session's `granted` or `captured` (an `everAll` worker per session, made in the hub's session creation and disposed in `_endSession`), and checked again when it fires; `measuringCapacity` is the test hook, and `encoderStats` feeds the evidence in tests with no capture channel. **Probes.** With two or more adapting sessions every ceiling the rule sets already fits the capacity, so a proven load never passes it and nothing would ever be learned (on the device: AVD first, then the Tab, which stayed at 45 fps for the whole run). So a window that proves a load and teaches nothing starts a probe (`_startProbe` → `EncodeBudget.startProbe`): of the adapting sessions (one codec, two or more), the one below its wanted rate whose next rung up adds the least load and no longer fits the capacity (a rung up that still fits, which stepping the largest demand down can leave, would teach nothing and hold the probe for good) gets that rung as its ceiling, pushed live. Swift's Max encoder climbs to a raised ceiling only after `stepUpDelay` healthy seconds (10 s, doubling to 5 min after a failed step-up), with no `onFrameRateChanged` before that, so the probed session's `granted` stays put meanwhile and no window runs; once it climbs, the next window with evidence proves the higher load and `raiseCapacity` learns it (and ends the probe: anything that works the ceilings out again does). An overload step-down while a probe runs fails it (`_probeFailed`: the ceilings go back, `endProbe`), and so does an encoder that has not climbed by `probeTimeout` (60 s; a constructor argument for tests); the least load a probe failed at is remembered per codec for the run (`_probeFailedAt`), and no probe reaches it again. `probe` is the test hook. Lower: an overload step-down (Swift's `onFrameRateChanged` then carries `achieved`, the ticks/s the encoder managed, which `ScreenCaptureChannel` hands to `onEncoderOverload` just before `onFrameRateChanged`) while two or more sessions are admitted with one codec gives `achievedLoad` (that session at `achieved`, the others at their reported rate, else their ceiling), and `lowerCapacity` brings `learned` down to it, never below the estimate (at or under it, nothing is learned any more); one session alone lowers nothing, since its own ladder looks after it. Either change works the ceilings out again and the hub pushes the changed ones live (`setFrameRateCeiling`, no restart; Max climbs to a raised one as its health allows), saves the value for this chip and codec (`SettingsService.setEncoderCapacityFor`, key `encoder_capacity.<chip slug>.<codec>`, e.g. `encoder_capacity.apple-m3-pro.h265`; nothing for an unknown chip) and bumps `capacityChanges`, which Home's load line and the Encoder line read. Nothing is learned (or probed) while any admitted session is synthetic, or is not one of `sessions` (one being ended). `_loadHostInfo` sets the estimate, then takes each saved value that is above what this run has learned already (`encoderCapacityFor`, which ignores values that can't be a capacity), and pushes every ceiling that changed (the estimate's own changes too, which used to be left unpushed). A learned value can be too high if the window ran on content cheaper to encode than usual; the overload signal is what corrects it. Each session gets it (`budget`, null in tests that build one alone: today's path, no admission) and a `cap` callback (the hub's `cap`; the default, for a session built alone, is 1). `_startCapture()` admits right after the `stale()` check that follows the permission requests, with no await in between: a teardown that has begun bumped the attempt first, and one that begins later gives the share up before its first await (in `onTeardown()`, next to `_stopBitrateAdaptation`), so a share is never left behind. Giving it up comes in two kinds. `_reserveBudget()` (`EncodeBudget.reserve`): the capture stopped but the session goes on (a teardown for a lost link, a retry, a settings `reconnect()` or `restartLink()`; a capture start that threw): the others' ceilings rise at once and `granted`/`captured` clear, but the session keeps its place, so its next admission is a return: never refused by the cap (a lowered Maximum tablets stops nobody, at their next reconnect or retry either), keeping its admission order, and every other admission meanwhile is planned with the reserved places counted at their floors, so tablets that restart together (a settings reconnect re-admits them in whatever order their handshakes finish) come back as they were and a newcomer cannot take a returning tablet's room. A reservation whose tablet is unplugged holds no room, though: a session whose attempt finds its tablet unlisted (`error_device_gone`) calls `EncodeBudget.suspend` before throwing, and `resume` once an attempt lists it again. A suspended place still counts under the cap but no admission is planned around it, so a running tablet's return (a settings reconnect while the other tablet is unplugged) never comes back at a lower resolution for a tablet that is not there, and the unplugged one, once back, is a return planned beside whatever runs then (past the cap still, possibly at a lower resolution). `wouldFit` counts reservations (a suspended one only towards the cap); `load` and `count` do not. `_releaseBudget()` (`EncodeBudget.release`): the place goes for good, when the hub ends the session (`retire()`, before its teardown, so a pick made while it ends is not planned around it; `onTeardown()` of a retired session; `dispose()`) and when the encoder refuses it (`CaptureLimit` in `connect()`: the user's Retry is a new tablet's admission). It pushes the running sessions' lowered ceilings to their encoders (`_pushCeilings` → `ScreenCaptureChannel.setFrameRateCeiling`, plain unawaited calls, never `pipeline.run`; each encoder answers with `onFrameRateChanged`, so its tablet hears a new `0xFB`), starts with the granted config (the ceiling travels as `fpsCeiling`, never in `refreshRate`, so a raised ceiling can climb back), and announces `0xFB` at min(rate, ceiling). The ceiling it starts with is read from the budget again right before `startCapture` (after the virtual display, with no await in between): another session leaving while the display was made raised it, and Swift's `startCapture` takes its `fpsCeiling` over any `setFrameRateCeiling` that came before it. A rate the encoder reports through `frameRateChanged` once the start is sent (`_reportedFps`, a ceiling raised during the start) is what that `0xFB` says instead. Everything after the admission runs inside a try (`_startAdmitted`): any start that throws reserves (above), so a failed start holds nobody down, its card shows no grant, and the next start, a wake's rebuild included (a stream-stop rebuild that fails has nothing else coming), is a return; an `ENCODER_BUSY` or `NO_ENCODER` becomes `CaptureLimit` only when another session held part of the budget at admission, and a lone tablet's stays the non-fatal failure it always was. `CaptureLimit` (from that or from `admit` itself) is the one pipeline error `connect()` lets through: the session sets `errorMessage`/`errorKey` (`error_encode_limit`) and `refused`, and runs `handleLinkFailure(retry: false)`, whose teardown removes its virtual display and tunnel; no retry is armed, and the next `connect()` (the user's) clears `refused` and admits again. A session's observables for its card: `refused`; `granted` (`GrantedCapture`: encoded size, the rate, updated by `frameRateChanged`, and `shared`, kept current by an `EncodeBudget` listener; null with no capture or no budget); `notice`, a translation key cleared by `connect()` and by each capture start: `error_extend_unavailable` when Extend made no display (`displayId` 0) or `startCapture` answered `fellBack`, `error_extend_wrong_display` from `onCaptureMismatch` (`captureMismatch()`) once the hub's display rebuilds have not cured it, or with no other virtual display (see *Display modes*), and `error_encode_limit` when a rebuild (the session's own or the hub's wake, both through `rebuildFailed`) fails with `CaptureLimit` or `ENCODER_BUSY`, which leaves the session up. A rebuild re-admits the same id while it is still admitted (rule 0: same resolution, never refused); one after a failed rebuild returns to its reserved place.
- **Synthetic tablets (debug builds only).** `synthTabletCount` is `int.fromEnvironment('SYNTH_TABLETS')` in a debug build and 0 otherwise, and the app branches only on the const bool `synthTablets` (`synthTabletCount > 0`): a top-level const bool is folded before tree-shaking, while an `if (synthTabletCount > 0)` is a comparison the tree-shaker does not evaluate, and it kept `FakeTablet`'s class in a profile build (the check is under *Commands*). With it, `InitialBinding` puts `SyntheticTablets(N)`: N `FakeTablet`s, `synth-1` on, models `Synthetic_<i>`, panels taking turns over 2560×1600@60, 2800×2000@120 and 2400×1080@60, three shapes further apart than the 2% `checkShowsOwnDisplay` tolerates, so a stream of another tablet's display shows bars and raises `onCaptureMismatch`. Its `SynthAdb.routing` is registered as the `AdbService` (`Get.put`, so its `onInit` still takes the adb channel's handler): a listing is adb's devices then the fakes (a failed `adb devices` reuses the last real listing), and every call on a serial without the `synth-` prefix goes to the real channel. The hub treats a fake like any USB tablet (it dials the session's loopback port with the key handed to it, so the virtual display, ScreenCaptureKit, VideoToolbox and the budget all run for real), except that nothing about it is persisted (see *Key settings*), the auto-connect policy never picks one, and `_offerWifiPairing` skips it. On the host Home's app bar has a grid icon (only under `synthTablets`) to `/loopback-preview` (`LoopbackPreviewView` and `LoopbackPreviewController` in `lib/modules/extended_screen/host/debug/`, a route `AppPages` adds by a const collection-if): a tile per fake with Start (`hub.connect(serial:)`, counted against `cap` like any pick) or Stop (`disconnectSession`), a label (serial, panel, phase, the codec from the fake's `0xFC`, frames received in the last second, the session's `captured` display id and `fellBack`, its `notice`) and the decoded picture in the panel's shape. Each tile feeds what reached its fake's socket (`frameStream`) to a `RemoteVideoPlugin` decoder of its own, id `0x40000000 + i` (`decoderBase`, clear of every `nativeId`), made on the first frame and again when the codec changes (frames are dropped meanwhile, then it asks for a keyframe), whose keyframe requests go through `listenIdr` to `FakeTablet.requestKeyframe`, a `0xFF` over the fake's link to the Mac's encoder; closing the page disposes the decoders. `RemoteVideoPlugin` rebuilds its decompression session on every keyframe's parameter sets, which the preview puts up with. `HostSession.captured` (`Rxn<CaptureStart>`, set after `startCapture`, cleared with `granted` in `_releaseBudget`) is what the label reads.
- **Rule:** inside `HostSession`, never read `settings.isReverseRemote`, `effectiveDisplayMode`, `sessionMode`, `effectiveRemoteDirection`, the global `clientPanel*` or the panel-less `capture*`/`refreshRate` getters. Use `spec` and `panel`. Once there are several tablets, a global read leaks one tablet's state into another. The panel-less getters (`SettingsService`'s and `EncodePresetX`'s `width`/`height`/`bitrate`/`refreshRate`/`resolutionLabel`/`bitrateLabel`) read the last panel a HELLO reported, and nothing in `lib/` calls them any more: Settings labels the presets with `SettingsController.panelForLabels`, the focused session's `panel`, else `lastClientPanel` (read first in any case, so an `Obx` follows every HELLO), through the `…For(panel)` variants; the custom resolutions are derived from it too.

### State management — GetX

`SettingsService` is constructed and `await settings.init()`-ed in `main()` **before** `runApp` so the persisted UI language is available when `GetMaterialApp` reads `locale` at first build; `InitialBinding` only registers it if not already registered. All other services are registered as `GetxService`/permanent singletons in `InitialBinding`, which inspects the platform and registers either `HostConnectionManager` or `ClientConnectionManager` **bound to the `BaseConnectionManager` type** (`Get.put<BaseConnectionManager>(...)`) — so shared UI depends on a single interface. Controllers are scoped to routes via per-feature `*Binding` classes (`HomeBinding`, `DisplayBinding`, etc.). An `Obx` only subscribes to observables read inside its own builder: Home passes `DevicePickerCard` snapshots (`hub.freeDevices.toList()` and the disabled tiles' reasons), because a plain widget that reads an `RxList` in its own `build` registers nothing and goes stale.

Role-specific services are registered only on their platform (`ScreenCaptureChannel`, `InputInjectChannel`, `RemoteVideoChannel`, `AdbService` on macOS, plus `SyntheticTablets` in a debug build with `SYNTH_TABLETS`, whose `SynthAdb.routing` is then the `AdbService`; `VideoDecoderChannel`, `AndroidCaptureChannel`, `BatteryChannel`, `UsbSessionService`, `WifiPairingChannel` on Android). Shared code must `Get.find` them lazily behind an `isHost` check, never as an eager field.

### Localization (`lib/shared/services/app_translations.dart`)

User-facing strings are GetX translation keys resolved with `.tr` (or `.trParams({'name': value})` for `@name` interpolation) against `AppTranslations`, which holds `en` and `th` maps. Existing exceptions: the host's USB connect errors (`HostSession.connect()` stores `e.toString()` in `errorMessage`, so Home's error banner shows raw English such as `Exception: No ADB device detected`; a new failure should throw `LinkError(key)` instead, whose `toString()` is the translation, as the Wi-Fi errors and the USB handshake's `error_usb_*` do; the client uses the key `error_waiting_for_host`, or a `LinkError`'s), the Settings Info values (`USB-C / ADB` or `Wi-Fi / TLS`, `7001`, `1.1.0`, `macOS 13+`; the version is a literal, so keep it in step with `pubspec.yaml`, and `macOS 13+` is one too and does not match the real floor, see *Native macOS plugins*; the Encoder line's chip is the brand string the plugin reads), codec/unit/link labels (`H.264`/`H.265`, `Hz`, `fps`, `ms`, `drop/s`, `Mbps`, `USB-C`, `Wi-Fi`), and the Android foreground-service notification text (English literals in Kotlin). **Never hard-code UI strings** — add a key to both locale maps. This applies to enum label extensions too (`ConnectionPhaseX.label`, `EncodePresetX.label/tagline/description`, `SessionModeX`/`RemoteDirectionX`/`LinkTypeX.label/description`): they are getters, so they resolve the active locale at read time. The Settings permission rows do not: `SettingsController._buildPermissionList()` stores `.tr` results in `PermissionItem.label/description`, so they keep the old language after a locale switch until `refreshPermissions()` runs again — don't copy that pattern. `fallbackLocale` is `en`. The saved language (or device language: Thai if the system is Thai, else English) is resolved in `SettingsService.init()`; `SettingsService.setLocale()` persists the code and calls `Get.updateLocale()`.

### Connection lifecycle (`lib/shared/connection/`)

`BaseConnectionManager` owns the shared phase/latency observables, the packet loop with heartbeat handling, the reconnect timer, and input-send helpers. `connect()` and `autoConnect()` are abstract; `refreshDevices()`, `sendUiFlags()`, `startScreenShare()`, `onRolePacket()`, `onTeardown()` and `onLinkLost()` are overridable no-ops. `ClientConnectionManager` implements the client. On the host every link is a `HostSession` (the hub, `HostConnectionManager`, holds them; see *Hub and sessions* below), so everything below about a host `connect()`, its phases, cancellation, pipeline and teardown is per session. Phases actually set on the happy path:

- Host: `disconnected → detectingDevice` (the session's own device must be listed; it never takes another) `→ portForwarding` (its loopback server bound to port 0, then `adb reverse tcp:7001 tcp:<that port>`) `→ handshaking` (session key handed to adb, waiting for the tablet to dial in) `→ configuring` (waiting for the client's proof, then for HELLO, starting the media pipeline) `→ streaming`. Over Wi-Fi it starts at `handshaking`, and the proof is the pairing token; there the packet loop and the proof/HELLO waiters are set up before `startSecureServer`, because the awaits between bind and `waitForClient` (the discovery responder reads the Computer Name from a process) are long enough for a tablet dialling a known address to send its token, and `packetStream` is a broadcast stream that drops what nobody listens for. Over USB a hello without the key sends it back to `handshaking` within the same attempt.
- Client: `disconnected → handshaking` (dialling; over USB also waiting for the Mac's answer to its hello) `→ configuring → streaming`

`error` is the state while a retry is pending. A `connect()` from `error` (tapping Connect on the tablet; on the Mac, a tablet card's Retry, offered beside Cancel in `error`, or with `cap` 1 a pick of the session's own device) is that retry run early: `beginConnect()` cancels `_reconnectTimer` and clears `_recovering`, so the attempt's own failure goes through `handleLinkFailure()` and arms the next retry instead of being swallowed by the `_recovering` guard. `adbConnecting` and `paused` exist in the enum (with labels and colours) but nothing sets them. `isActive` is streaming or paused; `isConnecting` is everything except disconnected/streaming/paused/error.

**Liveness.** Heartbeat every 2 s; 6 s without any packet from the peer calls `handleLinkFailure()`. An open socket proves nothing here: the ADB tunnel can accept the tablet's connection without ever delivering it to the host.

**Cancellation.** `disconnect()`, `handleLinkFailure()` and `restartLink()` all bump an attempt counter: any of them ends the session a `connect()` in flight was building. Each `connect()` captures `currentAttempt` and `beginConnect()` up front and must check `isCancelled(attempt)` after **every** `await`, bailing through an abandon helper that only cleans up when `isLatestConnect(seq)` (a newer attempt may already own the socket or capture; the host's `_abandon` checks again after each of its own awaits). Keep to this pattern when adding an `await` to either `connect()`. The bump in `handleLinkFailure()` is what stops an attempt whose link already failed from waking later (on a timeout, typically) and failing a second time into the retry that replaced it; the host's `onTeardown()` also completes the proof and HELLO waits, and the client's `onLinkLost()` the wait for the Mac's answer, so such an attempt finds out at once. (`return abandon()` in the two `connect()` methods is what `flutter analyze` warns about; the cancellation checks added for the USB handshake use `await abandon(); return;`, which does not.) `handleLinkFailure()` remembers the value it bumped to and, after its awaits, arms no retry if a `disconnect()` has bumped it again: a Cancel pressed while a lost link is still being torn down (the host's teardown can wait a second or two behind a capture start) stays cancelled. `SocketService` has the same idea one level down: `_dialGen` makes a dial that finishes after a `disconnect()` or another dial drop its socket instead of installing it, and `_bind` ignores events from a socket that is no longer the current one.

**The host's media pipeline is a queue.** `_startCapture` / `_startRemoteReceive`, `_restartCapture`, the hub's ordered rebuilds (`_rebuildAll` for a wake, `_rebuildDisplays` for a changed display set) and the stop in `onTeardown()` run through `_exclusive()` (the hub's through `pipeline.run`), one after the other: the hub's one `PipelineQueue`, which every session shares (and the hub's `disposeSession` when it ends a session goes through it too). Never call `pipeline.run` from inside a queued operation: it would wait for itself (`stopPipelineOp`/`startPipelineOp` are the halves of a rebuild meant for inside one, and queue nothing; a start that asks for a display rebuild only asks, and the hub queues the round from a `Timer.run`). A session can end while its capture is still starting; the stop then runs right after that start instead of beside it, so it always wins. `_startCapture(attempt)` returns after any of its awaits once `isCancelled(attempt)`, leaving the cleanup to that queued stop. Don't start or stop capture outside the queue.

**Who initiates.** `SplashController` (route `/`) calls `autoConnect()` once, from `onInit` (not `onReady`, which waits for a frame), and replaces itself with `/home` 2 s later. The client always dials and retries until the host is up, and over USB dials at once when adb delivers a session key (the host has just started an attempt), so it no longer waits out its 5 s retry after the Mac connects or reconnects for a settings change. The host connects without a tap through the hub's auto-connect policy, `connectIfUnambiguous({since, only})`. It does nothing once a Cancel, Disconnect or retry has bumped the attempt since `since`, while `autoConnectPaused` is set (the facade's Home card, over Wi-Fi or over USB with no session, calls `pauseAutoConnect()` before `disconnect()` from its Disconnect or Cancel, Wi-Fi's listening card included; a tablet's own card over USB pauses nothing: it puts that tablet in `stoppedDevices`; the user's next connect from Home, `_connect()`, calls `allowDevice(serial)`, which ends both; the remote view's Disconnect doesn't pause), or while a hub `disconnect()` runs. It checks Screen Recording and Accessibility itself (`hostGranted`, by default `PermissionsChannel().hostGranted`) before anything else, then waits up to 2 s for `hostInfoReady` so the launch does not admit tablets against the conservative encoder estimate. Over Wi-Fi it starts listening while no session exists, the hub is `disconnected` and `stoppedDevices` does not hold `wifi`. Over USB it lists the devices again, then takes as candidates the attached devices (mDNS duplicates dropped) with no session and none starting, not in `stoppedDevices`, never a stand-in (`synth-`), emulators only when no real tablet is attached, and only those in `only` when given. With no session, nothing starting, the hub `disconnected` and exactly one candidate, that one connects (the first-run rule, as the single manager had: two new tablets wait for a pick); a tablet in `stoppedDevices` is no candidate but still counts as attached for this rule, so stopping one of two tablets on its card does not make the other the only one. With `cap` over 1 so does every candidate in `knownDevices` (a tablet that has had a live session), in serial order, within `cap` less the USB sessions, the starts and the user's picks still under way (keys in `_choosing`, such as a pick waiting for its tablet's old session to end; such a key is no candidate either, so it holds one place, not two). With `cap` 1 (remote control, Wi-Fi, Maximum tablets 1) only the first-run rule applies, so two attached tablets mean nobody connects by itself, as before. Each start is `_start(key)`: `connect(serial:)` unawaited (a connect returns only once its session is live), its key in `_starting` until it returns. Callers: the host's `autoConnect()` at launch; `HomeController._maybeAutoConnect()` (Home init and each app resume, once `missingPermissions` is empty); the hub's own resume (Home is not built when the app was launched hidden); and the device poll. `autoConnect()` starts the poll first (every `devicePollInterval`, 3 s; null disables it), before any permission check, so a Mac granted them after launch still connects a tablet plugged in later; `stopPolling()` ends it (`onClose`, `detached`). A tick lists nothing while one is still out, while a session is in `detectingDevice` or `portForwarding`, or over Wi-Fi, and a failed listing (`AdbService.listDevicesOrNull` answering null) changes nothing; `refreshDevices()` and `_choose`'s listing use it too, so a failed `adb devices` no longer empties the picker. Every successful listing goes through `_listed`, which sets `availableDevices` and keeps a baseline (`_seen`): the first listing only seeds it (when that first one is the poll's, the launch's listings all failed and found nothing to connect, so the policy runs once on it, for every tablet), a serial counts as gone only after two successive listings without it, and the poll ignores one empty listing right after a non-empty one (adb restarting). A session in `error_device_gone` whose tablet is listed is retried at once (`retryNow`), and tablets that appeared run the policy with `only` set to them. A USB session waiting in `handshaking` for its tablet to dial in is restarted (`HostSession.tunnelLost()` → `restartLink()`) when two successive listings during one attempt miss its tablet (`_tunnelMisses`, the baseline's two-miss rule: one listing that misses it, adb hiccupping, restarts nothing) or one lists it under another adb `transport_id` (`DeviceModel.transportId`, from `adb devices -l` via `AdbManagerPlugin`; a re-seated cable gives a new one): adb drops a device's reverse rules with its transport, nothing on the Mac fails (the wait for a dial has no timeout), and the tablet's dials would never reach the session again. `SynthAdb.transports` sets the ids in tests. The policy does not run on every tick, so the poll does not connect again a tablet that stays plugged in after the remote view's Disconnect; the next resume or Home focus does, as before, since that Disconnect pauses nothing. The launch call is what connects a Mac app started behind other windows, at login or hidden: the macOS embedder reports such an app as `AppLifecycleState.hidden` (`FlutterEngine.mm`, on occlusion), the framework then draws no frames, and the `/home` route the splash pushed is not built, so Home's controller does not exist until the window is shown. Nothing on the host's connection path may wait for a frame or a built route. One layer down, `FlutterViewController` launches the engine only in `viewWillAppear`, so an app launched hidden (`open -j`, a login item set to hide) would not even run `main()` until its window was shown: `MainFlutterWindow.awakeFromNib` therefore runs the engine itself (`engine.run(withEntrypoint: nil)`) after registering the plugins.

Every link failure (socket error/close, heartbeat timeout, or a throwing connect attempt) goes through `BaseConnectionManager.handleLinkFailure()`: it stops that link's packet listener + heartbeat, runs the role's `onLinkLost()` (host: full `onTeardown()` — releases any mouse button the tablet left held (`InputInjectChannel.releaseAll()`), then capture, virtual display, adb tunnel; client: only lets go of a dial still waiting for the Mac's answer, so its keep-alive service survives for background reconnects), closes the socket (server included), sets `error`, then retries after `nextRetryDelay()` (`retryPending` is true from arming that timer until it fires, or `beginConnect()`, `disconnect()` or `restartLink()` drops it): the client 5 s; a host USB session 1 s, then 2, 5 and every 10 s (each ±20%) while it keeps failing, from 1 s again once it has been live (an adb restart drops every tunnel at once, and the retries must not storm it); a Wi-Fi session always 1 s. `handleLinkFailure(retry: false)` does all of that but arms no timer, for a failure trying again cannot fix (a host session the encoder has no room for, `CaptureLimit`); `_recovering` stays set, so the resume rule and a late socket error leave it alone, until the next `connect()` (`beginConnect()` clears it). Beside `errorMessage`, `errorKey` holds the `LinkError` key behind it (null for anything else; the client's fallbacks set `error_waiting_for_host` or `error_wifi_untrusted`, the hub's "No ADB device detected" sets none), so the UI can branch without comparing translated text. Host exceptions: a media pipeline that fails to start is only logged (`connect()` catches a throw from `_startCapture()`; the reverse-remote decoder init in `_startRemoteReceive()` swallows its own error), so the link still reaches `streaming` with no video instead of retrying, except `CaptureLimit`, which ends the session with no retry (see *Encode budget*). Never retry by calling `connect()` on a live session — that stacked duplicate listeners/timers and a second server socket. `restartLink()` is the one other way a session is replaced: the same teardown as a link failure, followed by `connect()` at once (the client uses it when a new USB session key arrives). It does nothing while a `disconnect()` is still tearing down (`_stopping`, `isStopping`): `disconnect()` sets `disconnected` only at its end, so a key arriving during the tablet's teardown used to start a link that outlived the user's Disconnect. `HostSession.connect()` refuses then too: a `reconnect()` of a session in `error` leaves it reading `error` with no retry pending through its teardown, and a connect started meanwhile (its card's Retry, `retryNow`, the resume rule) had its server closed and its phase overwritten under it, then ran beside the reconnect's own as a second attempt on one session. `SocketService` owns the raw TCP socket; `AdbService` wraps `adb` CLI calls. Over USB `SocketService.send()` is fire-and-forget (`Socket.add` with `tcpNoDelay`, errors swallowed, no flush or backpressure), and the server takes one client and destroys any further connection. Nothing on the sending side reacts to a slow USB link: frames queue in the socket, Max's adaptive rate only measures encoder load, and the one relief is the client decoder's queue cap (see `VideoDecoderPlugin.kt`). Wi-Fi sockets are paced instead (see *Link types*). The **macOS host is the sole settings/control surface**: display mode, encode preset and codec are editable only on the host (the client's Settings page renders none of those controls, only language, permissions and info). Every setting change persists the value and then calls `reconnect()` (full disconnect + reconnect to the same device, debounced 350 ms in `SettingsController` so several edits in one sheet collapse into one) so the capture/encode pipeline restarts with the new value. Five things don't reconnect: Maximum tablets (Settings → Tablets, 1 to 8) is only saved, since the hub's `cap` reads it at each pick and admission and a lower cap ends no tablet already connected; the overlay/HUD toggles push `0xFA` via `sendUiFlags()`; the language picker only calls `SettingsService.setLocale()`; the "keep the Mac cursor in place" toggle is pushed to `InputInjectPlugin` by an `ever()` worker in `InputInjectChannel.onInit()`; and session mode / remote direction are picked on Home (the selectors show only while nothing is connecting or live and there is at most one session), so they are just persisted and read by the next connect. On each start the host announces the active codec to the client via a `0xFC` control packet; the client's `DisplayController` rebuilds its decoder if that differs from the codec it was built with (see the `0xFC` row).

On the host, connects the user starts on Home (the Connect button, picking a device, a tablet card's Retry) go through `HomeController._connect()`, which is gated by `_ensureHostPermissions()`: if Screen Recording or Accessibility is missing, it snackbars, navigates to Settings with `arguments: {'scrollTo': 'permissions'}` (`SettingsController` scrolls to the Permissions header via its `permissionsKey` `GlobalKey`) and does not connect. The automatic connects (the auto-connect policy above) only check the permissions (`hostGranted` / `missingPermissions`) and never snackbar or navigate; the launch one takes `currentAttempt` first and stands down if a Cancel, Disconnect or retry came while it waited (adb's first call can take seconds; over Wi-Fi it does not wait for adb at all, and `adb devices -l` is ended after 10 s). Everything else calls `connect()` directly and skips the gate: the `handleLinkFailure()` retry, the resume reconnect in `BaseConnectionManager.didChangeAppLifecycleState`, `retryNow`, and `reconnect()` (settings changes, the remote view's Reconnect button; on the hub every session's). In reverse remote, Home opens `/remote-host` from a phase worker and also on its first frame when the session is already live (the launch can get there before Home exists).

### Packet protocol (`lib/shared/models/packet_model.dart`, `lib/shared/protocol/packet_codec.dart`)

Framing lives in `Packet.serialize()` and `SocketService._tryParsePackets()`: a 17-byte header (4-byte magic `EXTD` + 1-byte type + 4-byte payload length + 8-byte timestamp in µs) followed by the payload, all big-endian. `PacketCodec` only encodes and decodes payloads (input events, heartbeat ping/pong) as hand-rolled binary. An unknown type byte parses as `CONTROL`, a bad magic flushes the whole receive buffer, and a header announcing more than `SocketService.maxPayloadBytes` (16 MB) drops the peer (`_dropPeer`, reported like a close by the peer). A pong echoes only the ping's nine bytes. There is no version negotiation, and host and client are separately installed builds, so a wire change needs both rebuilt (the USB handshake was such a change: a build from before it and one from after refuse each other, see *Link types*). The only tolerance is for older, shorter payloads (`decodeMouse` without the modifiers byte, `_onHello` without the size or the rate). Enums travel as `.index`: `MouseAction`, `MouseButton` and `TouchAction` in input payloads (`InputInjectPlugin.swift` switches on the raw integers) and `SessionMode`/`RemoteDirection` in `0xF9`, so append to them and never reorder.

Packet types: `FRAME_DATA` (one encoded frame as an Annex-B buffer, in whichever direction the stream runs; keyframes are prefixed with their parameter sets, so a payload can hold several NAL units despite the `nal` naming in code), `TOUCH_EVENT`, `MOUSE_EVENT`, `KEY_EVENT`, `HEARTBEAT`, `CONTROL` (`ack` and `displayConfig` are declared but unused). The Android display currently sends only `MOUSE_EVENT`: `TouchGestureRecognizer` turns touches into click, scroll (with a fling, skipped when the finger rested longer than `_flingMaxIdle`, 100 ms, before lifting), long-press drag and pinch (⌘+scroll). `DisplayController._sendMouse` always sends `MouseButton.left`, so there is no right-click. A drag is down, `MouseAction.move`s, up; extra fingers during it are ignored, and every path that ends it (lift, cancel, `_reset()`, `dispose()`) goes through `_endDrag()`, so exactly one up follows each `onDragStart`. That up is dropped if the link is already down (`sendMouse` needs an active phase); the host's `releaseAll()` on teardown covers that case. `sendTouch()`/`sendKey()` have no callers, though the host decodes and injects all three.

Control sub-commands are the first payload byte, dispatched in each manager's `onRolePacket()`:

| Byte | Direction | Meaning |
|---|---|---|
| `0x01` | client → host | HELLO (sent once the peer is trusted: after `0xF5` over Wi-Fi, after the `0xF4`/`0xF3` exchange over USB): platform byte (`0x02` = Android), panel width and height (uint16 BE each, physical px, landscape), panel top refresh rate (1 byte, Hz). The size is the whole display, not the Flutter window (which can leave out the nav bar): `ClientConnectionManager._nativePanelSize()` reads `view.display.size`, falling back to `view.physicalSize` if the display is unreported or empty. The same size drives the reverse-remote capture |
| `0xFF` | viewer → encoder | Request an IDR. Client → host normally. Host → client in reverse remote: once as the host starts receiving (`_startRemoteReceive()`, after `0xF8`), and whenever `RemoteVideoPlugin.swift` raises `onRequestIdr` (a decoder fed pictures it cannot decode, at most once a second). The tablet passes it to its encoder (`PARAMETER_KEY_REQUEST_SYNC_FRAME`), so its next frame is a keyframe; with no capture running it does nothing |
| `0xFE` | host → client | Client replies with `0xFF`. Still handled, but nothing sends it |
| `0xFC` | host → client | Codec (`0` H.264, `1` H.265). Only `ClientConnectionManager` handles it, storing it in `SettingsService`. `DisplayController` records the codec each decoder build used (`_decoderCodec`), and an `ever(codecRx)` worker rebuilds whenever the setting differs, so a display opened before the announcement (on `streaming`, with last session's codec) still switches; the codec already running causes no rebuild. A build bumps `_decoderGen`, cancels the frame subscription, and stops after any await once superseded or closed. The native decoder ignores `initialize` while configured, so a rebuild must `dispose()` first |
| `0xFB` | host → client | Stream refresh rate (Hz) |
| `0xFA` | host → client | Performance-overlay and HUD-stats toggles (HUD off hides only the stats; Back and Disconnect stay) |
| `0xF9` | host → client | `SessionMode` index + `RemoteDirection` index |
| `0xF8` | host → client | Reverse remote: start capturing (codec, fps, bitrate in Mbps) |
| `0xF7` | host → client | Reverse remote: stop capturing |
| `0xF6` | nobody sends it | Was Wi-Fi pairing on USB sessions; the client now ignores it on every link (see *Link types*). The byte is still the first one of the pairing payload that adb delivers: `0xF6`, version byte, host id (16), token (32), name (1-byte length + UTF-8), certificate (uint16 BE length + DER), then the Mac's IPv4 addresses (count byte + 4 bytes each, at most 8; a payload may end at the certificate). Built and parsed by `WifiPairingService` |
| `0xF5` | client → host | Wi-Fi sessions only, first packet: the paired host's token (32 bytes) |
| `0xF4` | client → host | USB sessions only, first packet (the hello): nonce (16) + HMAC-SHA256(session key, client label + nonce) (32). The HMAC is left out when no key has been delivered; such a hello only tells a waiting host that the app is there. Built and checked by `UsbSessionService` |
| `0xF3` | host → client | USB sessions only, the answer to a hello that proved the key: HMAC-SHA256(session key, host label + nonce) (32). Nothing else from the peer is admitted by the client before it |

The host waits (3 s timeout) for the HELLO before starting capture and persists the reported panel via `SettingsService.setClientPanelFor(key, panel)`: under that tablet's key and as the last panel any tablet reported. The client sets its display mode from the host's `0xFB` (the slowest panel mode ≥ the stream rate, never below 60 Hz), not from its own (host-only) preset; a mid-stream `0xFB` only switches the panel mode (`setRefreshRate`, which also moves the decoder's input-queue cap) — the decoder is configured with the panel's top rate as its operating rate so it's never rebuilt for a rate change.

One `RemoteDecoder` (its own texture) per session: `initialize {session, codec}` replaces that session's decoder and answers the texture id, `dispose {session}` unregisters it, and each `remote_nal` message is the session's id (4 bytes, big-endian) then the frame (`RemoteVideoChannel.feedNal(session, bytes)`, which copies exactly the frame: it used to send a payload view's whole backing buffer). A decoder made while another is live must be a hardware one; a failure reaches Dart as `onCodecError`. A decoder fed pictures it cannot decode (no parameter sets yet: it joined a stream already under way; or a decode error) raises `onRequestIdr {session}`, at most once a second (`RemoteVideoChannel` gives it to that id's `listenIdr` listener if it has one, else to its `onRequestIdr` slot, the hub's). An `alive` flag keeps a late decode callback off an unregistered texture, and a torn-down decoder from asking for keyframes. Mirror image of the Android `VideoDecoderPlugin`. |
| `SocketSender.swift` | (legacy/alternative) NWConnection TCP sender; main path now goes through `SocketService` on the Dart side. |

Plugins are registered in `MainFlutterWindow.swift` against the Flutter engine, which that file then starts at once rather than when the window first appears (see *Who initiates*): register a new plugin before that `run` call. On both platforms they are hand-written (not pub plugins) on channels named `extended_screen/<name>`, each with a Dart wrapper (`*_channel.dart`, or `AdbService`). The exception is `SurfaceViewPlugin`, which has no channel or wrapper: it registers the platform-view type `extended_screen/surface_view`, which `display_view.dart` embeds with `AndroidView`. Adding a native method means touching the wrapper and the Swift/Kotlin handler; a new plugin also needs registering in `MainFlutterWindow.swift` / `MainActivity.kt`. A new Swift file is only compiled once it is added to the Runner target in `macos/Runner.xcodeproj/project.pbxproj`, which lists each source explicitly (`PBXBuildFile`, `PBXFileReference`, Runner group and Sources build-phase entries); a new Android `Service` also needs a `<service>` entry in `AndroidManifest.xml`, and a foreground service that only serves the Dart side also needs stopping with the activity (see *Native Android plugins*).

`AppDelegate` keeps the app alive after its window closes (a menu-bar item reopens it), so streaming continues with no window. Its own `static func main()` is the entry point: `VirtualDisplayModeHelper.runIfAsked()` (a child run that switches a virtual display to HiDPI exits there: `--extendedscreen-set-hidpi <displayID> <w> <h>`; the flag with anything else malformed exits 2, because falling through to `NSApplicationMain` started a second, full app whose auto-connect took a tablet and an adb tunnel), then `NSApplicationMain`; nothing else may run before that check. The host cannot run sandboxed, since it execs `adb` and posts CGEvents; that is why neither `DebugProfile.entitlements` (Debug/Profile builds) nor `Release.entitlements` (Release builds) has an App Sandbox key. `Info.plist` carries `NSLocalNetworkUsageDescription` for the Wi-Fi link: macOS 15+ asks the user before the app may talk to the local network. Extend also rests on a private API: `CGVirtualDisplay` and its descriptor, settings and mode classes are not in the public SDK, so they are declared by hand in `macos/Runner/CGVirtualDisplay.h` and reach Swift through `Runner-Bridging-Header.h`. A property or method not listed there has to be declared in that header before Swift can call it.

### Display modes

- **Extend:** Creates a `CGVirtualDisplay` matching the tablet resolution (logical panel ÷ 2, HiDPI, one mode w×h); ScreenCaptureKit captures that virtual display. Whether it comes up HiDPI (w×h pt over 2w×2h px) or 1x (bounds at the pixel size, tiny text on the tablet) is macOS's choice, and for a display it has no saved mode for it rests on the size in millimetres the descriptor reports (measured on macOS 27.2, M3 Pro, undocumented): HiDPI only when that is at least ~166 mm wide and at least ~150 px/in. The size used to be the logical width at 220 ppi, under 166 mm for every panel narrower than 1440 pt, so only the Tab S10 Ultra (1480 pt, 171 mm) came up HiDPI and an iPhone, the emulators and a foldable came up 1x; it is now the pixel buffer at 218 ppi, wide enough for any w ≥ 713 pt. A display below 800×525 pt (1600×1050 px) never comes up HiDPI, whatever the millimetres (832×440 came up 1600×846 pt at 1x), so `hiDPISize` grows a smaller panel's display, keeping its shape, until it fits (832×440 → 993×525 pt); the capture still encodes the panel's w×h × scale, so the tablet gets that desktop scaled to its panel (text at about 84% of its usual size). macOS also remembers the mode per display UUID (vendor, product, serial; not the millimetres) and set of attached displays, in `/Library/Preferences/com.apple.windowserver.displays.plist`, so a `vdSerial` that once came up 1x at a size comes up 1x there again. `createVirtualDisplay` therefore checks the display once it is active (`isHiDPI`: the bounds are vw×vh, and the mode, when there is one, is 2x) and otherwise switches it with `VirtualDisplayModeHelper`: the app's own executable run as a child with `--extendedscreen-set-hidpi <displayID> <w> <h>`, which `AppDelegate.main` hands over before `NSApplicationMain`, so the child never becomes an app. It touches only a display reporting the descriptor's vendor and product (0x3456/0x1234), leaves another HiDPI mode alone (the user's pick in System Settings, exit 4), and makes the switch `forSession`; macOS saves it, so the next display with that serial comes up HiDPI by itself. Never make the switch in the app's own process (`CGConfigureDisplayWithDisplayMode`, even `forAppOnly`/`forSession`): the display then stays active after release until the process exits (measured: still listed 8 s after release), while the child's switch leaves nothing behind (released in about 0.1 s). `createVirtualDisplay` answers after the switch (about 0.5 s more), and a display still not HiDPI then gets a `WARNING` line. A new one can take a moment to appear in ScreenCaptureKit's list, so `findCaptureDisplay` looks it up once and then re-polls up to 6 times, 0.25 s apart (~1.5 s); if it never shows up, capture falls back to the main display with a `WARNING` unified-log line and releases the virtual display. A session with no virtual display at all (`createVirtualDisplay` made none) captures the main display at once, with the same kind of line. Either way `startCapture` answers `fellBack`, and `HostSession._startCapture()` sets the session's `notice` to `error_extend_unavailable` ("Extend unavailable, mirroring"), which its `SessionCard` shows (and the Loopback preview's tile).
- **Mirror:** Captures the `CGMainDisplayID()` display (the one with the menu bar; the first listed one if it is missing); no virtual display created.

The encoded frame always has the panel's aspect ratio: panel-sized at a capture scale of 2.0, half-sized for `performance`, and `customWidth` wide for `custom`. A display of another shape (Mirror from a notched MacBook or a 16:9 monitor) is scaled to fit with bars, and the tablet normalizes touches over the whole frame, so `InputInjectPlugin` maps them through the session's `CaptureContentRect` onto the picture before scaling onto the captured display's bounds.

There is no in-place mode switch: changing the mode goes through `reconnect()` like every other setting. Remote-control sessions always capture in Mirror regardless of the setting.

The only in-session rebuild is `HostSession._restartCapture()`, fired through `ScreenCaptureChannel.onCaptureRestartNeeded` (routed by the hub) when the Swift plugin invokes `onCaptureNeedsRestart` (the Mac wakes from sleep) or `onStreamStopped` (the `SCStream` stops with an error; its `asleep` says the main display was asleep then). With one session able to rebuild (`canRebuild`: capture wired, live, not reverse remote) the hub hands both to it, an asleep stop like any other. With two or more, a wake is one hub operation (`_rebuildAll`, a single `pipeline.run`): it snapshots those sessions in key order with their attempts, runs every `stopPipelineOp()` (bitrate adaptation, frame subscription, `stopCapture`, `removeVirtualDisplay`), then every `startPipelineOp(attempt)` (`_startCapture()`, then an IDR), skipping one whose attempt moved or that is no longer active (or, for a display round, still `configuring` with its capture wired), so nothing slots between the stops and the starts and the displays come back in the same order every time; a wake during it gets one more full round (`_rebuilding`/`_wantAll`), a session whose stop threw is not started, and an asleep stop is ignored (the wake rebuilds it with the rest). A session's own requests are deduplicated by generation: each `startPipelineOp` bumps `_pipelineGen` before its first await, each request records it (`_restartRequestedGen`), and a queued round finding it moved since the latest request skips, so a stream-stop heard before the wake started that session is covered by it, while one after its start still gets a round of its own. Re-admission to the budget is idempotent, and a failed rebuild keeps its place (a reservation, which lets the other tablets climb into its share meanwhile), so a wake never refuses a running tablet, even after a round that failed (the displays still dark) and under a lowered Maximum tablets. Sleep invalidates ScreenCaptureKit, the virtual display and the VideoToolbox session, but the ADB socket survives, so after a short sleep or a display-only wake nothing else would recover. ScreenCaptureKit also stops the stream the moment the displays go to sleep (measured), so a rebuild runs then and fails: the virtual display can't be made and no display is found. The wake is what recovers: the plugin forwards every wake once any session exists, whether or not a stream is running (it used to forward only while one was, so a display sleep left the tablet frozen for good), and Dart rebuilds whichever session is still connected. Its two notifications (system and display wake) send one `onCaptureNeedsRestart`, 1.2 s after the last of them (`wakeGeneration`). A start that fails after making its encoder stops at once, releasing the encoder and App Nap's hold. A request that arrives while a session's rebuild runs gets a round of its own after it (`_restartAgain`), for the session that asked, unless that rebuild's start came after the request. (A link that sat silent past the 6 s heartbeat timeout goes through `handleLinkFailure()` instead, which rebuilds the whole session.) The rebuild is skipped in reverse remote. It stops capture, removes and recreates the virtual display, re-runs `_startCapture()` and forces an IDR. It does not call `releaseAll()`: the link is alive, so the tablet's mouse-up still arrives. `onDisplayBoundsChanged` (displays rearranged in System Settings) only refreshes the cached bounds that map normalized input coordinates to screen space.

**Several virtual displays (Apple FB17797423).** With several virtual displays, once the set changes macOS can hand a new `SCStream` another session's display (the most recently added) instead of its own, until every virtual display is gone. Reproduced on macOS 27 (M3 Pro): with an emulator extending, the Tab S10 Ultra was replugged; its retry made display 68 and its stream showed the emulator's 67 (`WARNING: the capture of virtual display 68 does not fill the frame`). An ordered full rebuild fixed it. So the hub keeps the display set (`VirtualDisplays`, in `host_session.dart`, `hub.displays`, handed to each session it makes): `_startAdmitted` calls `adding(this)` right before `createVirtualDisplay`, and `removed(this)` once `removeVirtualDisplay` has answered (`stopPipelineOp`, the teardown's queued stop), when no display was made (`displayId` 0), when `startCapture` answers `fellBack` (the plugin released it) and in `dispose()`. A session adding its display while another session's exists (a tablet joining, a retry after a lost link, one session's `reconnect()`, its own `_restartCapture`) is noted as due (`adding` puts it in `_due`), and asks only once its capture has started on that display (`started(this)`, right after `startCapture` answers without `fellBack`, still inside the queued start, so the round runs after it). A start the encoder refuses (`ENCODER_BUSY`/`NO_ENCODER`, which a join turns into `CaptureLimit`), one that made no display, fell back, threw or was cancelled asks for nothing (`startFailed`, `removed`): nothing of it runs to be fixed, and asking anyway stopped and restarted every extending tablet for a tablet that never ran, again on each Retry. The ask goes to `onRebuildNeeded`, the hub's `_displaysNeedRebuild`, which only sets a flag and queues `_rebuildDisplays` from a `Timer.run` (the ask comes from inside the queued start; several asks before the timer make one round, and a display round still waiting in the queue covers any ask made meanwhile, `_displayRoundWaiting`). That round (`_rebuildRound(displays)`, one `pipeline.run`) is the wake's shape with other targets: every session with `rebuildsDisplay` (not retired, capture wired, live or still `configuring` (a session whose connect has just started its capture, which may be the one that joined; `startPipelineOp` lets those through too), not reverse remote, holding a display), in key order, all stopped, then all started; and before those stops it takes down the displays of sessions on their way out (holders that are not targets: an ended or failing session whose own queued stop would come after the starts), so the set really is empty before any display is made again. Mirror sessions make no display, so they neither ask nor are rebuilt by it, and one display alone never asks. Every running Extend tablet blips for about a second per change. The displays a round makes, a wake's included, ask for nothing: the hub sets `VirtualDisplays.rebuilding` for the whole round, so no round feeds the next. The wake path is otherwise unchanged: wake and display rounds share `_rebuild` (`_wantAll`, `_wantDisplays`), a wake asked during any round gets a full round after it, a display ask during a wake round a display round after it. A first frame that shows another display (`onCaptureMismatch`) is ignored, neither asking nor counted, when that capture is going to be made again anyway (`VirtualDisplays.willRestart`: its own join's ask is still due, or the hub's `_roundWillRestart`: a round asked for or queued that will take it as a target, or a round under way that has not yet started it again, `_roundStartsLeft`). On the device a joiner's first frame showed the other tablet's display while its join's round was stopping the other tablet (whose `removeVirtualDisplay` can take a second), so it asked for a second full round and used up one of its two retries. Otherwise it asks for the same round through `VirtualDisplays.requestRebuild()`, only while another session holds a display and at most twice in a row per session (`_wrongDisplayRebuilds`, `_maxWrongDisplayRebuilds`), and `onCaptureMatched` (a first frame that fills its frame) sets the count back to 0; past that, or with no other display, the session only sets `notice` to `error_extend_wrong_display`, as before.

### Key settings (`lib/shared/services/settings_service.dart`)

Persisted via `shared_preferences`: session mode and remote direction, link type (`link_type`, per device) and the client's typed Mac address (`wifi_host_address`), display mode, last paired device serial and model name, the client's panel size and top refresh rate (from its HELLO, so presets stay correct across launches: per tablet as `client_panel.<key>` ("width,height,maxHz"), and the last one reported in the global `client_panel_w/h/max_hz`), the reverse-remote screen-off choice per tablet (`tablet_screen_off.<serial>`), the tablets the host has had a live USB session with (`known_devices`, a JSON list of `KnownDevice`: serial, model, `vdSerial`, `installId`; malformed JSON reads as none), and the cap on tablets at once (`max_tablets`, `maxTabletsRx`, default 4, clamped to 1..8; set on Settings → Tablets with no reconnect, and read by the hub's `cap` over USB in Extended screen, within the encoder estimate's `tabletCap`), and what the host learned of its encoder's capacity per chip and codec (`encoder_capacity.<chip slug>.<codec>`, Mpx/s, never from a synthetic tablet). `SettingsService.init()` migrates once (`_migrateToPerTablet`): the global panel and the old global `tablet_screen_off` become the saved last-used device's own, and the old screen-off key is removed; and while `known_devices` is absent (its presence is the run-once marker), a saved `last_device`, read raw, never through `lastDeviceSerial` and its baked-in fallback, becomes the one known device with `vdSerial` 1, the serial every virtual display had before, so macOS keeps its arrangement. Nothing falls back to the global values by the current last-used device, or a tablet that became last-used later would inherit another's choice. `vdSerialFor(key, taken:)` is a known device's own `vdSerial`, else `fnv1a32(key) | 0x10000`, stepped past 1, `taken` and every stored one (it saves nothing); `vdNameFor` is `Extended Screen` for serial 1 and `Extended Screen – <model, _ as spaces>` otherwise when a model is known; `rememberDevice` upserts a known device (keeping its `vdSerial` and `installId`) and still writes `last_device`/`last_device_name`, which the first-run auto-connect reads, and Settings' Target device row when no session is live (it lists the live sessions' models, joined, else the focused device's, else `last_device_name`). The hub calls `vdSerialFor` and `vdNameFor` when it makes a session, and a USB session calls `rememberDevice` once it is live (see *Hub and sessions*). Synthetic tablets (`synth-*` serials, `SettingsService.isSyntheticKey`, `DeviceModel.isSynthetic`) are never persisted: `setClientPanelFor` (the global last panel included), `rememberDevice`, `setLastDevice` and `setTabletScreenOffFor` do nothing for one; `setLastDeviceName` takes a model name, so only `rememberDevice` guards it. Also persisted: encode preset (plus custom width/height/bitrate/refresh for the `custom` preset), codec (`h264`/`h265`; with none saved, `init()` resolves it once at launch via `SettingsService.defaultCodecFor` — H.265 for `max`, H.264 otherwise — and it does not follow later preset changes, except that selecting `max` in the picker sets and saves H.265), UI locale (`en`/`th`), performance/HUD overlay toggles, and "keep the Mac cursor in place" (`keep_mac_cursor`, default on; host only). A build-time `--dart-define=DEVICE_SERIAL=<serial>` (a default is baked in) does not pin the target device: it is only what `lastDeviceSerial` returns when no serial has been saved, and the hub reads that getter only when `connect()` is called without a serial and with no session to retry (the Home device picker and the single-device auto-connect always pass one). If that device isn't attached, the first ADB device is used; once a session exists, its retries stay on its own device. `crypto` is a direct dependency for the USB handshake's HMAC-SHA256. `flutter_secure_storage`, `permission_handler`, `protobuf` and `async` are declared in `pubspec.yaml` but not imported anywhere yet (`flutter_secure_storage_macos` is the plugin behind the "do not support Swift Package Manager" warning on every macOS build).

### Encode presets (`lib/shared/models/display_config_model.dart`)

`EncodePreset` bundles resolution + scale factor + bitrate + refresh rate into five presets: `max` (the default), `quality`, `balanced`, `performance`, and `custom` (user-adjustable values persisted in settings); there is no separate frame-rate setting. `max` is native resolution at the client panel's top refresh rate (`clientMaxRefreshHz`, from the HELLO); its bitrate is `_qualityBitsPerPixel` (Quality's 20 Mbps at a fixed 2960×1848 @ 60 Hz reference) × panel pixels × top rate, clamped to 8 to 50 Mbps, so on a smaller panel it can be below Quality's fixed 20 Mbps. It passes `adaptiveFps` to the Swift encoder, which adapts over the ladder 30/45/60/90/120 plus the start rate, never above it. A saturated VideoToolbox session doesn't skip frames — `VTCompressionSessionEncodeFrame` blocks the timer thread once ~8 frames are in flight — so overload is detected as the encode queue pinned near that cap or the timer falling under 90% of its rate. After 3 s of that it drops straight to the highest rate that fits in 95% of the achieved throughput (e.g. an M3 Pro's H.264 session saturates near 50 fps at 2960×1848, so it lands on 45; HEVC sustains ~2× that), and steps back up one notch after `stepUpDelay` healthy seconds (10 s, doubling up to 5 min whenever a step-up fails within 30 s). Each change is reported via `onFrameRateChanged` so the host re-announces `0xFB`; an overload step-down also carries `achieved` (the ticks/s it managed), from which the hub's budget learns (see *Hub and sessions*). Keyframes stay at most a second apart at any rate (`MaxKeyFrameIntervalDuration`). While capturing, the plugin holds a `ProcessInfo` activity (`userInitiatedAllowingIdleSystemSleep` + `latencyCritical`) so App Nap can't throttle the usually-hidden host and stall encoding. In reverse remote (tablet encodes), `max` falls back to native @ 60 Hz / 20 Mbps. Fixed-preset resolutions are **relative to the connected client's panel** (read from `SettingsService.clientPanelWidth/Height`): logical size is always panel ÷ 2; `scaleFactor` 2.0 (quality/balanced) encodes at native panel resolution, 1.0 (performance) at half. Custom's width is the **physical encode width** (the picker labels each option as physical W×H): the desktop stays at panel ÷ 2 logical like the fixed presets, and `SettingsService.captureScaleFactor` becomes `customWidth ÷ (panel width ÷ 2)`. `customHeight` is only persisted and displayed, never used for capture: the encoded height is (panel height ÷ 2) × that scale, so it follows the panel's aspect ratio (the 1920×1200 option encodes at 1920×1198 on a 2960×1848 panel). The Swift `startCapture` multiplies logical × `scaleFactor` (clamped to even dims); `CGVirtualDisplay` is always created at logical × 2 (HiDPI). `HostSession._startCapture()` takes its config from `SettingsService.captureConfigFor(panel, spec)`, which feeds the settings to `EncodePresetX.configFor(panel, custom:, mode:, codec:)` (no settings read there; custom's scale clamped to 0.5..2.0; `known_devices_test.dart` checks it against the `capture…For(panel)` getters for every preset), and then from what the encode budget grants. `DisplayConfigModel.encodedWidth/Height/Pixels` round as the Swift side does, and its `fpsCeiling` (sent in `toMap` only when set) is the rate cap `EncodeBudget` (`lib/shared/connection/encode_budget.dart`, pure; its class comment is the reference) grants a session sharing the encoder with others: demand is encoded pixels × fps over the chip's estimate (`EncoderEstimate.forChip`: 274/550 Mpx/s per engine for H.264/H.265, 1 engine for a base or Pro chip, 2 for Max, 4 for Ultra; anything else 140 and at most 2 tablets) or what was learned of this Mac's encoder when that is more (see *Hub and sessions*), 85% usable; a tablet alone gets its config unchanged, a newcomer may get a lower resolution (native, 1920 wide, scale 1) if its 30 fps floor doesn't fit, and running tablets only change their ceiling (the largest demand steps down the 120/90/60/45/30 ladder). A refusal is `CaptureLimit` (`error_encode_limit`). The Swift side honours the ceiling (`startCapture`'s `fpsCeiling`, `setFrameRateCeiling`; see the `ScreenCapturePlugin.swift` row); how the sessions use the budget is under *Hub and sessions*.
