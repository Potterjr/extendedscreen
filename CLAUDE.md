## Project Purpose

**extendedscreen** turns an Android tablet into a second monitor for macOS via USB-C, or over Wi-Fi once the two have been paired over USB (see *Link types*); over USB the Mac holds several tablets at once, each its own session in its own mode (extending onto a virtual display of its own and sharing the Mac's encoder, or remote control in either direction; see *Hub and sessions*). The macOS app (Flutter + Swift native plugins) captures the screen and streams H.264/H.265 over an ADB-reverse TCP tunnel (USB) or TLS on the LAN (Wi-Fi); the Android app (same Flutter codebase, different platform role) decodes and renders frames while sending touch gestures back as mouse events (click, scroll, drag, pinch); it forwards no keyboard input. **Nothing is hardcoded to a specific tablet model**: the client reports its native panel size in the HELLO handshake and the host derives all capture/encode resolutions from the connected device. The Android client is landscape-locked (manifest + `SystemChrome` in `main()`, kept on Android 16+ by a manifest opt-out, which only works while `build.gradle.kts` pins `targetSdk` to 36; see *Native Android plugins*). A second session mode, remote control, reuses the same link to drive the Mac from the tablet, or to view and drive the tablet from the Mac (see *Session modes and stream direction*). Apart from all of that, the Mac can also view and drive an iPhone plugged into it, through AVFoundation and an XCUITest runner rather than this app's protocol (see *iPhone over USB*).

- An end-to-end session needs both sides running: the macOS host and the Android client are the same app. `.vscode/launch.json` has a compound config that launches both; its device id and `DEVICE_SERIAL` are one specific tablet's serial.
- The Mac app's preferences are `~/Library/Preferences/com.example.extendedscreen.plist` (keys prefixed `flutter.`). On a Mac that ever ran a sandboxed build of this bundle id, `defaults read com.example.extendedscreen` answers from the leftover container (`~/Library/Containers/com.example.extendedscreen/…`) instead, and a `defaults write` goes there too, where the app never looks. Give `defaults` the path: `defaults read ~/Library/Preferences/com.example.extendedscreen flutter.link_type`.
- `adb` is **not** resolved from `$PATH`. `AdbManagerPlugin.adbRun` probes `/usr/local/bin/adb`, `/opt/homebrew/bin/adb`, then `~/Library/Android/sdk/platform-tools/adb`.
- The USB link: the tablet dials its own `127.0.0.1:7001` (`BaseConnectionManager.host`/`port`); on the Mac each tablet's session listens on a loopback port of its own (bound to port 0), and `adb -s <serial> reverse tcp:7001 tcp:<that port>` joins the two, so `adb reverse --list` shows `tcp:7001 tcp:5xxxx`. The Wi-Fi link is TLS on 7001 on the Mac's LAN address, plus UDP 7001 for discovery.
- `flutter analyze` covers Dart only (`analysis_options.yaml` excludes `android/**`, `macos/**` and `ios/**`); Swift and Kotlin are checked only by building, plus the two `tool/*_check/run.sh` scripts above for the input shell and the remote decoder. It is not clean today: every `return abandon(…)` in the two `connect()` methods raises `unawaited_return_in_try_block` (14 warnings, no errors), so those are not regressions.
- The Runner target's Release configuration signs manually with a fixed `DEVELOPMENT_TEAM`, so `flutter build macos` needs that team's certificate; Debug signs ad hoc. The Android `release` build type signs with the debug key.
- Dart logs go through `LoggerService`, a `logger` instance with the package's default `DevelopmentFilter`: they print to the console, in debug builds only. In profile and release builds the Swift `esLog` lines (the `log stream` command above) are the only diagnostics, so a Dart-side failure such as capture not starting leaves no trace.
- Tests use `SharedPreferences.setMockInitialValues`, fake `BaseConnectionManager`/`DisplayController` subclasses, or (`display_codec_test.dart`) mock handlers on the `extended_screen/video_decoder` and `nal_feed` channels. That file also fakes wakelock_plus's macOS channel and its pigeon channel; on a Linux or Windows test host wakelock_plus registers a different implementation, so it may need another fake there. `wifi_link_test.dart` is the exception to fakes: it opens real loopback sockets (plain `test()`, since `testWidgets`' fake clock never completes real I/O) and gets a real certificate from `/usr/bin/openssl`, skipping those tests where that binary is missing. It runs a `HostConnectionManager` and a `ClientConnectionManager` side by side by passing each its own `SocketService` and a free port (the managers' optional `socket`/`port` constructor arguments exist for this, as does `SocketService(tlsDialTimeout:)`; the hub hands its socket and port to the session it makes). Over USB the free port is the tablet's side: `_NoAdb.reverseForward` (with `tunnel`) binds it with a `_Forwarder` that joins each connection to the Mac port the rule names, as adb does, re-pointed by a later reverse and closed by `removeForward`. A discovery test that expects an answer on each of this machine's addresses keeps only those a datagram comes back on (`_udpReachesItself`): a VPN tunnel's address is in `lanAddresses()` too and answers nothing. Several of its tests play a hostile machine on the LAN (connect and leave, skip the token, flood discovery, announce a huge packet); they take a few seconds each because they wait out real timeouts. ## Architecture

### Dual-role Flutter app, organized by feature module

The same Dart codebase runs on both sides of the link. The tree is organized **by feature module first, then by role**, with a central shared backbone (imports are `package:extendedscreen/...`):

- **`lib/shared/`** — the cross-mode backbone used by both roles *and* both feature modules:
  - `connection/` — `socket_service`, `connection_state`, the abstract `BaseConnectionManager`, plus the concrete `HostConnectionManager` (the host's hub) and `HostSession` (one per tablet), `PipelineQueue`, `ClientConnectionManager`, `AdbService`, the two Wi-Fi services (`WifiPairingService`, `WifiDiscoveryService`, registered on both roles) and `UsbSessionService` (the USB session handshake; an instance only on the client, where it holds the key adb delivered), and `usbmux.dart` (`UsbmuxClient` and its `Plist` codec, used only by the iPhone-over-USB path, see *iPhone over USB*). Both roles call into *both* feature modules, so they live here rather than in a module; only the host branches on the mode (each `HostSession`'s `spec`: a `SessionSpec` taken at the start of each connect attempt from the session's own fixed `choice`, its link and the app-wide display mode), while the client just follows the host's `0xF9` / `0xF8` / `0xF7` packets. `debug/synthetic_tablet.dart` (`FakeTablet`, `SynthAdb`, `SyntheticTablets` and the `synthTabletCount`/`synthTablets` build flag) serves the tests and, in a debug build with `SYNTH_TABLETS`, the app (see *Synthetic tablets* under *Hub and sessions*); no profile or release build contains it.
  - `models/`, `protocol/`, `services/` (logger, settings, translations), `platform/` (`permissions_channel`, `keepalive_channel`, `battery_channel`, `wifi_pairing_channel`), shared `widgets/`.
  - `features/` — mode-agnostic UI shells: `splash/`, `home/` (connection screen, both roles — on the host a card per device with its role chips, and the Add a device panel, whose role chooser picks a new device's role), `settings/` (the host's control surface, with a Tablets card for Maximum tablets and the Encoder line; on the client it shows only language, permissions and info).
- **`lib/modules/extended_screen/`** — the second-monitor streaming pipeline:
  - `host/` — `screen_capture_channel`, `input_inject_channel` (macOS capture + input injection), and `debug/`, the Loopback preview (`/loopback-preview`, debug builds with synthetic tablets only).
  - `client/` — `video_decoder_channel` and the `display/` feature (Android decode + render). Also reused by the remote tab-controls-Mac direction.
- **`lib/modules/remote_screen/`** — the remote-control additions:
  - `host/` — `remote_video_channel` (macOS decodes the tablet stream) and the `remote_host/` feature (the Mac's view of the tablets it controls: `RemoteHostView`, a grid with a `RemoteTile` per session, kept by `RemoteGridController`; see *Session modes and stream direction*), and, apart from all of that, the iPhone over USB: `ios_screen_channel`, `ios_touch_service` and the `iphone_remote/` feature (`/iphone-remote`; see *iPhone over USB*).
  - `client/` — `android_capture_channel` (Android captures + encodes its own screen).
- **`lib/app/`** — app shell: `app.dart`, `theme/`, `routes/`, `bindings/initial_binding.dart`.

Note: because the move was structure-only (no behavior rewrite), the shared connection managers import a couple of module-owned channels (e.g. `HostSession` → `remote_screen/.../remote_video_channel`; `ClientConnectionManager` → `remote_screen/.../android_capture_channel`). These are runtime `Get.find` dependencies whose imports are type-only — a deliberate, acyclic "shared depends on module" edge. `HomeController` → `remote_screen/.../remote_grid_controller` is one more (found only while the remote view is open).

Roles:

- **Host (macOS):** runs `adb reverse`, starts a TCP server, captures the screen via `ScreenCapturePlugin` (Swift/ScreenCaptureKit), encodes with VideoToolbox (H.264 or H.265/HEVC selectable), and streams `FRAME_DATA` packets. Injects touch/mouse/key events received from the tablet via `InputInjectPlugin`.
- **Client (Android):** dials into the ADB-reverse tunnel, decodes H.264/H.265 frames (via `VideoDecoderChannel`), renders them in `DisplayView`, and forwards user input back as packets.

### Session modes and stream direction (`lib/shared/models/session_mode.dart`)

Three host-chosen enums decide which pipeline runs, per session: the mode and direction are the session's own `choice` (a `SessionChoice`, given when the hub makes it and fixed for its life; see *Hub and sessions*), the display mode the app-wide setting. The persisted `session_mode` / `remote_direction` are, on the host, only the role a new device gets when nothing else says (`SettingsService.nextChoice`, the role chooser's last pick); nothing running follows them. The client never chooses; it learns the mode from the host's `0xF9` (and stores it in those same two settings, on its side).

| `SessionMode` | `RemoteDirection` | Video flows | Capture source | Input path |
|---|---|---|---|---|
| `extendedScreen` | (unused) | Mac → tablet | `DisplayMode` setting (Extend or Mirror) | tablet packets → `InputInjectPlugin` (CGEvent) |
| `remoteControl` | `tabControlsMac` | Mac → tablet | always Mirror (the session's `spec.displayMode`, forced by `SessionSpec.from`) | same as above |
| `remoteControl` | `macControlsTab` (USB only) | tablet → Mac | Android MediaProjection | `HostSession.sendRemoteTap/Swipe` (called by that tablet's tile of the remote view, `RemoteTile`; the hub's methods of the same name go to the focused session and nothing in the app calls them) → `AdbService.inputTap/inputSwipe` → the tablet's input shell, one long-lived `adb shell -T` per serial fed an `input tap …`/`input swipe …` line per event (no packets; see the `AdbManagerPlugin.swift` row). They go to the session's own `serial`, and only from a reverse-remote session the hub has not ended, whatever its phase: input travels through adb, so it keeps landing while the link reconnects. The session's teardown ends the shell (`closeInputShell`), so each attempt's first tap opens a new one |

The last row is "reverse remote" (a session's `spec.isReverseRemote`; `SettingsService.isReverseRemote` says the same of `nextChoice`, and of the mode the client was told), the only case where the tablet encodes and the Mac decodes. It needs adb for its input, so over Wi-Fi a session's direction is always `tabControlsMac` whatever it was made as (`SessionChoice.effective`; the saved choice is kept for USB), and `0xF9` carries the effective direction. `HostSession` branches on its `spec`, and on the tablet `HomeController` on the settings getter (the host's Home never reads it: it goes by `reverseActive`, below); `ClientConnectionManager` does not: it only stores the mode from `0xF9` and handles `0xF8`, `0xF7` and `0xFF` with no mode check. The host sends `0xF8` with codec/fps/bitrate, the client raises `needsScreenShare` and waits for the user to tap "Start screen sharing" on Home (MediaProjection consent has to be user-initiated from the foreground), then streams `FRAME_DATA` to the Mac, which decodes into a Flutter texture (the session's `remoteTextureId`, which its tile of the remote view shows; the hub's `remoteTextureId` mirrors the focused session's). The host's `onTeardown()` sends `0xF7`, so a Disconnect or a settings reconnect ends the capture and the next session needs the tap and the consent again. That `0xF7` is best-effort: if the link is already dead it never arrives, the client's `onLinkLost()` stops nothing, and the capture runs on into the tablet's next session. When that one is reverse remote too, it carries on with it: `0xF8` raises `needsScreenShare` only while `isScreenSharing` is false. Every other session (Extended, tablet controls Mac, any Wi-Fi one) sends `0xF7` itself, in `connect()` after the HELLO wait and before its pipeline starts (`_sendStopCapture`; once per attempt, so also when the capture start fails or the encoder refuses the tablet, and never for a capture rebuild): a tablet's mode changes by a new session (the card's menu on a session in `error`, a tile pressed with the Add panel on another mode), and without it the tablet went on encoding and sending its screen, which the Mac dropped, while it ran as a second screen, with Home showing its sharing button in place of Open View. With no capture running that `0xF7` only takes back a "Start screen sharing" offer the dead session left. The tablet's encoder asks for a keyframe every second (`KEY_I_FRAME_INTERVAL = 1` in `ScreenCaptureService.kt`), but those keyframes come with its frames: on a still screen the next one was measured over a minute away. That matters when a capture outlives its session (above): the next session's new Mac decoder gets only pictures it cannot start from, and its view stayed black. So `_startRemoteReceive()` sends `0xFF` right after `0xF8` (through `_sendToClient`, since base `requestIdr()` needs an active phase and the session is still `configuring`), and the Mac's decoder asks again, at most once a second, while it is fed pictures it cannot decode (see the `0xFF` row). Neither makes a still tablet produce a frame: the picture appears with the tablet's next frame.

**Tablet screen off (reverse remote only).** Each tile of the remote view has a toggle of its own, which calls its session's `HostSession.setTabletScreenOff` (`HostConnectionManager.setTabletScreenOff` still hands a call to the focused session; no UI uses it any more). That works only in a live USB reverse-remote session once the tablet's first `FRAME_DATA` has arrived (`tabletStreaming`; before that its user still has to approve capture), remembers the choice per tablet once it has worked (`SettingsService.tabletScreenOffFor(serial)`, key `tablet_screen_off.<serial>`; on is saved at once) and applies it again in the next session once its first frame has arrived and it is live, whichever comes last (`_darkenTabletIfChosen`, also run by a phase worker: a capture left running from the last session can send frames during `configuring`). One call at a time: `changingTabletScreen` covers the toggle and the remembered choice alike, and a call that finds `_tabletScreenSeq` moved on (teardown bumps it) changes nothing. On the Swift side a second hold for a serial whose hold is still starting gets that hold's answer, not `true` at once, and a release answers a hold still starting with `SCREEN_OFF_CANCELLED`. `AdbService.holdTabletScreenOff` → `AdbManagerPlugin` runs `ScreenPower` (`android/.../tools/ScreenPower.kt`) from the installed APK with the shell's privileges: `adb shell -T "CLASSPATH=$(pm path …) exec app_process / …ScreenPower hold"`. It turns every physical display's panel off with the hidden `SurfaceControl.setDisplayPowerMode` (tokens from `SurfaceControl`, or on API 34+ from `DisplayControl`, loaded with the whole `SYSTEMSERVERCLASSPATH` as scrcpy does since 3.1: with `services.jar` alone `libandroid_servers` aborts the process on some vendor ROMs). Everything is found before the panel is touched, and a helper started on a sleeping tablet refuses: SurfaceFlinger stops lighting the panel while PowerManager and DisplayManager still see an awake, ON display, so MediaProjection keeps getting frames (measured: `screenrecord` still produced frames 14 s into an idle period, at about 60 fps) and `adb shell input` still lands. Don't use DisplayManager's `requestDisplayPower` or `cmd display power-off` instead: those turn the logical display off and mirroring freezes (scrcpy #5530). Three things keep the panel from staying dark: the Mac renews a lease every 2 s (`keep` on the helper's stdin) and the helper lights the panel after 10 s without one (killing the Mac's adb client does not close the helper's input); adbd kills the helper outright when the Mac's side goes away, so before going dark it starts a watchdog (`ScreenPower watch`, `setsid`, fed `1`/`0` over a pipe) that lights the panel when that pipe ends with it off, and waits up to 5 s for its `ready` (said once it has found the panel itself), so no panel goes dark without one; and every path ends in `System.exit` (a process that loaded `libandroid_servers` crashes on a normal exit). The panel is only lit again while PowerManager says the device is interactive (lighting a sleeping one leaves it black, scrcpy #1667): `Panel.lightWhenAwake` waits up to 5 s for an asleep tablet to wake, because Android does not relight a panel after a sleep that short (its own switch to off never happened, so its wake switches nothing on: measured, a 0.3 s sleep left the tablet awake and dark), while after a longer one its wake-up lights the panel. While held, the helper reports `IPowerManager.userActivity` every 4 s, or the device idles and the mirror can go black. `onTeardown()` releases it; an unasked end (lease, cable, crash) comes back as `onTabletScreenRestored`, which the hub routes by serial to that session, clearing its `tabletScreenOff`. The helper changes no setting, so nothing outlives it. The physical power button puts the tablet to sleep, and on Android 16+ the lock screen that follows stops MediaProjection, so the capture ends too. The helper checks every 100 ms that PowerManager still reports interactive and that the lock screen has not appeared (and the last wake-up time, where `IPowerManager.getLastWakeup` exists; this Samsung build has none), so two quick presses are seen as well; it then ends, lighting the panel as above, and the Mac hears `onTabletScreenRestored`. `proguard-rules.pro` keeps `com.example.extendedscreen.tools.**`, which nothing in the app references, from R8, and the class suppresses the non-SDK-interface lint, which is about an app's own process.

Navigation follows the mode (`HomeController`): the client auto-opens `/display` once the link is active, except in reverse remote where it stays on Home; the host stays on Home as the capture source and only auto-opens `/remote-host` when the first tablet the Mac controls goes live (below). The client's phase listener runs as it sets `streaming`, right after sending HELLO and before this session's `0xF9` arrives, so it sees the previous session's mode: on a switch into reverse remote it pops `/display` once `0xF9` lands, but on a switch out nothing opens `/display` until the user taps "Open View".

On the host, Home opens `/remote-host` from the count of live tablets the Mac controls, `BaseConnectionManager.reverseActive` (the hub keeps it over every session, see *Hub and sessions*), not from the phase the hub shows or from `nextChoice`: an `ever` worker pushes the route when the count leaves 0 while the current route is `/home`, and when Home is made with the count above 0 (the launch can connect before Home exists) a post-frame callback does the same if it is still above 0 then. So a second such tablet opens nothing (it gets a tile in the view), an Extended tablet or one that drives the Mac going live opens nothing whatever `nextChoice` reads, a tablet whose link drops and comes back alone opens the view again as it always did, and nothing opens over Settings. `HomeController` reads only that `RxInt`, so this works over a plain `BaseConnectionManager` (`host_launch_test.dart`). A card's Open remote is `onOpenRemoteView(key:)`: it pushes the route with `{'focus': key}` and does not touch the hub's focus; called while `/remote-host` is the current route it pushes nothing and only asks the view's `RemoteGridController` to `expand(key)`. `HomeController` imports that controller for this, one more shared-to-module edge.

**The remote view (`/remote-host`).** `RemoteHostView` is a grid of the tablets the Mac controls, one tile per session in `hub.remoteSessions`, whatever its phase; a tablet the Mac extends onto or one that drives the Mac gets none. `RemoteGridController` (put by `RemoteHostBinding`) keeps `tiles`, an `RxList<RemoteTile>` in key order which a worker on `hub.sessions` rebuilds: a tile is kept while its session is the same object, so a new session under the same key gets a new tile (the tile widgets are keyed `tile/<key>/<nativeId>`). `RemoteTile` (`controllers/remote_tile.dart`, a plain class over one `HostSession`) reads only that session: its shape is `session.panel` (16:10 if that is empty), never the app-wide panel; its name the device's model, else the key; its picture `session.remoteTextureId`; its latency, notice and screen toggle that session's own. Nothing under `lib/modules/remote_screen` reads the hub's focused-session mirrors or `clientPanelWidth/Height`.

- **Pointer.** Each tile's picture has its own `Listener`, which normalises against its own box, and the tile keeps where each pointer went down by `PointerEvent.pointer`. A release clamps to the picture and is a tap (moved under 0.012) or a swipe through `session.sendRemoteTap/Swipe`; a release of a pointer that did not go down on that tile sends nothing (it used to be a tap), and a cancel forgets the pointer. Flutter delivers a pointer's later events to where it went down, so a drag that ends over another tile is a swipe to the first tile's edge. The `Listener` is built over the texture only, so a tile with no texture takes no pointer: a lost link's teardown takes the texture away, and it is back once the next attempt has made its decoder (during `configuring`, while the tile still says reconnecting). `HostSession.sendRemoteTap/Swipe` ask no phase, so from then on the taps land, and so does the release of a press that was already down when the texture went (Flutter still delivers its up).
- **A tile's picture** is an `Obx` over its session: the texture in an `AspectRatio` once there is one (drawn through `RemoteHostView.textureBuilder`, by default `Texture`; a widget test passes a box, since it has no texture registry), `remote_host_waiting` over it until `tabletStreaming` (unless the session has a `notice`), `remote_tile_reconnecting` while the phase is not active, and the `notice` translated at the bottom. The overlays ignore the pointer. The status box (spinner and text) is laid out at the tile's width inside a `FittedBox(scaleDown)`, so a tile too short for it (three or more tiles in a window under about 460 px high) draws it smaller instead of overflowing.
- **Controls** (`_TileControls`, an `Obx` over the session; keys `tile/<key>/screen`, `/reconnect`, `/disconnect`, `/expand`): the latency chip, the screen toggle only while that session's `tabletStreaming` is true (the button inside is keyed by what a press would do, `tile/<key>/screen/on` or `/off`, so a panel that changes under a finger makes the press do nothing), Reconnect (`hub.reconnectSession(key)`, only while the tile's session is still `sessions[key]`, as for Disconnect), Disconnect and, in a grid, Expand. In a tile's own bar the controls sit in a `FittedBox(scaleDown)` capped at the bar's width (the name takes what is left), and in the one-tile layout in what the view's bar has left, so a narrow window draws them smaller instead of overflowing; the view's own bar (Back, its title, the strip's Show all) does not shrink. The one-tile layout's controls are outside the keyed tile widget, so they are keyed themselves, `controls/<key>/<nativeId>`: a new session under the same key replaces the buttons, and a press held across the change does nothing. Disconnect is `hub.disconnectSession(key, userStopped: false)`, unawaited, and only while the tile's session is still `sessions[key]`; then, in the same synchronous step, the route is popped if `hub.remoteSessions` is empty and the current route is `/remote-host` (`Get.back(closeOverlays: true)`: a plain back would only close an open snackbar). So the view closes with its last tile before that session's teardown is done, and nothing is paused or stopped: the next resume or Home focus connects the tablet again, as after the old view's Disconnect. Nothing else pops the route: tablets ended from elsewhere leave `remote_grid_empty` and Back.
- **Layout.** A bar with Back (`grid/back`) in every state. No tile: `remote_grid_empty`. One tile: the picture fills the window and the bar floats over its top carrying that tile's controls with their labels, as the single-session view was laid out. Two tiles side by side, three or four in a 2×2 grid, each with a bar of its own (name, icon buttons with tooltips). Five or more: a two-column grid, two rows to a window, that scrolls (`RemoteGridController.gridScroll`). A press or drag on a tile is that tablet's, so the grid takes no pointer drag: its `ScrollConfiguration` leaves only the trackpad in `dragDevices` (a two-finger scroll is no press), and the wheel and an always-shown interactive `Scrollbar` do the rest. It does not use `NeverScrollableScrollPhysics`: `RawScrollbar`'s thumb drag and track tap, and `Scrollable`'s wheel handling, all return when the physics take no user offset (checked: the thumb moved nothing).
- **Expanded.** `expanded` (an `RxnString`) is the key of a tile shown alone at full size, with a strip of the other tiles' names in the bar (`strip/<key>`, each expands that one) and Show all (`grid/show_all`, `remote_tile_show_all`). `expand(key)` does nothing unless there are two or more tiles and the key is one of them; the route's `{'focus': key}` argument goes through it when the view opens, and it clears when its tablet goes or one tile is left.

Inside `/display` (`display_view.dart`), the HUD bar shows for 4 s, then collapses to `_HudHandle` (a 64×48 hit area at the top centre, below any cutout via `SafeArea`) that brings it back; touches elsewhere fall through to `_TouchOverlay`. The host's `showHudOverlay` (`0xFA`) only hides the bar's stats: Back and Disconnect are always there. `_ReconnectingOverlay` (phase connecting or `error`) takes every tap and has Back (`Get.back`: the client keeps redialling and Home's phase listener reopens `/display` when the link is active again) and Disconnect (`DisplayController.onDisconnect`). Its text is one neutral `display_reconnect_hint`, because the client cannot tell a host settings restart from a lost link.

### Link types (`lib/shared/models/link_type.dart`)

`LinkType { usb, wifi }` is how the two sides reach each other. Unlike the session mode it is not negotiated: each device persists its own (`SettingsService.linkTypeRx`, picked on Home), the host deciding how it listens and the client where it dials. The client's `connect()` reads it once at the start and keeps it in `_wifiSession`; on the host the hub reads it when it connects and makes a session for that link, whose `link` is fixed for its life (a change while that session waits to retry ends it and connects on the new link, `_onLinkTypeChanged`).

- **USB** is everything described elsewhere in this file: `adb reverse` and plain TCP on loopback. The tunnel is not the trust boundary, adb is: each session's two ends prove to each other that they hold a key that only adb could have given the tablet app (see *A USB session authenticates in both directions too* below).
- **Wi-Fi** uses no adb at all. The host skips `detectingDevice`/`portForwarding` and goes `handshaking` (TLS server on every interface, `SocketService.startSecureServer`, plus the UDP discovery responder) `→ configuring → streaming`. `activeDevice` is a `DeviceModel` whose serial is the tablet's address; `setLastDevice` is not called.

**Pairing is over USB, through adb itself, and has no user step** (`WifiPairingService`). The host owns a `WifiIdentity`: a 16-byte host id, a 32-byte random token, and a self-signed RSA certificate made by `/usr/bin/openssl` on first use (a failed generation is retried on the next call). After every USB session reaches `streaming` (a synthetic tablet's excepted), `HostSession._offerWifiPairing()` takes the pairing payload from `WifiPairingService.offerPayload()` (the identity, `macDisplayName()` and the Mac's current IPv4 addresses, `WifiDiscoveryService.lanAddresses()`; the iOS spike's devicectl delivery uses the same bytes) and gives it to `AdbService.deliverWifiPairing`, which runs `am broadcast -n com.example.extendedscreen/.plugins.WifiPairingReceiver -a com.example.extendedscreen.WIFI_PAIR --es payload '<base64url>'` in the device's shell:

- The command reaches `adb -s <serial> shell -T` on stdin (`AdbManagerPlugin`'s `shellScript`, the pipe filled before adb starts), not in its arguments: the payload holds the token, and every process on the Mac can read another's arguments.
- The manifest guards the receiver with `android.permission.DUMP`. The shell holds it; an installed app cannot, short of `adb shell pm grant` (androidx.profileinstaller guards its receiver the same way). So only adb can deliver a pairing, and `-n` means only this app receives one.
- `WifiPairingReceiver.kt` passes the bytes to Dart on `extended_screen/wifi_pairing` (`WifiPairingChannel`, registered on Android only), which calls `storePairing`. Dart's answer becomes the broadcast's result code (1 stored, 2 refused, 0 nobody took it: no engine running, or a build without the receiver); `am broadcast` prints it and `AdbService.broadcastResultCode` reads it into an `AdbDelivery`, which for a pairing the host only logs.

The name in the pairing, and in discovery replies, is `macDisplayName()` (`lib/shared/platform/host_name.dart`): the Computer Name from `/usr/sbin/scutil --get ComputerName`, else the first label of `Platform.localHostname`, cut to 64 UTF-8 bytes between characters. `Platform.localHostname` alone is whatever the current network calls the Mac (a VPN's reverse-DNS name, for one), so don't show it. The tablet shows the name it stored (`PairedHost.name`), which changes only when the next USB session pairs again.

The client stores a `PairedHost` (replacing one with the same id, keeping its `lastAddress`). `storePairing` refuses one that names an already paired host id with a different certificate or token (ids are public, and a real Mac creates all three together), and drops loopback, zero, multicast and broadcast addresses from the list. Identity and pairings live in `SharedPreferences` (`wifi_*` keys), not in `flutter_secure_storage`.

**Nothing that arrives on the link can pair.** The pairing used to travel as a `0xF6` control packet on USB sessions, which trusted the socket in both directions, and neither end knows who is on it. The tablet's "USB session" is whatever answered on its own `127.0.0.1:7001`: adb while a Mac has its tunnel up, any app on the tablet the rest of the time (the client redials every 5 s). The host's USB peer is whatever on the tablet dialled the tunnel first, and it would have been sent the token. So the host never puts a pairing on the socket, `ClientConnectionManager.onRolePacket` ignores `0xF6` on every link (don't reuse the byte), and `storePairing` must never be called with bytes that came from a packet. The session itself no longer rests on the socket either (next but one paragraph). Host and client are separately installed builds, and an old one on either side simply never pairs (the new host's broadcast finds no receiver; the new client ignores the old host's `0xF6`); pairings stored by earlier builds stay valid.

**Unpairing.** On the tablet, each paired Mac has its own row in Home's `_WifiClientCard` with a Forget button: after `showConfirmDialog` (`lib/shared/widgets/confirm_dialog.dart`) it calls `HomeController.onForgetHost` → `WifiPairingService.forget(id)`, then restarts a pending Wi-Fi dial (`_redialClient`, which leaves a stopped tablet stopped). On the Mac, Settings → Wi-Fi → Reset Wi-Fi pairing (host only, also confirmed) calls `BaseConnectionManager.resetWifiIdentity()`, a no-op on the client. The hub's override runs `WifiPairingService.resetIdentity()`, which removes the four identity preferences and the memoised identity (a reset waits for a creation still in flight, and `_loadOrCreateIdentity` waits for a reset in flight, so neither can bring the old identity back), then each session's `identityWasReset()`. There, if a Wi-Fi attempt or session is up, the session does `disconnect()` and an unawaited `connect()` of its own, because the TLS server still presents the old certificate and a connected tablet got in with the old token; a live USB session carries on and is handed the new identity at once (`_usbSessionSeq`). It does not go through `SettingsController`'s debounced `reconnect()`. There is one token for all tablets, so the Mac cannot revoke a single one, and a tablet keeps its entry for the old identity until it is forgotten there (after pairing again it lists the Mac twice).

**A Wi-Fi session authenticates in both directions.** The client dials with no trusted roots, so every certificate goes to `onBadCertificate`, which accepts only one equal to a paired host's DER (`WifiPairingService.hostForCert`), and it checks the peer certificate again after connecting. Its first packet is `0xF5` with that host's token. Anything on the network can complete the TLS handshake with the host, so the host treats a client as a stranger until that token passes `WifiIdentity.tokenMatches` (constant time), and the trust belongs to the connection, not to the session: `SocketService.connectionId` changes whenever a socket is installed, the host stores the id that authenticated in `_authedConnection`, and its `peerTrusted` is `_authedConnection == socket.connectionId`, on both links (a USB client earns it differently, see below). The server accepts whoever dials next the moment a client drops, before teardown has run, so a flag would let that newcomer inherit the previous client's standing. Both directions go through it:

- **Inbound:** `BaseConnectionManager._handlePacket` calls `admitPacket()` before anything else, heartbeats included. The host's override admits nothing from an untrusted peer and only looks at the one packet that can earn trust (`0xF5` over Wi-Fi, `0xF4` over USB), once per connection: no HELLO, no input, no pong. Until `SocketService.trustPeer()` the client may not even announce a payload over 1024 bytes (`_dropPeer`).
- **Outbound:** every packet the host sends goes through `_sendToClient()`, and `_forwardFrame` returns unless `peerTrusted`. Never call `socket.send` from the host directly: a capture can still be running, or just starting, when the socket already belongs to someone else.

`connect()` waits 3 s for the token and otherwise throws `LinkError('error_wifi_unpaired_client')`, which goes through `handleLinkFailure()` like any failed attempt (re-listening after 1 s). A TLS handshake that fails on the server is only logged; it must not reach `packetStream` as an error, or a port scan would tear down a live session. What a machine on the LAN can still do is get in the way: hold the single client slot for those 3 s, answer discovery with garbage, or keep idle connections open (`SecureServerSocket` has no handshake timeout). On the tablet, a TLS dial that times out (`SocketService(tlsDialTimeout:)`, 8 s) cannot be closed, because dart:io offers no way to abort a handshake: it stays open until the peer closes, so a peer that accepts and stays mute costs one socket per retry.

**A USB session authenticates in both directions too** (`UsbSessionService`). A port says nothing about who is on it. The host's USB peer is whatever dialled its session's loopback server: any app on the tablet, through the tunnel, or any process on the Mac, directly (the port being that session's own says which tablet the tunnel came from, not who dialled it) (which used to get the screen and injected input without either macOS permission). The tablet's peer is whatever answered on its own `127.0.0.1:7001`: adb while a Mac has its tunnel up, any app the rest of the time. So every USB attempt has a key, and it travels through adb, like a pairing:

- **Made and delivered by the host.** In the session's `connect()`, once its server is bound (on a port of its own) and `adb reverse` has pointed the tablet's 7001 at it, the host makes 32 random bytes (`_usbKey`) and gives them to `AdbService.deliverUsbSessionKey`: the pairing's broadcast with the action `com.example.extendedscreen.USB_SESSION` and the payload version byte + key. The call is not awaited, because the app can dial before adb has reported. On the tablet `WifiPairingReceiver` → `WifiPairingChannel` (`usbSession`) → `UsbSessionService.accept`, which keeps the key in memory only and fires `arrivals`. The key itself is never put on the socket.
- **Proved, not sent.** The client's first packet is `0xF4`: a fresh 16-byte nonce and HMAC-SHA256(key, client label + nonce) (`package:crypto`). On a hello that verifies, the host's `admitPacket` clears `_usbKey` (one session per key, so a recorded hello opens nothing), records the connection in `_authedConnection` and answers `0xF3`: HMAC-SHA256(key, host label + nonce). It answers only then, through `_sendToClient`, so the host still sends nothing at all to a peer that has not proved itself. The client's `admitPacket` admits nothing until that answer verifies for this connection (`_trustedConnection`), gives the peer one try, and `connect()` waits 2 s for it (`_answerTimeout`, deliberately shorter than the 3 s after which a host build from before the handshake would give up on HELLO and start a capture), otherwise `LinkError('error_usb_unverified_host')`. Only after it does the client send HELLO.
- **Trust is `peerTrusted`, on both roles.** `BaseConnectionManager.peerTrusted` defaults to false; the host overrides it as above, the client with `_trustedConnection == socket.connectionId` (set after the certificate check over Wi-Fi, after the answer over USB). The base uses it for `admitPacket`'s default, for `packetStream` (so `DisplayController` is never fed a frame from an unproven peer), for the input and IDR send helpers and for the heartbeat ping; the client's reverse-capture frames check it too, since that capture can outlive its session. An unproven peer may not announce a payload over 1024 bytes on either side (`startServer(untrustedPayloadLimit:)`, `SocketService.distrustPeer()`), until `trustPeer()`.
- **A key is only for connections dialled after it arrived.** The client reads `UsbSessionService.key` before `socket.connect` and judges that connection by that key alone. A key that arrives later (`_onSessionKey`) makes it drop what it has and dial again at once (`BaseConnectionManager.restartLink()`: a link loss whose retry is immediate, so the keep-alive service is left alone), unless the user had stopped it (`disconnected`) or the dial in flight, or the live session, was made with that very key. Without this rule an app could sit in the middle: it holds port 7001 before any tunnel exists, takes the tablet's dial, closes its listener but keeps the connection, and once the Mac's tunnel is up passes everything on in both directions. With it, a key is used only on a dial that reaches adb, because the host makes the key after its own `adb reverse` and an app cannot bind the port while adb holds it. For the same reason the host must never run `adb reverse` a second time inside one attempt.
- **A hello without the right key does not fail the attempt.** From this app it means the key has not arrived: the app was opened after the host started waiting (its delivery reached nobody, result 0), or a dial and a delivery crossed. The host's `connect()` loops: `SocketService.dropClient()` (closes the client without reporting a lost link; the server keeps listening), delivers the same key again unless the app confirmed taking it within the last second, and waits for the next client, back in `handshaking`. If that delivery is not `stored` it throws `LinkError('error_usb_key_not_delivered')`. Three seconds with no hello at all (a tablet build from before the handshake opens with HELLO), or more than 8 keyless hellos in one attempt, throw `LinkError('error_usb_unverified_client')`. Both go through `handleLinkFailure()`, and the retry makes a new key.

Nothing falls back to trusting the socket. A new host with an old tablet build: the key reaches nobody, the old client's HELLO is not admitted, and every 5 s redial ends in `error_usb_unverified_client` on the Mac while the tablet's display opens and closes. An old host with a new tablet build: no key ever arrives, the old host ignores the keyless hello, the client hangs up after 2 s with `error_usb_unverified_host` and tries again every 5 s; the old host re-listens each time and never starts a capture. What is left: whatever can run adb on the Mac is inside the boundary (it can deliver a key of its own, re-point the tunnel, or read `am`'s arguments in the tablet's shell, where the key is visible to the shell user and to no app); another app on the tablet can still get in the way (dial the tunnel first and hold the single client slot for up to 3 s per attempt); and after the handshake the link is as before, plain TCP that only adb and loopback protect.

**Finding the Mac** (`ClientConnectionManager._findWifiHost`): one `WifiDiscoveryService.probe()` sends `EXTD?` on UDP 7001 to 255.255.255.255, to each interface's /24 broadcast, and directly (`directTargets`) to every address a paired Mac might have: the one typed on Home (`SettingsService.wifiHostAddress`), each `PairedHost.lastAddress`, and each `PairedHost.addresses` entry from pairing. The Mac replies unicast with id, name and TCP port, and the first reply from a paired host id is dialled. The direct targets are what reach a Mac on another subnet (a tablet behind a mesh router doing NAT, as on the development network), and probing them all is why a stale typed address does not hide a Mac that answers elsewhere. With no reply a known address is dialled anyway (UDP can be filtered where TCP is not), a different one on each attempt, starting with the typed one; with no address either it throws `LinkError('error_wifi_host_not_found')`, and with no pairing at all `LinkError('error_wifi_not_paired')` without probing. The typed address is stored through `SettingsService.normalizeHostAddress` (trimmed, a copied `:port` removed, anything that is not an IPv4 address or host name stored as empty). Discovery replies are not trusted: they only say where to dial. `WifiDiscoveryService(udpPort:, broadcast:)` lets tests run it on a free loopback port without broadcasting. Two dart:io behaviours shape `WifiDiscoveryService`, and both have bitten:

- A datagram that can't be sent does not throw: it is reported as an error on the socket's stream, and the socket is closed. So `probe()` gives each target a socket of its own (one unreachable target must not cost the replies to the others), and the host's responder binds itself again 1 s after an error.
- A read handler is called again, from a microtask, for as long as a datagram waits on an open socket. A handler that returns without `receive()`-ing it spins for ever and freezes the whole app, because microtasks run before the event loop gets the turn that would close the socket. On an ordinary network the Mac answers the broadcast, the subnet broadcast and its own address at once, so several of the probe's sockets hold a reply at the moment the first one decides it. `probe()` therefore binds all its sockets before sending, and `finish()` closes every one of them synchronously the instant the probe is decided (first paired reply, or 64 datagrams read); never `await` between deciding and closing. The responder, which must keep reading, handles 32 datagrams and then switches `readEventsEnabled` off until a `Timer.run`, sends at most 20 replies a second, and is stopped as soon as a client authenticates (the next listen starts it again).

**Pacing.** The two TLS entry points put `SocketService` in paced mode: every write goes through a queue and one `flush()` at a time (an `IOSink` rejects `add()` while a flush is pending, so nothing may write to a paced socket directly, and `disconnect()` uses `destroy()` because `close()` throws then). `isCongested` is true when data queued more than 120 ms ago has not been flushed; `sendFrame()` then returns false. `HostSession._forwardFrame` drops frames from that point until the link has drained and `isKeyframeAccessUnit` (`lib/shared/protocol/annexb.dart`, the Dart twin of the Kotlin function) sees a keyframe, asking the encoder for an IDR at most every 500 ms. `_startCapture()` also caps `SO_SNDBUF` (`limitSendBuffer`, macOS only) at 400 ms of the bitrate, re-applied whenever the adapted bitrate changes: room for a keyframe (a smaller buffer, 100 ms as it once was, kept every keyframe on a link near the rate waiting past the congestion limit, so frames were refused), and no more, since the kernel's own buffer would otherwise hide a slow link for seconds and is latency the adapter can no longer cut at its floor. Over USB none of this runs: `sendFrame()` is `send()`.

**Bitrate adaptation (Wi-Fi only).** Dropping frames is the last resort; before that the encoder is fitted to the link. `_startCapture()` ends with `_startBitrateAdaptation()`: a 50 ms timer feeds `BitrateAdapter` (`lib/shared/connection/bitrate_adapter.dart`, pure arithmetic; its class comment is the reference) with the link's queue, `SocketService.unackedBytes` (bytes queued in Dart plus, on macOS, the kernel's `SO_NWRITE`: TCP data the tablet has not acknowledged; `_pump` flushes one packet at a time so a flush under way is not counted twice), taken at its low point (`_queueTrough`, read before each frame write, since a 50 ms timer sits on one phase of a 60 fps frame cycle), less one round trip of stream (`inFlight`: the heartbeat's lowest round trip of the last 30 s, 10 ms until measured, capped at 40 ms; `beginConnect()` resets `latencyMs` so a USB session's round trip is not taken for the Wi-Fi one's). It judges the smallest queue over 400 ms, so keyframe bursts don't count: a standing queue over 30 ms cuts towards 85% of what the link delivered (at most halving per step, one step per 800 ms); a refused frame cuts at once (60%, or towards the delivered rate if the window measured the link); a window in which the link carried next to nothing for 200 ms (a stall, a roam) is not judged at all. It climbs only while the stream used at least 60% of its budget over the last 1.2 s, longer than the 1 s keyframe interval (an idle screen sends little more than a keyframe a second, which fills most of a 400 ms window by itself and proves nothing about headroom), 2 s after a cut, 15% a second up to just below where the link gave out (what it delivered, remembered for 30 s and forgotten once a 5%-per-2 s probe passes it by 15%); never above the preset's bitrate, never below max(2 Mbps, preset ÷ 8). After a refusal `_forwardFrame` resumes only once `unackedBytes` is under `_resumeBelow` (~30 ms of stream): resuming with the kernel buffer still full got the resuming keyframe refused in turn. A change goes to `ScreenCaptureChannel.setBitrate` → `ScreenCapturePlugin.swift`, which leaves it in `requestedBitrate` for the timer thread to apply (`kVTCompressionPropertyKey_AverageBitRate`) before its next encode: no new session, no keyframe. The host's Home chip shows the current rate (`BaseConnectionManager.streamBitrate`, null on the client and over USB). `_stopBitrateAdaptation()` is synchronous and runs before the first await of `onTeardown()`, again inside its `_exclusive` block, and in a rebuild's `stopPipelineOp()` (the rebuilt encoder starts at the preset again); `adaptingBitrate` is the test hook. `test/bitrate_adapter_test.dart` drives the adapter, partly through a fluid model of a link with the host's send buffer, refusal and resync and an encoder with quarter-second keyframes, busy or idle (`simulate`); `wifi_link_test.dart` runs host and tablet through `_SlowLink`, a clock-paced leaky bucket on a `RawSocket` (a tick the isolate runs late must not slow the link), with `_Encoder` keeping its average around 250 ms keyframes and starting its GOP again on a forced keyframe. On a link near capacity the rate does not sit still: it moves in a band mostly below the link, because a keyframe's backlog drains only at what the link has to spare, with now and then a probe a step above. The tablet, for its part, holds a low-latency Wi-Fi lock while a Wi-Fi session streams (`KeepAliveChannel.setLowLatencyWifi`, `WifiLatencyLock` in `ClientKeepAlivePlugin.kt`), so its radio doesn't doze between frames.

Home (`home_view.dart`) is two bodies: `_ClientBody`, the tablet's, and `_HostBody`, which takes the manager as the hub (`HostConnectionManager`; there is no host layout over a plain manager). The app bar shows `app_name` alone on both, a plain `Text` never in an `Obx`; the host's actions are the Loopback preview's grid (debug builds with synthetic tablets) and Settings (the old phone `IconButton`, `home/iphone-remote`, is gone: an iPhone has a card). The host body is one `Obx`, a `ListView` that reads every session's phase and grant (the facade follows only the focused one), the hub's map, focus, device list, `endingAll`, `heldPlaces`, `capacityChanges`, `listening` and `wifiTurnedAway`, the settings' `deviceProfiles`, `codecRx` and `wifiListenRx`, and the controller's addresses, iPhone list, refresh flag and missing permissions, and passes every widget below plain snapshots. Whatever the link, it lays out: the permission banner; `_DevicesHeader` (`home/devices`, `home_devices`) with a summary line (`home/summary`) while any session exists, any place is held or any session has a `granted` capture: `home_devices_connected` (the live sessions), then `home_devices_at_cap` once `hub.heldPlaces` (USB sessions whatever their phase, a refused one too, a tablet between two sessions, and every device on Wi-Fi) reaches `cap`, and, while capturing, `home_encoder_load` (`budget.load`, codec); a `DeviceCard` (`lib/shared/widgets/device_card.dart`, keyed `session/<key>`) per session, sorted by key; an `IphoneUsbCard` (`iphone-usb/<id>`) per iPhone or iPad plugged in over USB (below); with no card at all `_EmptyState` (`home/empty`, `home_empty`: plug a device in, or turn on Wi-Fi below; `home_empty_wifi_on` instead while `wifiListenRx` is on, which it reads) when nothing is free to add and no tablet is between two sessions, else `home_none_connected` (`home/none-connected`); then the Add a device panel, `AddDevicePanel` (`home/add`, `lib/shared/widgets/add_device_panel.dart`). There is no mode, direction or link selector on the Mac's Home any more: what a device is for (its role) is chosen on its own card, or in the role chooser when a new device is connected. The host's old Wi-Fi body (one listening session through the facade, its selectors and address card) is gone with them: only a Mac whose saved link is Wi-Fi reached it, and `InitialBinding` runs `migrateHostLinkToListen` before the hub exists, so the app never showed it; such a Mac now gets this same body, and nothing was added to Settings for it. Nothing on Home calls the hub's `connect()` without a serial any more, so the facade's "No ADB device detected"/`_lookAgain` state is not drawn either; the empty state says what to do instead.

A `DeviceCard` is an `InkWell` whose tap focuses its session (`HomeController.onFocus` → `hub.focus`; with several sessions the focused one, `hub.focusedKey`, has an accent border), with its own `Obx` over that session alone (and the settings its codec follows). Its top row: an icon by kind (`phone_iphone` for an iPhone HELLO or a Wi-Fi device named iPhone, `tablet_mac` for an iPad, else `tablet_android`), the name (the model, an iPhone's from its HELLO; else `session_wifi_beside` for a Wi-Fi device, else the key) with one status line under it after a coloured dot: `link.chipLabel`, over Wi-Fi the device's address, over USB the serial when another card or row shows the same model (`showSerial`, which Home works out over the sessions' and free devices' models, so two Tab S10 Ultras can be told apart), then while live the encoded size from `granted`, the announced fps, the round trip in ms, the Wi-Fi bitrate (as `LatencyChip` formats it) and `home_status_shared` when the encoder is shared; otherwise plain words, never a protocol step (`DeviceCard.statusFor`): `home_status_waiting_app` in `handshaking` (waiting for the device to dial in), `home_status_connecting` in the other connecting phases, in `error` `home_status_waiting_you` ("Press Retry to try again") for a refused session (no retry armed) or `home_status_retrying` with `retryPending`, else `home_status_not_connected` (the status words begin with a capital in English; units and link names untranslated, as elsewhere; two lines at most, then an ellipsis); and its one action, a `TextButton` keyed `'<key>/<label>'`: Disconnect while live and Cancel while connecting both go to `onSessionStop(key)` → `disconnectSession(key, userStopped: true)`, which stops that device alone and does not pause the auto-connect; in `error` Cancel (the same) beside Retry (`common_retry`), whether no retry is armed (the encoder refused it) or one waits out its backoff (up to 10 s ±20% over USB; Retry runs it now), which goes to `onSessionRetry(key)`, the same permission-gated `_connect(serial: key)` as a pick, which the hub turns into that session's `connect()` (it keeps its own role), so a refused tablet's card, and its place under `cap`, can always be let go. Under it, in plain words, what went wrong (`session_unplugged` for `error_device_gone`, else the `errorKey` translated at build, else `errorMessage`, else the `notice`; computed in build so a language switch reaches it). Then the role chips (`RoleChip`, public in the same file, so tests read `selected`, `enabled` and `hint`), a `Wrap` that takes more lines in a narrow window: `DeviceCard.choicesFor(session)` of `SessionChoice.all`, each labelled `roleLabel` (`role_extended` "Second display for the Mac", `role_controls_mac` "Control the Mac", `role_mac_controls` "The Mac controls this device"), keyed `<key>/role/<mode>.<direction>`. The Mac-controls one is offered only over USB to an Android tablet: never over Wi-Fi nor for an iPhone or iPad (`isApple`), as `SessionChoice.effective` says. The chip of what the session runs as (`sameEffect(effectiveChoice)`) is highlighted and cannot be pressed; the others carry, as their tooltip, what the change asks of the device's user, since the tablet app cannot follow by itself (`DeviceCard.hint`: `session_mode_hint_to_reverse` into Mac-controls-tablet, tap Start screen sharing there; `session_mode_hint_from_reverse` out of it, tap Open View there; both naming the tablet's button by its own label key; else `session_mode_hint_restart`), and can be pressed only while the session is live or in `error` (the hub refuses one on its way to being live), never while `hub.endingAll` (Home then passes no `onRole`), and over Wi-Fi only for a device beside the tablets (`beside`). There is no confirm dialog. A chip's press is a closure built with the chip, so it carries the session the chip was built for, and the chip row is a `KeyedSubtree(ObjectKey(session))`: when the hub replaces the session under the same card key, the chips are new elements and a press that began on the old session's chip does nothing. `HomeController.onSessionMode(session, choice)` returns unless `hub.sessions[session.key]` is still that session, goes through `_ensureHostPermissions()` when `choice.encodesOnMac`, then calls `hub.changeMode(key, choice, expected: session)`. Below the chips, a `Picture settings` `TextButton` (`<key>/settings`, `home_picture_settings`) for a device that can keep a profile (`SettingsService.hasOwnProfile`: not a synthetic tablet, not a `wifi:conn` key) opens `DeviceSettingsSheet`, and in a live reverse-remote session an Open remote button (`<key>/open-remote`, `HomeController.onOpenRemoteView(key: s.key)`, which leaves the focus alone). The two sit in a `Wrap` (`spaceBetween`), not a `Row` with a `Spacer`: the Spacer's share of the row cut Picture settings to an ellipsis beside Open remote at 560 px; when they do not fit side by side Open remote goes onto the next line.

An `IphoneUsbCard` (`lib/shared/widgets/iphone_usb_card.dart`) is outside the hub: it takes no place under `cap` and has no Disconnect (closing its page stops the capture). Its icon is `phonelink` for an iPhone and an iPad alike: the capture device does not say which, and its name is whatever the user called the device. Its status is `USB-C · role_mac_controls`, plus `iphone_remote_touch_ready` or `iphone_remote_touch_off` once touch was tried (`IosTouchService.state` `ready`, or `noRunner`/`noDevice`; `idle` says nothing), read in an `Obx` of its own, only while exactly one iPhone or iPad is listed: the touch service is bound to whichever phone it reached first (`IosTouchService.connect()` with no udid), and a capture device's id is not its UDID, so with two attached no card can say whose touch it is and neither mentions touch; its Open screen button (`iphone-usb/<id>/open`, `iphone_usb_open`) is `HomeController.onOpenIphone(id)` → `/iphone-remote` with `{'id': id}`. The list is `HomeController.iosUsbDevices`, from `IosScreenChannel.listDevices` (no permission needed: the Camera prompt comes with `start`): listed when Home opens, on each resume, and every `iosPollInterval` (2 s; null in tests: only those two) while `/home` is the current route and the app is resumed (`_resumed`, false on `hidden`/`paused`), one listing at a time, the list replaced only when an id or name changed; with no `IosScreenChannel` registered (the client, most tests) there is no timer. `onClose` cancels it.

The Add a device panel has a refresh button (`add/refresh`, a spinner while `refreshingDevices`), a row per `hub.freeDevices` entry (`_AddRow`, keyed `device/<serial>`; no row is tappable, only its button), then a divider and, always last, the Wi-Fi row (`_WifiAcceptRow`, `add/wifi-listen`, see *Listening on Wi-Fi*). A row shows an icon, the model (else the serial), a subtitle (`home_row_plugged_in` or, for an emulator, `home_row_emulator`, then `home_row_last_role` with the role it ran as last, `settings.knownChoice(serial).roleLabel`, or `home_row_new`), the serial too when another row or card shows the same model, a reason in amber when it cannot be connected, and a Connect button keyed by device and meaning (`AddDeviceRow.asksRole`): `device/<serial>/connect` on a remembered device whose remembered role fits the encoder, which connects it in that role (`HomeController.onConnectDevice(device)` → `_connect(serial:, choice: knownChoice)`; `knownChoice` is read non-observably at each build and at the press, which is safe since a tablet's entry changes only while it has a session or is between two, and so is not a row), and `device/<serial>/choose` on a new one, or on a remembered one whose remembered role the encoder has no room for now (`HomeController.fitsEncoder(serial, choice)`: `budget.wouldFit(captureConfigFor(clientPanelFor(serial) ?? lastClientPanel, SessionSpec.from(choice, usb, displayMode: displayModeFor(serial)), profile:))`, always true for a role the Mac only views; the row then says `home_row_role_no_room` in amber, a note, not a reason to disable it), which opens `RoleChooser` (`lib/shared/widgets/role_chooser.dart`: an `AlertDialog` titled `home_choose_role_title`, a full-width tile per `SessionChoice.all` keyed `choose/<serial>/<mode>.<direction>` with `roleLabel` and `roleDescription`, the one preselected (the remembered role, else `settings.nextChoice`) highlighted by `sameEffect` (an Extended `nextChoice` carries whichever direction was saved), a role that does not fit the encoder disabled with `home_row_encoder_full`, and Cancel `choose/<serial>/cancel`, which connects nothing). So a remembered tablet the encoder cannot take as it was is never a dead end: The Mac controls this device always fits. A pick is `onConnectDevice(device, choice:)`, which checks it again first, since the page can change under the dialog (`isFree(serial)`, else `home_row_taken`; `addBlockedReason(role:, serial:)`): refused, a snackbar (`home_connect_refused` and the reason) says why and nothing is connected or saved; otherwise `_connect(..., saveAsNext:)`, which for a new device saves the pick as `nextChoice` (session mode and direction) only once `_ensureHostPermissions()` has passed (a press that ends in Settings changes nothing), then connects with it. A row is disabled (dimmed, its button `onPressed` null) by `HomeController.addBlockedReason()`, the same for every row, unless a pick could go ahead (`canAdd`, or with `cap` 1 the replace of a lone session that is neither connecting nor live, as before; reason `home_disconnecting` while a hub `disconnect()` ends every session, `hub.endingAll`, an observable twin of `_endingAll` that `canAdd` reads too, else `home_row_full` with `@cap` ("… (Settings → Tablets)") when Maximum tablets sets the cap, or `home_row_full_mac` ("This Mac can drive @cap at once") when the cap is below Maximum tablets (`capIsTheMacs`: the encoder estimate's `tabletCap`, which Settings cannot raise; the Wi-Fi row's turned-away line picks `home_wifi_turned_away_mac` the same way)). With no row the panel says `home_all_attached_connected` when sessions, iPhones or a tablet between two sessions exist; with nothing anywhere the empty state above says it. On the client the link selector (`_LinkTypeSelector`, the tablet's only) shows whenever no session is live, and choosing a link or submitting an address restarts the pending dial (`HomeController._redialClient`) unless the user had stopped it. Two rules keep one touch from meaning two things, since a button decides what it does from the state when the finger comes up: nothing may change the phase on pointer-down (the address field's `onTapOutside` only saves), and buttons are keyed by device and meaning (`'<key>/<label>'` on a card, `actionKeyPrefix` on the client's `ConnectionCard`, `device/<serial>/connect` vs `/choose` on a row, the chips under the session's `ObjectKey`), so when the phase, the list or a device's remembered role changes under a finger the button is replaced and the touch does nothing. The rows are keyed by serial for the same reason: the list changes under a finger when a tablet is plugged in or connects by itself, and an unkeyed row kept the press while taking the next device's place. The Wi-Fi row stays last, so a row joining the list moves it down rather than taking its place. The Loopback preview's Start/Stop is keyed by serial and meaning.

### Hub and sessions (host)

The host holds several tablets over USB, up to `cap`, each in a mode of its own (one may extend while another is a remote screen in either direction), and one over Wi-Fi. `HostConnectionManager` is the hub, registered as before (`Get.put<BaseConnectionManager>(HostConnectionManager(), permanent: true)`, so every `Get.find` and `RemoteGridController`'s cast still work). It runs no link of its own (no packet loop, heartbeat or retry). Each tablet's link is a `HostSession` (`host_session.dart`): what used to be the whole host manager, with its own copy of the base state machine (phase, attempt counters, `_recovering`, retry, heartbeat), so cancelling or failing one session never touches another.

- **The hub owns** `sessions` (an `RxMap` by key: the adb serial over USB, `wifi` for the one Wi-Fi session), the focused session, the device list, the app-lifecycle observer (the only one: `detached` ends every session and the device poll, other states go to each session, which applies the base rule with its own `_recovering`, and a resume also runs the auto-connect policy), the one `PipelineQueue`, the one `EncodeBudget` (`budget`, see *Encode budget* below), and the native plugins' single-slot callbacks. It routes those: `AdbService.onTabletScreenRestored` by serial; `ScreenCaptureChannel.onCaptureRestartNeeded` to the session with that native id, or for a wake (null) to every session, or with two or more sessions able to rebuild (`canRebuild`) to its own one-operation rebuild of them all (see *Display modes*); `onDisplayBoundsChanged` to every session; `onFrameRateChanged`, `onCaptureMismatch` and `onCaptureMatched` (the first-frame check of an Extend capture of its own display, and of a Mirror capture of the main display) and `RemoteVideoChannel`'s `onRequestIdr`, `onCodecError` and `onDecoderReady` by native id, to the session's `decoderWantsKeyframe()`, `decoderFailed(code)` and `decoderReady()` (a decoder with a listener of its own, `RemoteVideoChannel.listenIdr(id, f)`, the Loopback preview's, never reaches those slots: its keyframe requests go to its listener, its failure and recovery are only logged). A session never assigns them, and accepts them only from the start of its capture or decoder until its teardown (`_captureWired` / `_remoteWired`, set and cleared where the callbacks used to be assigned and nulled).
- **The facade.** The hub's `phase`, `errorMessage`, `errorKey`, `activeDevice`, `latencyMs`, `refreshRateHz`, `streamBitrate`, `remoteTextureId`, `tabletStreaming`, `tabletScreenOff` and `changingTabletScreen` follow the focused session through `ever` workers (`_focus`). Each is the hub's own Rx for its whole life, because what reads them (Home's `Obx`, tests) holds on to them. GetX notifies synchronously, so after `await hub.connect()` the hub already shows `streaming`. The session a pick connects is focused (`hub.connect` starts its `connect()` first and focuses it in the same synchronous step, so the hub's phase goes straight to the session's connecting one, never through a new session's `disconnected`); `focus(key)` focuses another, and `focusedKey` (an `RxnString`, set in `_focus` and cleared in `_unfocus`) is the focused key for the UI. When the focused session ends, the hub refocuses at once, before anything is awaited: the most recently focused session left (`_recent`, which holds every session: one `changeMode` makes for a tablet that was not the one shown is not focused, so `_replace` puts its key in as the least recent), else any session left, or with none, `disconnected` and no error (`_refocus`; `detectingDevice` instead while a tablet is between two sessions, see *Changing a tablet's mode*), except during a hub `disconnect()`, where it keeps the last values it mirrored until the base sets `disconnected` at the end, as before. `availableDevices` is not mirrored: only the hub's own listings set it (see *Who initiates*), and a session's listing while it connects is its own. The four reverse-remote mirrors (`remoteTextureId`, `tabletStreaming`, `tabletScreenOff`, `changingTabletScreen`) and the hub's `setTabletScreenOff` and `sendRemoteTap/Swipe` are focused-session compatibility: they say nothing about any other tablet the Mac controls, and nothing in the app reads or calls them any more (the remote view goes to each session itself, see *The remote view* under *Session modes and stream direction*); `tablet_screen_off_test.dart`'s hub test and `multi_remote_test.dart` still do.
- **Every tablet the Mac controls.** What is not the focused session's: `reverseActive` (an `RxInt` declared on `BaseConnectionManager`, which the client and a session never set) is the number of sessions in `sessions` with `spec.isReverseRemote` whose phase is live, and `remoteSessions` lists those sessions whatever their phase, sorted by key (it reads `sessions`, so an `Obx` that calls it follows the map, not each session's phase). One worker on `sessions` (`_sessionsChanged`) keeps the count: on every change of the map it drops its phase worker for each session that left (the same key under another object included), adds one for each new session, and counts again, and each phase worker counts again too. So the count is right however a session enters the map (a pick, `adopt`, a test putting one in), and it drops in the same synchronous step in which `_endSession` takes a session out, before its teardown. A session's spec is its attempt's, taken before its phase leaves `disconnected` or `error`, so it is settled when the phase says live. Its phase worker is added when the session enters the map, which is before `_focus` adds the mirrors: when a session goes live, `reverseActive` moves before the hub's `phase` does. The remote view builds its tiles from `remoteSessions`, and Home opens the remote view from `reverseActive` (see *Session modes and stream direction*).
- **The cap.** `hub.cap` is `min(settings.maxTablets, budget.estimate.tabletCap ?? 8)` over USB, whatever the modes (a tablet the Mac only views counts too, though it takes nothing of the encoder), else 1 (the old Wi-Fi link). Devices on Wi-Fi count under it with the tablets (see *Listening on Wi-Fi*). The single (replace) path below therefore runs only over Wi-Fi and with Maximum tablets 1. The cap is applied in one place, the hub's check before a session is made (see *Choosing*). Each session's budget-admission `cap` callback is `max(cap, heldUsbPlaces.length)`, so the budget never refuses, as one tablet too many, a session that holds a place here: one made before Maximum tablets was lowered, the new session (a new native id, so a newcomer to the budget) of a tablet changing mode, or a refused tablet's Retry; the estimate's own `tabletCap` and the encoder's room still can. Handed the bare `cap`, a tablet changed into a mode the Mac encodes under a lowered cap was refused with `error_encode_limit` beside an idle encoder, and so was the change back. `usbSessionCount` counts every USB session whatever its phase (a refused one too); `heldUsbPlaces` is those sessions' keys plus `_reserved`, the tablets whose session is being replaced by `changeMode` (out of `sessions` for a moment, their place still theirs; `replacing`, observable, says there is one); `canAdd` says a pick of a tablet with no session would add one (USB, `heldUsbPlaces` under the cap, no hub `disconnect()` running).
- **A pick's mode** (`connectWith`). Every session the hub makes gets a `choice`, Wi-Fi included, and keeps it. Every connect that picks a tablet (the user's `connect`, the policy's `_start`, a link change's, `_lookAgain`) goes through one overridable seam, `connectWith(serial, {choice})` (public: Home's Add a device panel calls it too) (the base class's default just calls `connect`, so the client and a session are unchanged). Two things do not: `changeMode`, whose `_replace` makes the new session with `_sessionFor` and starts its `connect()` itself (`connectWith` would refuse the key it holds in `_choosing`), and `retryNow`, `reconnect()` and `reconnectSession`, which act on a session that exists. Home's Add a device panel calls `connectWith(serial, choice:)` with the device's role: its remembered one (`knownChoice`) on a known device's Connect, the role chooser's pick on a new one's (`HomeController.onConnectDevice`); a card's Retry passes none (the session keeps its own). `connect({serial})` (the Loopback preview's Start) calls `connectWith(serial, choice: settings.nextChoice)`, the role a new device gets when nothing else says: the last one picked in Home's role chooser. The auto-connect policy's `_start(key)` passes `settings.knownChoice(key)`, the mode the tablet is remembered in (see *Key settings*), whichever rule picked it, and a link change's own connect passes none. A new session runs as `choice ?? settings.knownChoice(key) ?? fallback`, where `fallback` is `nextChoice` read at the top of `connectWith`, before any await (a `nextChoice` changed during a slow `adb devices` does not reach a connect already asked for); `_lookAgain` re-arms with the call's own argument. A session that exists already (a retry run early, a card's Retry, the same tablet with `cap` 1) keeps its own choice and ignores the argument. So `nextChoice` decides only what a device with no role of its own runs as: a known tablet comes back in its remembered mode whatever it says.
- **Changing a tablet's mode** (`changeMode(key, choice, {expected})`, a no-op answering false on the base class). A session never changes what it is, so its teardown undoes exactly what its attempts built: the hub ends it and makes a new one for the same key (`_replace`), with a new native id and, over USB, the tablet's own `vdSerial`. It refuses, answering false, for no such session, one that is not `expected` (the session the caller was looking at), a retired one, a key in `_endingKeys` or `_choosing`, a link change or hub `disconnect()` under way, with `cap` 1 any pick under way, a session that is connecting, and a choice that comes to what the session already runs as on its link (`SessionChoice.sameEffect` after `effective(link)`: over Wi-Fi a direction alone is no change). Otherwise, in one synchronous step with no await: the key goes into `_choosing` (no pick, and no automatic connect, brings the tablet back in its old mode while the old session ends) and, over USB, `_reserved` (its place under the cap is not given to another pick); `_endSession(old, showing:)` starts; and `settings.setKnownChoice(key, choice)` remembers the new mode for a known tablet. Then it waits for the end, makes the new session through `_sessionFor(single: false, choice:)` (which skips the hub's cap check for a reserved key, and the new session's budget cap covers every place held, see *The cap*: a cap lowered under the live count stops nobody), starts its `connect()` and focuses it if the old one was focused or nothing is; otherwise its key goes into `_recent` as the least recent, so the hub shows it when the shown tablet ends (left out, the hub read `disconnected` with that tablet live, and with Maximum tablets 1 a Retry then made a second session for it, which nothing could end). When the old session was the last one the hub shows a connecting phase meanwhile (`detectingDevice`, or `handshaking` over Wi-Fi), never `disconnected`, with any `cap`: with one tablet at a time that is what holds off a pick, and otherwise it keeps the policy's first-run rule from taking the hub for idle, while a tablet is on its way back; if nothing comes back (a `disconnect()` overtook it) the phase is set back. The same holds when another tablet's session, the last one left, is ended while a tablet is between two sessions (`_endSession` shows `detectingDevice` while `_reserved` is not empty), and for as long as `hub.replacing` Home keeps the tablet out of its Add a device rows and does not show the empty state, whatever the phase (a second tablet idle in `error` leaves the facade idle). An await between the sets and the end would reopen both races; `multi_remote_test.dart` pins them. Callers: a card's role chips (`HomeController.onSessionMode`, with `expected`), on a USB tablet or a Wi-Fi device beside them. The tablet app cannot change with this: switched out of Mac-controls-tablet it stays on its Home until its user taps Open View, and switched into it it needs Start screen sharing and the consent again.
- **Choosing** (`hub.connect({serial})`, through `connectWith`). Nothing while a hub `disconnect()` ends sessions (`_endingAll`) or a link change ends them (`_linkChange` in `_choosing`). With `cap` 1 (Wi-Fi, or Maximum tablets 1) and at most one session it is the old single manager's rule: only while neither the hub's phase nor any session's is connecting or live, and one pick at a time (any key in `_choosing`); the one session it retries or replaces is the one in `sessions`, shown or not, and `_sessionFor` never puts a new session over one that is in the map. Otherwise per key: `_choosing` is a set of the keys being picked, from the call until that key's session has started connecting (`_anyDevice` while a pick without a serial looks for a device, then the device it settles on too); a key already being picked, or whose session is connecting or live, is refused, while one in `error` is its retry run early (the user's Retry for a refused one), on the same session and native id. A key still ending (`_endingKeys`) is waited for, then connected anew; `TabletTunnels` orders the two sessions' adb calls. A new key is refused once the other `heldUsbPlaces` reach `cap`, counted after every await, so lowering Maximum tablets under the live count stops nothing and only refuses new ones; the replace path never runs while more than one session exists. Over Wi-Fi the hub uses the `wifi` session. Over USB it takes, in order: `serial`; the focused session's own device (with cap 1 always; otherwise only when it waits in `error`), so a retry run early keeps the session and its native id; the last-used device if attached; the first attached (otherwise only devices with no session and none being replaced, mDNS duplicates dropped). With nothing attached and no session it makes none (one would be fixed to a device that may never come): it shows `error` with "No ADB device detected" and looks again every second (`_lookAgain`), taking whichever tablet appears; with sessions, it just adds nothing. With cap 1, picking another device ends the session there is first, showing a connecting phase throughout (`_endSession(showing:)`), as the old single manager did. An injected test socket goes to one session at a time (`_injectedHolder`, until that session has ended); the others get their own.
- **Ending a session** (`_endSession`) takes it out of reach before anything is awaited: out of `sessions`, unfocused and refocused (the hub resets the mirrored device and reverse-remote values itself), in `_endingKeys` until it has ended, and `retire()`d, so its `connect()` refuses from then on, whoever calls it. Only then come its `disconnect()`, `dispose()` and `ScreenCaptureChannel.disposeSession` in the queue. Without this, a second pick or a pick right after Cancel could take the ending session or make a second one, and the stray session kept capturing after Disconnect. The synchronous refocus is load-bearing for the cap-1 replace: the pick's connecting phase is set there, so the hub never reads idle mid-pick. `disconnectSession(key, {userStopped})` ends one session this way and nothing else: it does not bump the hub's attempt, so another tablet's pick in flight carries on; with `userStopped` the key joins `stoppedDevices`.
- **Each tablet's adb rule** (`TabletTunnels`, in `host_session.dart`): the hub `claim`s a tablet for each new session, a session's `adb reverse` and `--remove` for that tablet run one at a time in order, and only the newest session for a tablet may remove its rule, release its screen hold or end its input shell. A session's counters are its own, so `_abandon`'s `isLatestConnect` cannot see a newer session for the same tablet; without this an ended session whose adb call returned late removed the new session's rule.
- **One device under two adb serials.** A tablet attached by its cable and also by wireless adb (`adb connect <ip>:5555`, `adb tcpip`) is listed twice, under its USB serial and under `ip:port`. Only the mDNS form (`adb-<serial>-…._adb-tls-connect._tcp`) is recognised as a duplicate (`DeviceModel.withoutMdnsDuplicates`); the `ip:port` form is not, so that tablet can be given two sessions, since phase 3 possibly in two modes, whose `adb reverse` rules for the tablet's port 7001 replace each other (adbd keeps one rule per device port), so only one of the two can be dialled. This has been so since several tablets were allowed. Wireless adb is not a supported link (the Wi-Fi link uses no adb), and telling the two apart needs a `getprop ro.serialno` through each transport, which is left for the link work of phase 4. Until then: disconnect the wireless adb transport (`adb disconnect`), or do not pick the `ip:port` entry.
- **The other hub calls.** `disconnect()` ends every session (the base `disconnect()` runs the hub's `onTeardown`). `setTabletScreenOff`, `sendRemoteTap/Swipe` and `adaptingBitrate` go to the focused session (`adopt(session)` focuses one without connecting it, for tests). `reconnect()` (a settings change) runs the base `reconnect()` of every session that is connecting, live or in `error` and not `refused`, in parallel: each the same object, so the same native id, and one waiting out its backoff restarts at once (its `activeDevice` survives the lost link). That rule is `_reconnectWhere(test)`, which two more calls share: `reconnectSession(key)` restarts that one session and leaves the others running, and `reconnectExtendedOnly()` restarts only the sessions whose `spec.mode` is Extended screen, for a change that cannot reach a remote-control session (the display mode: those always mirror). A remote-view tile's Reconnect calls the first; Settings' Extend/Mirror row calls the second (see *Connection lifecycle*). `retryNow(key)` runs a session's pending retry now, only in `error` and not `refused`. `sendUiFlags()` goes to every session. A link-type change does nothing while any session is connecting or live (or a pick or `disconnect()` is under way); otherwise it ends the sessions on the other link and connects on the new one only if one of them had `retryPending` (never for a refused one, which has none), through `connectWith(null)`, so a known tablet comes back in its remembered mode. `connectIfUnambiguous` is overridden by the auto-connect policy (see *Who initiates*). `stoppedDevices` is an in-memory `RxSet`; `allowDevice([key])` takes the key out of it (no key: the `wifi` session over Wi-Fi) and ends the pause that `pauseAutoConnect()` sets (`autoConnectPaused`); `freeDevices` is the device list without mDNS duplicates, devices that have a session and those in `_reserved` (an `RxSet`, so Home's panel follows it); `anyActive` and `anyConnecting` look at every session. The base class has no-op `disconnectSession`, `retryNow`, `reconnectSession`, `changeMode`, `pauseAutoConnect` and `allowDevice`, so shared UI can call them on the client, and its `reconnectExtendedOnly()` is `reconnect()`: anything with one link restarts it.
- **Listening on Wi-Fi** (phase 4). The Mac has no link selector any more: USB always runs, and Wi-Fi is the Add a device panel's last row, Accept devices over Wi-Fi (`add/wifi-listen`, `_WifiAcceptRow`: a `SwitchListTile` whose subtitle says `home_wifi_accept_desc` and where the Mac is, `home_wifi_mac_at` with its addresses or `wifi_host_no_network`, then `home_wifi_not_listening` while on and not yet listening and `home_wifi_turned_away` with a count; `settings.wifiListen`, `wifi_listen`, saved with no reconnect; a Mac saved on the Wi-Fi link is moved to USB with the switch on at launch, `SettingsService.migrateHostLinkToListen` from `InitialBinding`). While it is on over USB (`hub.listenWanted`) the hub runs one `WifiListener` (`lib/shared/connection/wifi_listener.dart`) on `linkPort`: a plain `ServerSocket` on every interface; each connection is upgraded with `SecureSocket.secureServer` under a 5 s deadline (past it the connection gives its pending place back; dart:io gives no way to close a socket it has taken over for TLS, so a mute peer keeps its socket until it leaves, as with `SecureServerSocket` before), at most 4 wait to prove themselves, at most 2 from one address, and live plus pending stay within `cap` + 4 (anything more is destroyed at once, `turnedAway`), and a proven connection must send the pairing token (`0xF5`, 3 s, constant time) then HELLO (3 s) on a `SocketService` that took it over (`adoptClient`, paced, 1 KB until trusted). It also owns the discovery responder, which runs exactly as long as it does (a session's teardown no longer stops it). A proven device (`WifiPeer`: socket, HELLO, `HelloTail`, address) goes to `_onPeer`: its key is `wifi:<install id hex>` when HELLO carried the identity tail (the clients send it from phase 4 on, with the name `iPhone`/`iPad` on iOS and none on Android), else `wifi:conn<n>` (a tablet build from before: a new device on every connection, whose panel is not kept under that key); the same key's stale session is ended first; a key in `stoppedDevices` (a Wi-Fi card's Disconnect, never kept for a `conn` key; turning the switch on again clears them) turns it away, and so does no place left under `cap` (`heldPlaces`, which counts every Wi-Fi session), counted in `wifiTurnedAway` (in that row's subtitle) together with a device the encoder refused (`refused` when its session ends). It is also dropped if its connection went while the hub waited for its stale session to end. Its session (`HostSession(peer:, beside: true)`, `wifiSessions`) takes the socket and HELLO over: `connect()` goes straight to `configuring` with the peer trusted and the HELLO parsed, and lives exactly as long as that connection: a lost link ends it with no retry (`handleLinkFailure` → `onPeerGone` → `_endSession`), and anything that would connect it again (a retry, a settings `reconnect()`, an identity reset) ends it instead; the device redials and gets a new session. Its teardown releases its budget place. Its mode is `knownChoice(key)` ?? `wifiListenChoice` ?? `nextChoice` (kept as it was: a Wi-Fi device dials in by itself, so no chooser is shown for it, and its card's chips change it); a mode change from its card (`changeMode`) saves both and ends the session, and the device comes back in it when it redials (about 5 s). Its display serial: a known device's own, else 1 for an anonymous tablet when no session holds 1 and no known device owns 1 (the one display a Wi-Fi tablet always had; the migrated USB tablet owns 1, and two displays on one serial are one to macOS), else for the first device known on Wi-Fi the serial the earlier single Wi-Fi session had (`vdSerialFor('wifi')`), else an FNV serial; its name `Extended Screen – <tail name, iPhone, iPad or Wi-Fi>`. Once live a tailed device is remembered in `known_devices` (`rememberDevice(…, lastDevice: false)`: never the last-used adb device). A new session is focused when nothing else is. The old Wi-Fi-link path (one `wifi` session with a TLS server of its own) is still in `HostSession`/the hub and still tested, but the app no longer reaches it. Reset Wi-Fi pairing stops the listener first and starts it again with the new identity (it held the old certificate and token). A listener that cannot bind is tried again every 5 s while the switch is on. Not done: standby (a USB session parked while the same tablet is on Wi-Fi, which needs the tablet's app updated to a build that sends the tail), 0xF1/0xF2 (phase 5).
- **A device's own settings** (phase 5). Each device that is the same one next time (an adb serial, a `wifi:<install id>`; never a `synth-*` or `wifi:conn<n>` key, `SettingsService.hasOwnProfile`) can keep a `DeviceProfile` (`lib/shared/models/device_profile.dart`, `device_profile.<key>` JSON): preset, codec, display mode (Extend/Mirror), text size (`divisor` 2, 2.5 or 3: the desktop is panel ÷ divisor points, so larger text and less to encode) and a frame-rate cap (`maxFps` 60, 90 or 120). Every field left null is the app-wide value, so an empty profile is the behaviour before phase 5 (both the iPhone and the tablets default to ÷2 and no cap; the iOS design's ÷3/60 defaults were not adopted, since the owner found ÷2 at 120 good). `captureConfigFor(panel, spec, profile:)` feeds it to `EncodePresetX.configFor(…, divisor:, fpsCap:)`, which computes divisor 2 exactly as before (`panel ~/ 2`, odd panels included) and scales Max's bitrate with the pixels and the capped rate (never under 8 Mbps). A session reads `settings.deviceProfile(key)` for its capture, `displayModeFor(key)` in its spec, `codecFor(key)` for its reverse-remote decoder and `0xF8`, and `presetFor(key)` for the reverse-remote rate; Home's `wouldFit` reads the tile's profile too. The card's Picture settings button (`<key>/settings`, `home_picture_settings`) opens `DeviceSettingsSheet` (`lib/shared/widgets/device_settings_sheet.dart`): each row starts on "as in Settings (value)", a change is saved at once (`setDeviceProfile`, which bumps `deviceProfiles`) and restarts that device alone 350 ms after the last one (`reconnectSession(key)`; a Wi-Fi device ends and redials), and a change still waiting when the sheet closes is applied then. The app-wide Settings stay the defaults for every device without its own value. `reconnectSession` of a session the encoder refused runs its `connect()` (a profile change is the user's, often made to fit). Reverse remote takes its rate and bitrate from the same profiled config (a device's own Custom values, its cap; Max still 60 Hz / 20 Mbps, capped). On a small panel ÷2.5 and ÷3 can look alike: Swift's `hiDPISize` grows any display under 800×525 pt (an iPhone at ÷3, 832×440 pt, comes up about 993×525). Not done: an app-wide change still restarts devices that override it, and Home's encoder line and Settings' Encoder line name the app-wide codec.
- **A session is fixed for its life.** It keeps the same `key`, `link`, USB `serial`, `nativeId`, `vdSerial` and `vdName` through its retries and reconnects, and its `choice` (a `SessionChoice`, final, no setter): the mode and direction every attempt of it runs as, whatever the settings say by then. The hub gives every session it makes one (see *A pick's mode* above); a `HostSession` constructed without one (tests) takes `settings.nextChoice` in its initializer list and keeps that, the one place the mode settings reach a session. A tablet's mode changes by ending its session and making a new one (`hub.changeMode`), never on a live object, so each teardown runs with the spec of the attempt that built its pipeline. `isRetired` says the hub has ended it. `vdSerial` and `vdName` are its virtual display's serial number and name, which the hub gives it when it makes it: over USB `SettingsService.vdSerialFor(key, taken:` the live USB sessions' serials`)` and `vdNameFor(key, model:` the device list's model`)`, so the migrated tablet keeps serial 1 and `Extended Screen` and a new one gets an FNV serial and `Extended Screen – <model>`; over the Wi-Fi link 1 and `Extended Screen`, as every display had before; a Wi-Fi device's is set by the hub from its HELLO (see *Listening on Wi-Fi*), and the USB sessions' `taken` set holds every session's serial. Once the session is live over USB it calls `settings.rememberDevice(serial, model:, vdSerial:, choice:)` with its own `choice` (which also writes `last_device`/`last_device_name`), so a new tablet's serial is saved only then, and its mode each time it goes live. Its retries look for its own device and no other; while it is not listed they fail with `LinkError('error_device_gone')`, also when nothing at all is listed (it was the only tablet), so the device poll retries it at once when it comes back; only a listing adb could not make at all fails with "No ADB device detected". It reads `spec` (a `SessionSpec`: mode, effective direction and display mode, taken at the start of each connect attempt from `_specNow()`: `SessionSpec.from(choice, link, displayMode: settings.displayMode)`, and taken again in `_onHello` with `android: false` when the HELLO names an iPhone or iPad (`isApple`, platform `0x03`/`0x04`), so such a device only ever drives the Mac, and over Wi-Fi gets `activeDevice.model` `iPhone`/`iPad`; before its first attempt, what one begun now would get) instead of the settings' mode getters, and `effectiveChoice` is that spec's mode and direction as a `SessionChoice`, for the UI. It reads `panel` (a `ClientPanel`: this attempt's HELLO, else `SettingsService.clientPanelFor(key)`, else `lastClientPanel`) for the capture config (`SettingsService.captureConfigFor(panel, spec)`), the reverse-remote rate and bitrate (`refreshRateFor(panel)`, `captureBitrateFor(panel)`), the remote texture and remote taps. It is never `Get.put`, so it adds no lifecycle observer and its `onInit` never runs. When the hub ends it, the hub calls `dispose()`, which drops its phase worker, any share of the encode budget and its budget listener.
- **Encode budget.** Every session's capture shares the Mac's encoder through the hub's `EncodeBudget` (`lib/shared/connection/encode_budget.dart`, pure; its class comment is the reference), made with `EncoderEstimate.conservative` and re-estimated from the chip once `hostInfoReady` (`ScreenCaptureChannel.getHostInfo`, at once without the plugin) has it; a new estimate never ends anyone. The hub keeps the `HostInfo` it estimated from in `hostInfo` (an `Rxn`, set after the estimate, so it is the one thing to watch), which Settings' Encoder line shows (`SettingsController.encoderSummary`: the chip if known, the codec, and `budget.capacity(codec)` in Mpx/s, all engines, marked `settings_encoder_measured` once a learned value is above the estimate (`isLearned`), else `settings_encoder_estimated`; a dash without a hub). **Learned capacity.** The estimate was low on the measuring M3 Pro itself (one Tab S10 Ultra ran 2960×1848 at 120 fps with H.265, 656 Mpx/s, with no overload, so Home said `encoder 119%` and a second tablet pushed it to 45 fps), so `budget.capacity(codec)` is max(estimate, `learned(codec)`), and the hub moves `learned` from two signals. Raise: while every admitted session whose encoder adapts (Max, `adaptiveFps`, the only one that reports overload) runs at its ceiling (`granted.fps`, once `captured` is set) for an unbroken `capacityWindow` (10 s; a constructor argument for tests), what they encode is a proven lower bound (`EncodeBudget.provenLoad`; fixed-rate sessions count for nothing, mixed codecs prove nothing), and `raiseCapacity` lifts the codec's capacity just enough that it fits the budget's own rule (total ≤ 85%, the largest session ≤ one engine's share); a proven load never lowers it. A rate granted is not a rate encoded, so the window also needs evidence (`_encodedThrough`): each adapting session's encoder reports once a diag second (`onEncoderStats {session, encoded, captured}`: frames VideoToolbox handed back without error, and SCK frames, both per second), and the window passes only if every adapting session reported, averaged at least 95% of its granted rate encoded, and had SCK frames in at least half of its seconds. Without it a sleep-invalidated encoder (it refuses every frame, so ticks stay on target and nothing is pending: Swift looks healthy) or an idle desktop (the timer re-encodes one frame, the cheapest work there is) taught a lone tablet's 120 fps load for good; a window without the evidence just starts again. The window is a `Timer` restarted by every budget notification and every change of a session's `granted` or `captured` (an `everAll` worker per session, made in the hub's session creation and disposed in `_endSession`), and checked again when it fires; `measuringCapacity` is the test hook, and `encoderStats` feeds the evidence in tests with no capture channel. **Probes.** With two or more adapting sessions every ceiling the rule sets already fits the capacity, so a proven load never passes it and nothing would ever be learned (on the device: AVD first, then the Tab, which stayed at 45 fps for the whole run). So a window that proves a load and teaches nothing starts a probe (`_startProbe` → `EncodeBudget.startProbe`): of the adapting sessions (one codec, two or more), the one below its wanted rate whose next rung up adds the least load and no longer fits the capacity (a rung up that still fits, which stepping the largest demand down can leave, would teach nothing and hold the probe for good) gets that rung as its ceiling, pushed live. Swift's Max encoder climbs to a raised ceiling only after `stepUpDelay` healthy seconds (10 s, doubling to 5 min after a failed step-up), with no `onFrameRateChanged` before that, so the probed session's `granted` stays put meanwhile and no window runs; once it climbs, the next window with evidence proves the higher load and `raiseCapacity` learns it (and ends the probe: anything that works the ceilings out again does). An overload step-down while a probe runs fails it (`_probeFailed`: the ceilings go back, `endProbe`), and so does an encoder that has not climbed by `probeTimeout` (60 s; a constructor argument for tests); the least load a probe failed at is remembered per codec for the run (`_probeFailedAt`), and no probe reaches it again. `probe` is the test hook. Lower: an overload step-down (Swift's `onFrameRateChanged` then carries `achieved`, the ticks/s the encoder managed, which `ScreenCaptureChannel` hands to `onEncoderOverload` just before `onFrameRateChanged`) while two or more sessions are admitted with one codec gives `achievedLoad` (that session at `achieved`, the others at their reported rate, else their ceiling), and `lowerCapacity` brings `learned` down to it, never below the estimate (at or under it, nothing is learned any more); one session alone lowers nothing, since its own ladder looks after it. Either change works the ceilings out again and the hub pushes the changed ones live (`setFrameRateCeiling`, no restart; Max climbs to a raised one as its health allows), saves the value for this chip and codec (`SettingsService.setEncoderCapacityFor`, key `encoder_capacity.<chip slug>.<codec>`, e.g. `encoder_capacity.apple-m3-pro.h265`; nothing for an unknown chip) and bumps `capacityChanges`, which Home's load line and the Encoder line read. Nothing is learned (or probed) while any admitted session is synthetic, or is not one of `sessions` (one being ended). `_loadHostInfo` sets the estimate, then takes each saved value that is above what this run has learned already (`encoderCapacityFor`, which ignores values that can't be a capacity), and pushes every ceiling that changed (the estimate's own changes too, which used to be left unpushed). A learned value can be too high if the window ran on content cheaper to encode than usual; the overload signal is what corrects it. Each session gets it (`budget`, null in tests that build one alone: today's path, no admission) and a `cap` callback (from the hub, never less than the places held, see *The cap*; the default, for a session built alone, is 1). `_startCapture()` admits right after the `stale()` check that follows the permission requests, with no await in between: a teardown that has begun bumped the attempt first, and one that begins later gives the share up before its first await (in `onTeardown()`, next to `_stopBitrateAdaptation`), so a share is never left behind. Giving it up comes in two kinds. `_reserveBudget()` (`EncodeBudget.reserve`): the capture stopped but the session goes on (a teardown for a lost link, a retry, a settings `reconnect()` or `restartLink()`; a capture start that threw): the others' ceilings rise at once and `granted`/`captured` clear, but the session keeps its place, so its next admission is a return: never refused by the cap (a lowered Maximum tablets stops nobody, at their next reconnect or retry either), keeping its admission order, and every other admission meanwhile is planned with the reserved places counted at their floors, so tablets that restart together (a settings reconnect re-admits them in whatever order their handshakes finish) come back as they were and a newcomer cannot take a returning tablet's room. A reservation whose tablet is unplugged holds no room, though: a session whose attempt finds its tablet unlisted (`error_device_gone`) calls `EncodeBudget.suspend` before throwing, and `resume` once an attempt lists it again. A suspended place still counts under the cap but no admission is planned around it, so a running tablet's return (a settings reconnect while the other tablet is unplugged) never comes back at a lower resolution for a tablet that is not there, and the unplugged one, once back, is a return planned beside whatever runs then (past the cap still, possibly at a lower resolution). `wouldFit` counts reservations (a suspended one only towards the cap); `load` and `count` do not. `_releaseBudget()` (`EncodeBudget.release`): the place goes for good, when the hub ends the session (`retire()`, before its teardown, so a pick made while it ends is not planned around it; `onTeardown()` of a retired session; `dispose()`) and when the encoder refuses it (`CaptureLimit` in `connect()`: the user's Retry is a new tablet's admission). It pushes the running sessions' lowered ceilings to their encoders (`_pushCeilings` → `ScreenCaptureChannel.setFrameRateCeiling`, plain unawaited calls, never `pipeline.run`; each encoder answers with `onFrameRateChanged`, so its tablet hears a new `0xFB`), starts with the granted config (the ceiling travels as `fpsCeiling`, never in `refreshRate`, so a raised ceiling can climb back), and announces `0xFB` at min(rate, ceiling). The ceiling it starts with is read from the budget again right before `startCapture` (after the virtual display, with no await in between): another session leaving while the display was made raised it, and Swift's `startCapture` takes its `fpsCeiling` over any `setFrameRateCeiling` that came before it. A rate the encoder reports through `frameRateChanged` once the start is sent (`_reportedFps`, a ceiling raised during the start) is what that `0xFB` says instead. Everything after the admission runs inside a try (`_startAdmitted`): any start that throws reserves (above), so a failed start holds nobody down, its card shows no grant, and the next start, a wake's rebuild included (a stream-stop rebuild that fails has nothing else coming), is a return; an `ENCODER_BUSY` or `NO_ENCODER` becomes `CaptureLimit` only when another session held part of the budget at admission, and a lone tablet's stays the non-fatal failure it always was. `CaptureLimit` (from that or from `admit` itself) is the one pipeline error `connect()` lets through: the session sets `errorMessage`/`errorKey` (`error_encode_limit`) and `refused`, and runs `handleLinkFailure(retry: false)`, whose teardown removes its virtual display and tunnel; no retry is armed, and the next `connect()` (the user's) clears `refused` and admits again. A session's observables for its card: `refused`; `granted` (`GrantedCapture`: encoded size, the rate, updated by `frameRateChanged`, and `shared`, kept current by an `EncodeBudget` listener; null with no capture or no budget); `notice`, a translation key cleared by `connect()` and by each capture start (a reverse-remote start clears nothing, the attempt's `connect()` already has): `error_extend_unavailable` when Extend made no display (`displayId` 0) or `startCapture` answered `fellBack`, `error_extend_wrong_display` from `onCaptureMismatch` (`captureMismatch()`) once the hub's display rebuilds have not cured it, or with no other virtual display (see *Display modes*), `error_mirror_wrong_display` the same way for a capture of the main display (Mirror, every tablet that drives the Mac in remote control included) once the hub's repair rounds have not cured it, or with no virtual display at all, and `error_encode_limit` when a rebuild (the session's own or the hub's wake, both through `rebuildFailed`) fails with `CaptureLimit` or `ENCODER_BUSY`, which leaves the session up, and in reverse remote `error_remote_decoder` while the Mac has no decoder for that tablet's picture: `_startRemoteReceive()` sets it when `RemoteVideoChannel.initialize` answers no texture (it still sends `0xF8`), `decoderFailed()` when the plugin reports `onCodecError` for the session, and `decoderReady()` (the plugin's `onDecoderReady`) clears it, and only it, never another notice. A rebuild re-admits the same id while it is still admitted (rule 0: same resolution, never refused); one after a failed rebuild returns to its reserved place.
- **Synthetic tablets (debug builds only).** `synthTabletCount` is `int.fromEnvironment('SYNTH_TABLETS')` in a debug build and 0 otherwise, and the app branches only on the const bool `synthTablets` (`synthTabletCount > 0`): a top-level const bool is folded before tree-shaking, while an `if (synthTabletCount > 0)` is a comparison the tree-shaker does not evaluate, and it kept `FakeTablet`'s class in a profile build (the check is under *Commands*). With it, `InitialBinding` puts `SyntheticTablets(N)`: N `FakeTablet`s, `synth-1` on, models `Synthetic_<i>`, panels taking turns over 2560×1600@60, 2800×2000@120 and 2400×1080@60, three shapes further apart than the 2% `checkShowsOwnDisplay` tolerates, so a stream of another tablet's display shows bars and raises `onCaptureMismatch`. Its `SynthAdb.routing` is registered as the `AdbService` (`Get.put`, so its `onInit` still takes the adb channel's handler): a listing is adb's devices then the fakes (a failed `adb devices` reuses the last real listing), and every call on a serial without the `synth-` prefix goes to the real channel. The hub treats a fake like any USB tablet (it dials the session's loopback port with the key handed to it, so the virtual display, ScreenCaptureKit, VideoToolbox and the budget all run for real), except that nothing about it is persisted (see *Key settings*), the auto-connect policy never picks one, and `_offerWifiPairing` skips it. As a tablet the Mac controls it sends no picture (nothing calls `sendFrame` in the app), the taps and swipes sent to it are only kept in the `SynthAdb` (no input shell is opened for a `synth-` serial, and its `closeInputShell` is only kept too), and its screen-off hold is refused. On the host Home's app bar has a grid icon (only under `synthTablets`) to `/loopback-preview` (`LoopbackPreviewView` and `LoopbackPreviewController` in `lib/modules/extended_screen/host/debug/`, a route `AppPages` adds by a const collection-if): a tile per fake with Start (`hub.connect(serial:)`, counted against `cap` like any pick and, like any pick, as `nextChoice`) or Stop (`disconnectSession`), a label (serial, panel, the mode its session runs as, `effectiveChoice.label`, then the phase, the codec from the fake's `0xFC`, frames received in the last second, the session's `captured` display id and `fellBack`, its `notice`) and the decoded picture in the panel's shape. A tile whose session is one the Mac controls (Mac → Tablet) shows `loopback_no_picture_reverse` instead of a picture, also over a texture an earlier session of that tile left: the Mac streams nothing to such a tablet and a stand-in sends no screen, so there is no preview of that direction. Each tile feeds what reached its fake's socket (`frameStream`) to a `RemoteVideoPlugin` decoder of its own, id `0x40000000 + i` (`decoderBase`, clear of every `nativeId`), made on the first frame and again when the codec changes (frames are dropped meanwhile, then it asks for a keyframe), whose keyframe requests go through `listenIdr` to `FakeTablet.requestKeyframe`, a `0xFF` over the fake's link to the Mac's encoder; closing the page disposes the decoders. `RemoteVideoPlugin` makes a tile's decompression session again only when a keyframe's parameter sets differ from the ones it was made from (see its row under *Native macOS plugins*), and holds its App Nap activity for the preview's decoders as for any other. `HostSession.captured` (`Rxn<CaptureStart>`, set after `startCapture`, cleared with `granted` in `_releaseBudget`) is what the label reads.
- **Rule:** inside `HostSession`, never read `settings.isReverseRemote`, `effectiveDisplayMode`, `sessionMode`, `remoteDirection`, `effectiveRemoteDirection`, `nextChoice`, the global `clientPanel*` or the panel-less `capture*`/`refreshRate` getters. Use `spec` and `panel`. Once there are several tablets, a global read leaks one tablet's state into another. The mode settings reach a session only as the default of its constructor's `choice` (`nextChoice`, once, for a session built without one); `settings.displayMode` is read in `_specNow()` (the display mode is app-wide), and nowhere else. The panel-less getters (`SettingsService`'s and `EncodePresetX`'s `width`/`height`/`bitrate`/`refreshRate`/`resolutionLabel`/`bitrateLabel`) read the last panel a HELLO reported, and nothing in `lib/` calls them any more: Settings labels the presets with `SettingsController.panelForLabels`, the focused session's `panel`, else `lastClientPanel` (read first in any case, so an `Obx` follows every HELLO), through the `…For(panel)` variants; the custom resolutions are derived from it too.

### State management — GetX

`SettingsService` is constructed and `await settings.init()`-ed in `main()` **before** `runApp` so the persisted UI language is available when `GetMaterialApp` reads `locale` at first build; `InitialBinding` only registers it if not already registered. All other services are registered as `GetxService`/permanent singletons in `InitialBinding`, which inspects the platform and registers either `HostConnectionManager` or `ClientConnectionManager` **bound to the `BaseConnectionManager` type** (`Get.put<BaseConnectionManager>(...)`) — so shared UI depends on a single interface. Controllers are scoped to routes via per-feature `*Binding` classes (`HomeBinding`, `DisplayBinding`, etc.). An `Obx` only subscribes to observables read inside its own builder: Home passes `AddDevicePanel` a list of `AddDeviceRow` values (each free device with its subtitle, its last role, the reason it is disabled or the note that its role has no room), built from `hub.freeDevices.toList()` inside its `Obx`, because a plain widget that reads an `RxList` in its own `build` registers nothing and goes stale.

Role-specific services are registered only on their platform (`ScreenCaptureChannel`, `InputInjectChannel`, `RemoteVideoChannel`, `AdbService`, `IosDeviceService`, `IosScreenChannel` and `IosTouchService` on macOS, plus `SyntheticTablets` in a debug build with `SYNTH_TABLETS`, whose `SynthAdb.routing` is then the `AdbService`; `VideoDecoderChannel`, `AndroidCaptureChannel`, `BatteryChannel`, `UsbSessionService`, `WifiPairingChannel` on Android, and all of them but `AndroidCaptureChannel` on iOS, the spike's client). Shared code must `Get.find` them lazily behind an `isHost` check, never as an eager field.

### Localization (`lib/shared/services/app_translations.dart`)

User-facing strings are GetX translation keys resolved with `.tr` (or `.trParams({'name': value})` for `@name` interpolation) against `AppTranslations`, which holds `en` and `th` maps. Existing exceptions: the host's USB connect errors (`HostSession.connect()` stores `e.toString()` in `errorMessage`, so Home's error banner shows raw English such as `Exception: No ADB device detected`; a new failure should throw `LinkError(key)` instead, whose `toString()` is the translation, as the Wi-Fi errors and the USB handshake's `error_usb_*` do; the client uses the key `error_waiting_for_host`, or a `LinkError`'s), the Settings Info values (`USB-C / ADB` or `Wi-Fi / TLS`, `7001`, `1.1.0`, `macOS 13+`; the version is a literal, so keep it in step with `pubspec.yaml`, and `macOS 13+` is one too and does not match the real floor, see *Native macOS plugins*; the Encoder line's chip is the brand string the plugin reads), codec/unit/link labels (`H.264`/`H.265`, `Hz`, `fps`, `ms`, `drop/s`, `Mbps`, `USB-C`, `Wi-Fi`), and the Android foreground-service notification text (English literals in Kotlin). **Never hard-code UI strings** — add a key to both locale maps. This applies to enum label extensions too (`ConnectionPhaseX.label`, `EncodePresetX.label/tagline/description`, `SessionModeX`/`RemoteDirectionX`/`LinkTypeX.label/description`): they are getters, so they resolve the active locale at read time. The Settings permission rows do not: `SettingsController._buildPermissionList()` stores `.tr` results in `PermissionItem.label/description`, so they keep the old language after a locale switch until `refreshPermissions()` runs again — don't copy that pattern. `fallbackLocale` is `en`. The saved language (or device language: Thai if the system is Thai, else English) is resolved in `SettingsService.init()`; `SettingsService.setLocale()` persists the code and calls `Get.updateLocale()`.

### Connection lifecycle (`lib/shared/connection/`)

`BaseConnectionManager` owns the shared phase/latency observables, the packet loop with heartbeat handling, the reconnect timer, and input-send helpers. `connect()` and `autoConnect()` are abstract; `refreshDevices()`, `sendUiFlags()`, `startScreenShare()`, `onRolePacket()`, `onTeardown()` and `onLinkLost()` are overridable no-ops. `ClientConnectionManager` implements the client. On the host every link is a `HostSession` (the hub, `HostConnectionManager`, holds them; see *Hub and sessions* below), so everything below about a host `connect()`, its phases, cancellation, pipeline and teardown is per session. Phases actually set on the happy path:

- Host: `disconnected → detectingDevice` (the session's own device must be listed; it never takes another) `→ portForwarding` (its loopback server bound to port 0, then `adb reverse tcp:7001 tcp:<that port>`) `→ handshaking` (session key handed to adb, waiting for the tablet to dial in) `→ configuring` (waiting for the client's proof, then for HELLO, starting the media pipeline) `→ streaming`. Over Wi-Fi it starts at `handshaking`, and the proof is the pairing token; there the packet loop and the proof/HELLO waiters are set up before `startSecureServer`, because the awaits between bind and `waitForClient` (the discovery responder reads the Computer Name from a process) are long enough for a tablet dialling a known address to send its token, and `packetStream` is a broadcast stream that drops what nobody listens for. Over USB a hello without the key sends it back to `handshaking` within the same attempt.
- Client: `disconnected → handshaking` (dialling; over USB also waiting for the Mac's answer to its hello) `→ configuring → streaming`

`error` is the state while a retry is pending. A `connect()` from `error` (tapping Connect on the tablet; on the Mac, a tablet card's Retry, offered beside Cancel in `error`, or with `cap` 1 a pick of the session's own device) is that retry run early: `beginConnect()` cancels `_reconnectTimer` and clears `_recovering`, so the attempt's own failure goes through `handleLinkFailure()` and arms the next retry instead of being swallowed by the `_recovering` guard. `adbConnecting` and `paused` exist in the enum (with labels and colours) but nothing sets them. `isActive` is streaming or paused; `isConnecting` is everything except disconnected/streaming/paused/error.

**Liveness.** Heartbeat every 2 s; 6 s without any packet from the peer calls `handleLinkFailure()`. An open socket proves nothing here: the ADB tunnel can accept the tablet's connection without ever delivering it to the host.

**Cancellation.** `disconnect()`, `handleLinkFailure()` and `restartLink()` all bump an attempt counter: any of them ends the session a `connect()` in flight was building. Each `connect()` captures `currentAttempt` and `beginConnect()` up front and must check `isCancelled(attempt)` after **every** `await`, bailing through an abandon helper that only cleans up when `isLatestConnect(seq)` (a newer attempt may already own the socket or capture; the host's `_abandon` checks again after each of its own awaits). Keep to this pattern when adding an `await` to either `connect()`. The bump in `handleLinkFailure()` is what stops an attempt whose link already failed from waking later (on a timeout, typically) and failing a second time into the retry that replaced it; the host's `onTeardown()` also completes the proof and HELLO waits, and the client's `onLinkLost()` the wait for the Mac's answer, so such an attempt finds out at once. (`return abandon()` in the two `connect()` methods is what `flutter analyze` warns about; the cancellation checks added for the USB handshake use `await abandon(); return;`, which does not.) `handleLinkFailure()` remembers the value it bumped to and, after its awaits, arms no retry if a `disconnect()` has bumped it again: a Cancel pressed while a lost link is still being torn down (the host's teardown can wait a second or two behind a capture start) stays cancelled. `SocketService` has the same idea one level down: `_dialGen` makes a dial that finishes after a `disconnect()` or another dial drop its socket instead of installing it, and `_bind` ignores events from a socket that is no longer the current one.

**The host's media pipeline is a queue.** `_startCapture` / `_startRemoteReceive`, `_restartCapture`, the hub's ordered rebuilds (`_rebuildAll` for a wake, `_rebuildDisplays` for a changed display set) and the stop in `onTeardown()` run through `_exclusive()` (the hub's through `pipeline.run`), one after the other: the hub's one `PipelineQueue`, which every session shares (and the hub's `disposeSession` when it ends a session goes through it too). Never call `pipeline.run` from inside a queued operation: it would wait for itself (`stopPipelineOp`/`startPipelineOp` are the halves of a rebuild meant for inside one, and queue nothing; a start that asks for a display rebuild only asks, and the hub queues the round from a `Timer.run`, as it does a Mirror capture's repair round). A session can end while its capture is still starting; the stop then runs right after that start instead of beside it, so it always wins. `_startCapture(attempt)` returns after any of its awaits once `isCancelled(attempt)`, leaving the cleanup to that queued stop, and so does `_startRemoteReceive(attempt)`: at its top (an attempt that ended while its start waited at the queue sends no `0xF9` and makes no decoder) and after the decoder's `initialize` (no texture shown, no `0xF8` or `0xFF`; the queued stop disposes the decoder). Don't start or stop capture outside the queue.

**Who initiates.** `SplashController` (route `/`) calls `autoConnect()` once, from `onInit` (not `onReady`, which waits for a frame), and replaces itself with `/home` 2 s later. The client always dials and retries until the host is up, and over USB dials at once when adb delivers a session key (the host has just started an attempt), so it no longer waits out its 5 s retry after the Mac connects or reconnects for a settings change. The host connects without a tap through the hub's auto-connect policy, `connectIfUnambiguous({since, only})`. It does nothing once a Cancel, Disconnect or retry has bumped the attempt since `since`, while `autoConnectPaused` is set (the host's Home no longer sets it: it has no facade card, every device's card stops that device alone by putting it in `stoppedDevices` (a Wi-Fi device too: the listener turns it away), and Wi-Fi is the Accept devices over Wi-Fi switch, which stops the listener rather than pausing anything; `HomeController.onConnectTap`, the one Home caller of `pauseAutoConnect()`, is wired only to the client's `ConnectionCard`, where the base no-op makes it nothing, so on the host `autoConnectPaused` is set only by `pauseAutoConnect()` callers outside Home, tests today; the user's next connect from Home, `_connect()`, calls `allowDevice(serial)`, which ends both, and calls it only after its permission check, in the same synchronous step as `hub.connectWith`, which holds the key in `_choosing` before its first await: lifted before that check, a policy run already waiting on its listing connected the stopped tablet in its remembered mode and the pick, in the role picked, was refused as a second one (so a press that ends in Settings for the permissions lifts neither); a remote-view tile's Disconnect pauses nothing and stops no tablet: it is `disconnectSession` with `userStopped` false), or while a hub `disconnect()` runs. It checks Screen Recording and Accessibility itself (`hostGranted`, by default `PermissionsChannel().hostGranted`) before anything else, then waits up to 2 s for `hostInfoReady` so the launch does not admit tablets against the conservative encoder estimate. Over Wi-Fi it starts listening while no session exists, the hub is `disconnected` and `stoppedDevices` does not hold `wifi`. Over USB it lists the devices again, then takes as candidates the attached devices (mDNS duplicates dropped) with no session and none starting, not in `stoppedDevices`, never a stand-in (`synth-`), emulators only when no real tablet is attached, and only those in `only` when given. With no session, nothing starting, no tablet between two sessions (`_reserved`), the hub `disconnected` and exactly one candidate, that one connects (the first-run rule, as the single manager had: two new tablets wait for a pick); a tablet in `stoppedDevices` is no candidate but still counts as attached for this rule, so stopping one of two tablets on its card does not make the other the only one. With `cap` over 1 so does every candidate in `knownDevices` (a tablet that has had a live session), in serial order, within `cap` less the places held (`heldUsbPlaces`: the USB sessions and any tablet whose mode is being changed), the starts and the user's picks still under way (keys in `_choosing`, such as a pick waiting for its tablet's old session to end; such a key is no candidate either, so it holds one place, not two). With `cap` 1 (Wi-Fi, Maximum tablets 1; the mode no longer matters) only the first-run rule applies, so two attached tablets mean nobody connects by itself, as before. Each start is `_start(key)`: `connectWith(key, choice: settings.knownChoice(key))` unawaited (a connect returns only once its session is live), its key in `_starting` until it returns. So a tablet the policy connects runs in the mode it is remembered in, whichever rule took it, and one with none remembered (or the Wi-Fi session) in `nextChoice` then; `nextChoice` does not change a known tablet's automatic mode. Callers: the host's `autoConnect()` at launch; `HomeController._maybeAutoConnect()` (Home init and each app resume, once `missingPermissions` is empty); the hub's own resume (Home is not built when the app was launched hidden); and the device poll. `autoConnect()` starts the poll first (every `devicePollInterval`, 3 s; null disables it), before any permission check, so a Mac granted them after launch still connects a tablet plugged in later; `stopPolling()` ends it (`onClose`, `detached`). A tick lists nothing while one is still out, while a session is in `detectingDevice` or `portForwarding`, or over Wi-Fi, and a failed listing (`AdbService.listDevicesOrNull` answering null) changes nothing; `refreshDevices()` and `_choose`'s listing use it too, so a failed `adb devices` no longer empties the picker. Every successful listing goes through `_listed`, which sets `availableDevices` and keeps a baseline (`_seen`): the first listing only seeds it (when that first one is the poll's, the launch's listings all failed and found nothing to connect, so the policy runs once on it, for every tablet), a serial counts as gone only after two successive listings without it, and the poll ignores one empty listing right after a non-empty one (adb restarting). A session in `error_device_gone` whose tablet is listed is retried at once (`retryNow`), and tablets that appeared run the policy with `only` set to them. A USB session waiting in `handshaking` for its tablet to dial in is restarted (`HostSession.tunnelLost()` → `restartLink()`) when two successive listings during one attempt miss its tablet (`_tunnelMisses`, the baseline's two-miss rule: one listing that misses it, adb hiccupping, restarts nothing) or one lists it under another adb `transport_id` (`DeviceModel.transportId`, from `adb devices -l` via `AdbManagerPlugin`; a re-seated cable gives a new one): adb drops a device's reverse rules with its transport, nothing on the Mac fails (the wait for a dial has no timeout), and the tablet's dials would never reach the session again. `SynthAdb.transports` sets the ids in tests. The policy does not run on every tick, so the poll does not connect again a tablet that stays plugged in after a remote-view tile's Disconnect; the next resume or Home focus does, as before, since that Disconnect pauses nothing. The launch call is what connects a Mac app started behind other windows, at login or hidden: the macOS embedder reports such an app as `AppLifecycleState.hidden` (`FlutterEngine.mm`, on occlusion), the framework then draws no frames, and the `/home` route the splash pushed is not built, so Home's controller does not exist until the window is shown. Nothing on the host's connection path may wait for a frame or a built route. One layer down, `FlutterViewController` launches the engine only in `viewWillAppear`, so an app launched hidden (`open -j`, a login item set to hide) would not even run `main()` until its window was shown: `MainFlutterWindow.awakeFromNib` therefore runs the engine itself (`engine.run(withEntrypoint: nil)`) after registering the plugins.

Every link failure (socket error/close, heartbeat timeout, or a throwing connect attempt) goes through `BaseConnectionManager.handleLinkFailure()`: it stops that link's packet listener + heartbeat, runs the role's `onLinkLost()` (host: full `onTeardown()` — releases any mouse button the tablet left held (`InputInjectChannel.releaseAll()`), then capture, virtual display, adb tunnel; client: only lets go of a dial still waiting for the Mac's answer, so its keep-alive service survives for background reconnects), closes the socket (server included), sets `error`, then retries after `nextRetryDelay()` (`retryPending` is true from arming that timer until it fires, or `beginConnect()`, `disconnect()` or `restartLink()` drops it): the client 5 s; a host USB session 1 s, then 2, 5 and every 10 s (each ±20%) while it keeps failing, from 1 s again once it has been live (an adb restart drops every tunnel at once, and the retries must not storm it); a Wi-Fi session always 1 s. `handleLinkFailure(retry: false)` does all of that but arms no timer, for a failure trying again cannot fix (a host session the encoder has no room for, `CaptureLimit`); `_recovering` stays set, so the resume rule and a late socket error leave it alone, until the next `connect()` (`beginConnect()` clears it). Beside `errorMessage`, `errorKey` holds the `LinkError` key behind it (null for anything else; the client's fallbacks set `error_waiting_for_host` or `error_wifi_untrusted`, the hub's "No ADB device detected" sets none), so the UI can branch without comparing translated text. Host exceptions: a media pipeline that fails to start is only logged (`connect()` catches a throw from `_startCapture()`; the reverse-remote decoder init in `_startRemoteReceive()` swallows its own error and only sets the session's `notice` to `error_remote_decoder`), so the link still reaches `streaming` with no video instead of retrying, except `CaptureLimit`, which ends the session with no retry (see *Encode budget*). Never retry by calling `connect()` on a live session — that stacked duplicate listeners/timers and a second server socket. `restartLink()` is the one other way a session is replaced: the same teardown as a link failure, followed by `connect()` at once (the client uses it when a new USB session key arrives). It does nothing while a `disconnect()` is still tearing down (`_stopping`, `isStopping`): `disconnect()` sets `disconnected` only at its end, so a key arriving during the tablet's teardown used to start a link that outlived the user's Disconnect. `HostSession.connect()` refuses then too: a `reconnect()` of a session in `error` leaves it reading `error` with no retry pending through its teardown, and a connect started meanwhile (its card's Retry, `retryNow`, the resume rule) had its server closed and its phase overwritten under it, then ran beside the reconnect's own as a second attempt on one session. `SocketService` owns the raw TCP socket; `AdbService` wraps `adb` CLI calls. Over USB `SocketService.send()` is fire-and-forget (`Socket.add` with `tcpNoDelay`, errors swallowed, no flush or backpressure), and the server takes one client and destroys any further connection. Nothing on the sending side reacts to a slow USB link: frames queue in the socket, Max's adaptive rate only measures encoder load, and the one relief is the client decoder's queue cap (see `VideoDecoderPlugin.kt`). Wi-Fi sockets are paced instead (see *Link types*). The **macOS host is the sole settings/control surface**: display mode, encode preset and codec are editable only on the host (the client's Settings page renders none of those controls, only language, permissions and info). Every setting change persists the value and then reconnects (full disconnect + reconnect to the same device, debounced 350 ms in `SettingsController` so several edits in one sheet collapse into one) so the capture/encode pipeline restarts with the new value. A preset, codec or custom-value change calls `reconnect()`, every session: a tablet the Mac controls takes its codec, rate and bitrate from them too (`0xF8`). The display mode alone calls `reconnectExtendedOnly()`, which on the hub restarts only the sessions whose `spec.mode` is Extended screen: a remote-control session mirrors whatever that setting says, and restarting a tablet the Mac controls would make its user approve capture again for nothing. `_pendingAll` is the OR of what the changes since the last reconnect that started need; it is read and cleared only when a reconnect starts (before its first await), so the display mode and a codec in one debounce make one `reconnect()`. One reconnect runs at a time. A debounce that runs out while one is still running sets `_again` (the change used to be dropped there, saved but running on no tablet until the next change), and when the running one returns, also by throwing, exactly one more runs for everything changed meanwhile, with the merged flag; a round that starts cancels a debounce still pending, since it applies that change too. `isApplying` (the rows are disabled, "applying" shows) stays set through that second round and while a change made near the end of a reconnect still waits out its debounce. A change still in its debounce when Settings is closed is applied at once (`onClose`; it used to be dropped with the timer). Six things don't reconnect: Maximum tablets (Settings → Tablets, 1 to 8) is only saved, since the hub's `cap` reads it at each pick and admission and a lower cap ends no tablet already connected; the Add a device panel's Accept devices over Wi-Fi row starts or stops the listener and the Wi-Fi devices' sessions alone; the overlay/HUD toggles push `0xFA` via `sendUiFlags()`; the language picker only calls `SettingsService.setLocale()`; the "keep the Mac cursor in place" toggle is pushed to `InputInjectPlugin` by an `ever()` worker in `InputInjectChannel.onInit()`; and session mode / remote direction are picked on Home, where they are just persisted and say what the next session the user adds runs as (a session that exists keeps its own; a USB tablet's is changed from its card's menu, and over Wi-Fi a pick made while the session waits to retry replaces it, both through `hub.changeMode`, see *Hub and sessions*). On each start the host announces the active codec to the client via a `0xFC` control packet; the client's `DisplayController` rebuilds its decoder if that differs from the codec it was built with (see the `0xFC` row).

On the host, connects the user starts on Home (a row's Connect, after the role chooser for a new device, and a device card's Retry) go through `HomeController._connect()`, which is gated by `_ensureHostPermissions()`: if Screen Recording or Accessibility is missing, it snackbars, navigates to Settings with `arguments: {'scrollTo': 'permissions'}` (`SettingsController` scrolls to the Permissions header via its `permissionsKey` `GlobalKey`) and does not connect, nor lift a stop or the pause (`allowDevice` comes after the gate, see *Who initiates*). The automatic connects (the auto-connect policy above) only check the permissions (`hostGranted` / `missingPermissions`) and never snackbar or navigate; the launch one takes `currentAttempt` first and stands down if a Cancel, Disconnect or retry came while it waited (adb's first call can take seconds; over Wi-Fi it does not wait for adb at all, and `adb devices -l` is ended after 10 s). Everything else calls `connect()` directly and skips the gate: the `handleLinkFailure()` retry, the resume reconnect in `BaseConnectionManager.didChangeAppLifecycleState`, `retryNow`, `reconnect()` (settings changes; on the hub every session's) and `reconnectSession` (a remote-view tile's Reconnect). Home opens `/remote-host` when `reverseActive` leaves 0, and on its first frame when a tablet the Mac controls is already live (the launch can get there before Home exists).

### Packet protocol (`lib/shared/models/packet_model.dart`, `lib/shared/protocol/packet_codec.dart`)

Framing lives in `Packet.serialize()` and `SocketService._tryParsePackets()`: a 17-byte header (4-byte magic `EXTD` + 1-byte type + 4-byte payload length + 8-byte timestamp in µs) followed by the payload, all big-endian. `PacketCodec` only encodes and decodes payloads (input events, heartbeat ping/pong) as hand-rolled binary. An unknown type byte parses as `CONTROL`, a bad magic flushes the whole receive buffer, and a header announcing more than `SocketService.maxPayloadBytes` (16 MB) drops the peer (`_dropPeer`, reported like a close by the peer). A pong echoes only the ping's nine bytes. There is no version negotiation, and host and client are separately installed builds, so a wire change needs both rebuilt (the USB handshake was such a change: a build from before it and one from after refuse each other, see *Link types*). The only tolerance is for older, shorter payloads (`decodeMouse` without the modifiers byte, `_onHello` without the size or the rate). Enums travel as `.index`: `MouseAction`, `MouseButton` and `TouchAction` in input payloads (`InputInjectPlugin.swift` switches on the raw integers) and `SessionMode`/`RemoteDirection` in `0xF9`, so append to them and never reorder.

Packet types: `FRAME_DATA` (one encoded frame as an Annex-B buffer, in whichever direction the stream runs; keyframes are prefixed with their parameter sets, so a payload can hold several NAL units despite the `nal` naming in code), `TOUCH_EVENT`, `MOUSE_EVENT`, `KEY_EVENT`, `HEARTBEAT`, `CONTROL` (`ack` and `displayConfig` are declared but unused). The Android display currently sends only `MOUSE_EVENT`: `TouchGestureRecognizer` turns touches into click, scroll (with a fling, skipped when the finger rested longer than `_flingMaxIdle`, 100 ms, before lifting), long-press drag and pinch (⌘+scroll). `DisplayController._sendMouse` always sends `MouseButton.left`, so there is no right-click. A drag is down, `MouseAction.move`s, up; extra fingers during it are ignored, and every path that ends it (lift, cancel, `_reset()`, `dispose()`) goes through `_endDrag()`, so exactly one up follows each `onDragStart`. That up is dropped if the link is already down (`sendMouse` needs an active phase); the host's `releaseAll()` on teardown covers that case. `sendTouch()`/`sendKey()` have no callers, though the host decodes and injects all three.

Control sub-commands are the first payload byte, dispatched in each manager's `onRolePacket()`:

| Byte | Direction | Meaning |
|---|---|---|
| `0x01` | client → host | HELLO (sent once the peer is trusted: after `0xF5` over Wi-Fi, after the `0xF4`/`0xF3` exchange over USB): platform byte (`0x02` = Android; the iOS spike sends `0x03` iPhone and `0x04` iPad, and there the size is the safe area, not the panel; see *iOS client*), panel width and height (uint16 BE each, physical px, landscape), panel top refresh rate (1 byte, Hz). Then, from phase 4's clients, the identity tail (`HelloTail`, `lib/shared/protocol/client_hello.dart`): `0xA1`, the install id (16), the name's length (1) and the name (UTF-8, at most 64 bytes); a host that does not know it reads only the first seven bytes, and the host accepts a HELLO without it (today's tablet build sends none). The size is the whole display, not the Flutter window (which can leave out the nav bar): `ClientConnectionManager._nativePanelSize()` reads `view.display.size`, falling back to `view.physicalSize` if the display is unreported or empty. The same size drives the reverse-remote capture |
| `0xFF` | viewer → encoder | Request an IDR. Client → host normally. Host → client in reverse remote: once as the host starts receiving (`_startRemoteReceive()`, after `0xF8`), and whenever `RemoteVideoPlugin.swift` raises `onRequestIdr` (a decoder fed pictures it cannot decode, at most once a second). The tablet passes it to its encoder (`PARAMETER_KEY_REQUEST_SYNC_FRAME`), so its next frame is a keyframe; with no capture running it does nothing |
| `0xFE` | host → client | Client replies with `0xFF`. Still handled, but nothing sends it |
| `0xFC` | host → client | Codec (`0` H.264, `1` H.265). Only `ClientConnectionManager` handles it, storing it in `SettingsService`. `DisplayController` records the codec each decoder build used (`_decoderCodec`), and an `ever(codecRx)` worker rebuilds whenever the setting differs, so a display opened before the announcement (on `streaming`, with last session's codec) still switches; the codec already running causes no rebuild. A build bumps `_decoderGen`, cancels the frame subscription, and stops after any await once superseded or closed. The native decoder ignores `initialize` while configured, so a rebuild must `dispose()` first |
| `0xFB` | host → client | Stream refresh rate (Hz) |
| `0xFA` | host → client | Performance-overlay and HUD-stats toggles (HUD off hides only the stats; Back and Disconnect stay) |
| `0xF9` | host → client | `SessionMode` index + `RemoteDirection` index |
| `0xF8` | host → client | Reverse remote: start capturing (codec, fps, bitrate in Mbps) |
| `0xF7` | host → client | Stop capturing this screen for the Mac. Sent by a reverse-remote session as it ends (best-effort), and by every other session once per connect attempt, before its pipeline starts, for a capture a dead link left running (see *Session modes and stream direction*). The client handles it with no mode check; with no capture it only clears `needsScreenShare` |
| `0xF6` | nobody sends it | Was Wi-Fi pairing on USB sessions; the client now ignores it on every link (see *Link types*). The byte is still the first one of the pairing payload that adb delivers: `0xF6`, version byte, host id (16), token (32), name (1-byte length + UTF-8), certificate (uint16 BE length + DER), then the Mac's IPv4 addresses (count byte + 4 bytes each, at most 8; a payload may end at the certificate). Built and parsed by `WifiPairingService` |
| `0xF5` | client → host | Wi-Fi sessions only, first packet: the paired host's token (32 bytes) |
| `0xF4` | client → host | USB sessions only, first packet (the hello): nonce (16) + HMAC-SHA256(session key, client label + nonce) (32). The HMAC is left out when no key has been delivered; such a hello only tells a waiting host that the app is there. Built and checked by `UsbSessionService` |
| `0xF3` | host → client | USB sessions only, the answer to a hello that proved the key: HMAC-SHA256(session key, host label + nonce) (32). Nothing else from the peer is admitted by the client before it |

The host waits (3 s timeout) for the HELLO before starting capture and persists the reported panel via `SettingsService.setClientPanelFor(key, panel, global:)`: under that tablet's key and, for an Android HELLO (platform `0x02`, or none, or a byte this build does not know; `HostSession.platform` keeps the known ones), as the last panel any tablet reported. An iPhone's (`0x03`) or iPad's (`0x04`) is kept under its key only, so it never becomes a new tablet's guess. The client sets its display mode from the host's `0xFB` (the slowest panel mode ≥ the stream rate, never below 60 Hz), not from its own (host-only) preset; a mid-stream `0xFB` only switches the panel mode (`setRefreshRate`, which also moves the decoder's input-queue cap) — the decoder is configured with the panel's top rate as its operating rate so it's never rebuilt for a rate change.

### Native macOS plugins (`macos/Runner/`)

| File | Purpose |
|---|---|
| `ScreenCapturePlugin.swift` | ScreenCaptureKit capture → VideoToolbox H.264/H.265 encode → `FlutterEventChannel` frame stream. One registered `ScreenCapturePluginImpl` (method channel, the single frames sink, the wake and screen-parameter observers, the App Nap activity, held while any session streams) keeps a `CaptureSession` per session id (every call's `session` argument, none meaning 0; Dart's ids are `HostSession.nativeId`, from 1, never reused in a run: a session keeps its id through retries and reconnects, and a new session gets a new one): its virtual display, `SCStream`, encoder, timer thread, capture queue (`capture.<id>`) and diag counters, logged as `[ExtendedScreen] s<id>`. Every encoded frame starts with its session's id, 4 bytes big-endian, which `ScreenCaptureChannel.framesFor(id)` strips. Dart holds one `receiveBroadcastStream` subscription for the app, started by the first `framesFor` and never cancelled, and hands each frame to its id's broadcast stream (`_routes`; an id nobody asked for is dropped, and `disposeSession` closes its stream): a second subscription would take the first one's frames, and cancelling the last listener stopped the native sink, so a rebuilt encoder's first frames were lost before the next listen. Frames that come while an id has no listener are still dropped. Also manages `CGVirtualDisplay` (Extend mode): `createVirtualDisplay` is add-only (it replaces only that session's own display, after 0.3 s), takes `serialNum` and `name` from Dart (the session's `vdSerial`/`vdName`), reports its size in millimetres as the pixel buffer (2w×2h) at 218 ppi (see *Display modes*), and answers `{applied, displayID}` once the display is in `CGGetActiveDisplayList` (at most 1 s; its mode is final by then), logging the mode it came up in (`mode=1248x660 pt 2496x1320 px 2x`; `CGDisplayCopyDisplayMode` is often nil once the process has made another virtual display, so the scale is then judged from `CGDisplayBounds` against w×h) the display's size (w×h, grown to at least 800×525 pt for a HiDPI desktop, `hiDPISize`), and the switch to HiDPI from a child process when macOS brought it up 1x (`VirtualDisplayModeHelper`, see *Display modes*), with a `WARNING` when it is still not HiDPI after that (`ScreenCaptureChannel.createVirtualDisplay` → `VirtualDisplayResult`, `ok` only with both; `_startCapture()` logs a warning otherwise, and with no display at all sets the session's `notice`); its `terminationHandler` reports `onVirtualDisplayTerminated {session, displayID}` (main thread; the channel's callback of that name, which nothing wires yet: whether macOS also calls it for a display we released is unchecked); `removeVirtualDisplay` answers once the display has left `CGGetActiveDisplayList` (at most 1 s). `startCapture` honours `mode` (0 Extend: that session's virtual display; 1 Mirror: the main display, whatever else exists), picks the display with `findCaptureDisplay` (see *Display modes*), stores it in `capturedDisplayID`, which `getVirtualDisplayBounds` reports, so input maps onto the display actually shown, and answers `{displayID, hardware, fellBack}` (Dart's `CaptureStart`; An Extend start that fell back to the main display, or had no virtual display, is not checked. A start on a session that is still running stops it first. ### iPhone over USB, driven by the Mac (`/iphone-remote`)

The Mac sees and drives an iPhone or iPad plugged into it. This path uses none of the protocol above: no hub, session, packet, adb or Wi-Fi, and nothing of this app runs on the phone. The picture comes from AVFoundation and the touches go through usbmuxd to an XCUITest runner. It is host only, built but not yet tried in the app on a real device (the spike's numbers are in `docs/roadmap.md` §4).

- **Picture**: `IosScreenPlugin.swift` (see *Native macOS plugins*) → `IosScreenChannel` (`lib/modules/remote_screen/host/ios_screen_channel.dart`, permanent on the host, inert until called): `listDevices`, `start([id])` (throws the `PlatformException`), `stop`, and the Rx `textureId` and `frameSize` (cleared on `onStopped`). Measured on an iPhone 18 Pro Max: 1320×2868 portrait at about 53 fps, and only while the screen changes; a still screen sends nothing, a locked or dark one nothing at all. It needs the Camera permission (see the `AppDelegate` paragraph). When a capture starts the phone drops off usbmuxd for a moment, so the runner can read as missing for a second or two.
- **usbmuxd**: `UsbmuxClient` (`lib/shared/connection/usbmux.dart`) on `/var/run/usbmuxd`, as `iproxy` does: a 16-byte little-endian header (length, version 1, type 8 for a plist, tag) and an XML plist. `listDevices` (`UsbmuxDevice`: `DeviceID`, which changes on every replug, the UDID as `serial`, `USB` or `Network`), and `connect(deviceId, port)`, after whose success the same socket is the stream to the phone's port (`UsbmuxStream`; a non-zero `Number` throws `UsbmuxRefused`, 3 when nothing listens). `PortNumber` goes in network byte order as a 16-bit value (8100 is sent as 0xA41F). The repo has no XML dependency, so `Plist` is a small codec of its own for the shapes usbmuxd uses (dict, array, string, integer, true/false, data kept as base64 text).
- **The runner** (`ios/TouchRunner/`, its own Xcode project, apart from Flutter's `ios/Runner`): the UI-test target `TouchRunner` (`com.porto.extendedscreen.ios.touchrunner`) with its blank host app `TouchHost` (`….touchhost`, which Xcode wants beside a UI-testing bundle; the runner drives SpringBoard), the free team T4P27BU383, iOS 17. Its one test, `testServe`, never ends: it listens on TCP 8100 on the phone's loopback only (`requiredInterfaceType = .loopback`; usbmuxd's connections arrive there, nothing on the LAN can reach it) and answers one line per command line: `tap`/`atap <nx> <ny>`, `swipe`/`aswipe <nx1> <ny1> <nx2> <ny2> <seconds> [<hold>]` (from a point to itself, a press held that long; `<hold>` holds at the start first), `orient` (`orient <UIDeviceOrientation raw value>`), `ping` (`pong <w>x<h> fast=<bool>`, the screen in points: 440x956 on the iPhone 18 Pro Max), `quit`. Coordinates are normalized to the portrait screen, seconds 0 to 5; anything else is `err <line>`. `FastTouch.m` synthesizes the touches straight through XCTest's private event synthesizer (`XCPointerEventPath`, `XCSynthesizedEventRecord`, WebDriverAgent-style) instead of `XCUICoordinate`, which waits for the app to go idle (~700 ms a tap). `atap`/`aswipe` answer `sent` at once and the touch lands about 100 ms later (a swipe sent on the Mac showed in the USB capture 109 to 129 ms later); `tap`/`swipe` answer once XCTest reports (~250 ms), and fall back to `XCUICoordinate` only when the synthesizer never got the touch (code 1), so nothing lands twice. Without the private classes (`fast=false`) every command is the `XCUICoordinate` one.
- **Starting the runner**: open `ios/TouchRunner/TouchRunner.xcodeproj` in Xcode, pick the phone, and run `testServe` from the test's gutter button; leave it running (turning off Auto-Lock keeps it alive). `xcodebuild test-without-building` fails on the iPhone 18 Pro Max with "Root install style is not supported" (six variations tried), so there is no command line for it. It needs Developer Mode, and on the free team its signature lasts 7 days, after which it has to be run from Xcode again.
- **Touches**: `IosTouchService` (`ios_touch_service.dart`, permanent on the host): `connect()` (one at a time) takes the first USB device usbmuxd lists, opens port 8100 and sends `ping`; `state` is `idle`, `noDevice`, `noRunner` (refused, no pong, or the link dropped) or `ready`, `screenPoints` the pong's size and `fast` its flag. `tap` and `swipe` (seconds clamped to 0.02..3, hold to 0..3) connect first if needed and send `atap`/`aswipe`; a runner without fast synthesis gets `tap`/`swipe`, and a fast verb it answers `err <verb> …` (a build from before `aswipe`) is sent again at once the blocking way, and that way for the rest of the connection (a refused command touched nothing). Replies are matched to commands in order; no reply in 2 s (plus the touch's length and 5 s for a blocking one) drops the link. The side the phone is turned is cached in `lastTurn` (an Rx): `turn()` asks `orient` (one question at a time; a failed one drops the link) and stores a landscape answer, keeping the last side when the phone lies flat; `connect()` asks it once, unawaited, right after the pong, and `refreshTurn()` asks only while connected (it never opens a link). Caveat: `orient` reads `XCUIDevice.shared.orientation`, the phone's physical orientation, not the frontmost app's interface orientation, so with rotation lock on or the phone flat the two can differ (plan unit L2 makes the runner answer the interface orientation). `disconnect()` bumps a generation, so a connect under way closes what it opened.
- **The view**: each iPhone or iPad `IosScreenChannel.listDevices` lists has a card on Home (`IphoneUsbCard`, `iphone-usb/<id>`, listed as Home opens, on resume and every 2 s while Home is shown; see the Home paragraphs under *Link types*), whose Open screen button (`iphone-usb/<id>/open`) pushes `/iphone-remote` (`AppRoutes.iphoneRemote`) with `{'id': id}`; the route's `BindingsBuilder` puts `IphoneRemoteController(deviceId:)` from those arguments. The controller starts the capture of that device when it is listed, else of the first listed device and connects the touches, and tries both again every 2 s while missing (one start at a time, `_starting`, so the Camera prompt never gets a second capture behind it; nothing more after `PERMISSION_DENIED` until Retry). `IphoneRemoteView` shows `Texture(textureId)` in a box of the frame's aspect ratio, with a `_TouchChip` (`iphone_remote_touch_ready`/`_off`) in the app bar, a banner over the picture only for `noRunner` (`iphone_remote_runner_missing`, which says how to start the runner), and with no picture a message by `IphoneScreenState` (`noDevice`, `permissionDenied` and `failed` with Retry, else waiting). A click is `tap`; a drag a `swipe` replayed over the time it took (0.05 to 3 s); a press past the long-press delay sends nothing until let go, then a press held as long as it was, or, if it moved after the hold, that hold then a drag to where it was let go. Closing the page stops the capture and disconnects the touches.
- **Latency probe** (`--dart-define=IPHONE_PROBE=true`; plan unit M0a in `docs/iphone-usb/plan.md`, results in `docs/roadmap.md` §4): the const `IPHONE_PROBE` (`IphoneRemoteController.probeDefine`) is only the default of `probeEnabled` on the controller and on `IphoneRemoteView` (each its own, so tests inject both). With it on, the view wraps the picture's `GestureDetector` in a `Listener` whose `onPointerDown` calls `onPointerDown`, which sends `IosScreenChannel.markProbe(id)` before the gesture arena decides anything, so before any touch command. Swift (`markProbe {id}` in `IosScreenPlugin`) takes t0 itself with `mach_absolute_time` as the call arrives (both ends on the Mac's one clock; Flutter's event timestamps are never compared with it), samples a 16×32 grid of the frame shown then (`ProbeGrid`: 2×2-pixel averages, BGRA as Rec. 601 luma, or the luma plane of 420v/420f, so the numbers stay comparable after a switch to NV12), and answers whether it armed (false with no frame yet). Only while a probe is armed does `captureOutput` sample each frame; the first whose mean difference (samples differing by 6 levels or more) reaches 0.5 ends it: `probe id=<id> change=<ms>` (`esLog`, category `ios_screen`) and `onProbe {id, ms}` (ms from t0 to that frame's callback). After 2 s with no change, when a newer probe replaces it or when the capture stops, it gives up with `ms` null. Dart's `ProbeResult.parse` reads it, `ProbeSummary` keeps the last 50 with nearest-rank p50/p90. Felt mode: every pointer-down on the picture is probed and logged (`LoggerService`, debug builds), and an overlay (`iphone/probe-overlay`) shows the felt p50/p90 and the last value. Scripted mode: the speed menu (`iphone/probe`, `iphone_probe_*` keys) runs `runProbe` with 50 trials (`probeTrials`), each after `probeSettle` (800 ms) and armed (awaited) just before its command: `atap` at the last point clicked on the picture (click a blank row first; else the middle), or an `aswipe` of 0.15 over 0.2 s, up and down in turn, in the middle; the run's p50/p90 is logged and shown. Felt probes are not armed while a run is under way.
- **Coordinates**: `IphoneRemoteController.toPortrait` normalizes the point in the box; a portrait frame maps straight, and a landscape one (the phone turned) is a quarter turn of the portrait screen the runner addresses, one way or the other by the cached `lastTurn` (`UIDeviceOrientation` 3 `topLeft`, 4 `topRight`), since the frame's size cannot tell which. `_map` is synchronous: no touch waits on an `orient` round trip. The controller refreshes the cache (`refreshTurn`) when `IosScreenChannel.frameSize` changes to a landscape frame (an `ever` worker; a rotation changes the frame) and right after each gesture has gone out while the frame is landscape (a flip from one landscape side to the other keeps the size, so the first gesture after it can go to the old side and the next is right). Never on a timer (an `orient` shares the runner's main queue with touches), and never while a drag or long press is under way (`_gestureOpen`, from its start until its command has gone out, or `onPanCancel`/`onLongPressCancel`): a refresh asked for meanwhile is sent after it. The landscape mapping is covered by tests only, not checked on a real phone.
- **Limits**: one phone: the capture takes the first capture device and the touches the first USB device usbmuxd lists, which need not be the same phone when two are plugged in. The screen must stay on and unlocked. No keyboard, scroll wheel or Home button. Windows would need another capture (a reverse-engineered protocol or a ReplayKit extension) and another way to start the runner (go-ios, testmanagerd).

### Display modes

- **Extend:** Creates a `CGVirtualDisplay` matching the tablet resolution (logical panel ÷ 2, HiDPI, one mode w×h); ScreenCaptureKit captures that virtual display. Whether it comes up HiDPI (w×h pt over 2w×2h px) or 1x (bounds at the pixel size, tiny text on the tablet) is macOS's choice, and for a display it has no saved mode for it rests on the size in millimetres the descriptor reports (measured on macOS 27.2, M3 Pro, undocumented): HiDPI only when that is at least ~166 mm wide and at least ~150 px/in. The size used to be the logical width at 220 ppi, under 166 mm for every panel narrower than 1440 pt, so only the Tab S10 Ultra (1480 pt, 171 mm) came up HiDPI and an iPhone, the emulators and a foldable came up 1x; it is now the pixel buffer at 218 ppi, wide enough for any w ≥ 713 pt. A display below 800×525 pt (1600×1050 px) never comes up HiDPI, whatever the millimetres (832×440 came up 1600×846 pt at 1x), so `hiDPISize` grows a smaller panel's display, keeping its shape, until it fits (832×440 → 993×525 pt); the capture still encodes the panel's w×h × scale, so the tablet gets that desktop scaled to its panel (text at about 84% of its usual size). macOS also remembers the mode per display UUID (vendor, product, serial; not the millimetres) and set of attached displays, in `/Library/Preferences/com.apple.windowserver.displays.plist`, so a `vdSerial` that once came up 1x at a size comes up 1x there again. `createVirtualDisplay` therefore checks the display once it is active (`isHiDPI`: the bounds are vw×vh, and the mode, when there is one, is 2x) and otherwise switches it with `VirtualDisplayModeHelper`: the app's own executable run as a child with `--extendedscreen-set-hidpi <displayID> <w> <h>`, which `AppDelegate.main` hands over before `NSApplicationMain`, so the child never becomes an app. It touches only a display reporting the descriptor's vendor and product (0x3456/0x1234), leaves another HiDPI mode alone (the user's pick in System Settings, exit 4), and makes the switch `forSession`; macOS saves it, so the next display with that serial comes up HiDPI by itself. Never make the switch in the app's own process (`CGConfigureDisplayWithDisplayMode`, even `forAppOnly`/`forSession`): the display then stays active after release until the process exits (measured: still listed 8 s after release), while the child's switch leaves nothing behind (released in about 0.1 s). `createVirtualDisplay` answers after the switch (about 0.5 s more), and a display still not HiDPI then gets a `WARNING` line. A new one can take a moment to appear in ScreenCaptureKit's list, so `findCaptureDisplay` looks it up once and then re-polls up to 6 times, 0.25 s apart (~1.5 s); if it never shows up, capture falls back to the main display with a `WARNING` unified-log line and releases the virtual display. A session with no virtual display at all (`createVirtualDisplay` made none) captures the main display at once, with the same kind of line. Either way `startCapture` answers `fellBack`, and `HostSession._startCapture()` sets the session's `notice` to `error_extend_unavailable` ("Extend unavailable, mirroring"), which its `DeviceCard` shows (and the Loopback preview's tile).
- **Mirror:** Captures the `CGMainDisplayID()` display (the one with the menu bar; the first listed one if it is missing); no virtual display created.

The encoded frame always has the panel's aspect ratio: panel-sized at a capture scale of 2.0, half-sized for `performance`, and `customWidth` wide for `custom`. A display of another shape (Mirror from a notched MacBook or a 16:9 monitor) is scaled to fit with bars, and the tablet normalizes touches over the whole frame, so `InputInjectPlugin` maps them through the session's `CaptureContentRect` onto the picture before scaling onto the captured display's bounds.

There is no in-place mode switch: changing the mode restarts the sessions it can reach, the Extended-screen ones, through `reconnectExtendedOnly()` (see *Connection lifecycle*). Remote-control sessions always capture in Mirror regardless of the setting, so the change leaves them running.

The only in-session rebuild is `HostSession._restartCapture()`, fired through `ScreenCaptureChannel.onCaptureRestartNeeded` (routed by the hub) when the Swift plugin invokes `onCaptureNeedsRestart` (the Mac wakes from sleep) or `onStreamStopped` (the `SCStream` stops with an error; its `asleep` says the main display was asleep then). With one session able to rebuild (`canRebuild`: capture wired, live, not reverse remote) the hub hands both to it, an asleep stop like any other. With two or more, a wake is one hub operation (`_rebuildAll`, a single `pipeline.run`): it snapshots those sessions in key order with their attempts, runs every `stopPipelineOp()` (bitrate adaptation, frame subscription, `stopCapture`, `removeVirtualDisplay`), then every `startPipelineOp(attempt)` (`_startCapture()`, then an IDR), skipping one whose attempt moved or that is no longer active (or, for a display round, still `configuring` with its capture wired), so nothing slots between the stops and the starts and the displays come back in the same order every time. The stops run in key order; the starts run Mirror targets first (`spec.displayMode == mirror`, which every tablet that drives the Mac in remote control is), then Extend targets, each group in key order, so a stream of the main display is made while no virtual display exists (see *Several virtual displays* below); with only Extend targets that is key order, as before. A wake during it gets one more full round (`_rebuilding`/`_wantAll`), a session whose stop threw is not started, and an asleep stop is ignored (the wake rebuilds it with the rest). A session's own requests are deduplicated by generation: each `startPipelineOp` bumps `_pipelineGen` before its first await, each request records it (`_restartRequestedGen`), and a queued round finding it moved since the latest request skips, so a stream-stop heard before the wake started that session is covered by it, while one after its start still gets a round of its own. Re-admission to the budget is idempotent, and a failed rebuild keeps its place (a reservation, which lets the other tablets climb into its share meanwhile), so a wake never refuses a running tablet, even after a round that failed (the displays still dark) and under a lowered Maximum tablets. Sleep invalidates ScreenCaptureKit, the virtual display and the VideoToolbox session, but the ADB socket survives, so after a short sleep or a display-only wake nothing else would recover. ScreenCaptureKit also stops the stream the moment the displays go to sleep (measured), so a rebuild runs then and fails: the virtual display can't be made and no display is found. The wake is what recovers: the plugin forwards every wake once any session exists, whether or not a stream is running (it used to forward only while one was, so a display sleep left the tablet frozen for good), and Dart rebuilds whichever session is still connected. Its two notifications (system and display wake) send one `onCaptureNeedsRestart`, 1.2 s after the last of them (`wakeGeneration`). A start that fails after making its encoder stops at once, releasing the encoder and App Nap's hold. A request that arrives while a session's rebuild runs gets a round of its own after it (`_restartAgain`), for the session that asked, unless that rebuild's start came after the request. (A link that sat silent past the 6 s heartbeat timeout goes through `handleLinkFailure()` instead, which rebuilds the whole session.) The rebuild is skipped in reverse remote. It stops capture, removes and recreates the virtual display, re-runs `_startCapture()` and forces an IDR. It does not call `releaseAll()`: the link is alive, so the tablet's mouse-up still arrives. `onDisplayBoundsChanged` (displays rearranged in System Settings) only refreshes the cached bounds that map normalized input coordinates to screen space.

**Several virtual displays (Apple FB17797423).** With several virtual displays, once the set changes macOS can hand a new `SCStream` another session's display (the most recently added) instead of its own, until every virtual display is gone. Reproduced on macOS 27 (M3 Pro): with an emulator extending, the Tab S10 Ultra was replugged; its retry made display 68 and its stream showed the emulator's 67 (`WARNING: the capture of virtual display 68 does not fill the frame`). An ordered full rebuild fixed it. So the hub keeps the display set (`VirtualDisplays`, in `host_session.dart`, `hub.displays`, handed to each session it makes): `_startAdmitted` calls `adding(this)` right before `createVirtualDisplay`, and `removed(this)` once `removeVirtualDisplay` has answered (`stopPipelineOp`, the teardown's queued stop), when no display was made (`displayId` 0), when `startCapture` answers `fellBack` (the plugin released it) and in `dispose()`. A session adding its display while another session's exists (a tablet joining, a retry after a lost link, one session's `reconnect()`, its own `_restartCapture`) is noted as due (`adding` puts it in `_due`), and asks only once its capture has started on that display (`started(this)`, right after `startCapture` answers without `fellBack`, still inside the queued start, so the round runs after it). A start the encoder refuses (`ENCODER_BUSY`/`NO_ENCODER`, which a join turns into `CaptureLimit`), one that made no display, fell back, threw or was cancelled asks for nothing (`startFailed`, `removed`): nothing of it runs to be fixed, and asking anyway stopped and restarted every extending tablet for a tablet that never ran, again on each Retry. The ask goes to `onRebuildNeeded`, the hub's `_displaySetNeedsRebuild`, which marks the next display round as wanted for the display set (`_displaySetAsked`) and goes on to `_displaysNeedRebuild`, which only sets a flag and queues `_rebuildDisplays` from a `Timer.run` (the ask comes from inside the queued start; several asks before the timer make one round, and a display round still waiting in the queue covers any ask made meanwhile, `_displayRoundWaiting`). That round (`_rebuildRound(displays)`, one `pipeline.run`) is the wake's shape with other targets: every session with `rebuildsDisplay` (not retired, capture wired, live or still `configuring` (a session whose connect has just started its capture, which may be the one that joined; `startPipelineOp` lets those through too), not reverse remote, holding a display), in key order, all stopped, then all started; and before those stops it takes down the displays of sessions on their way out (holders that are not targets: an ended or failing session whose own queued stop would come after the starts), so the set really is empty before any display is made again. Mirror sessions make no display, so they neither ask for a display round nor are rebuilt by one (except for a repair, below), and one display alone never asks. Every running Extend tablet blips for about a second per change. The displays a round makes, a wake's included, ask for nothing: the hub sets `VirtualDisplays.rebuilding` for the whole round, so no round feeds the next. The wake path is otherwise unchanged: wake and display rounds share `_rebuild` (`_wantAll`, `_wantDisplays`), a wake asked during any round gets a full round after it, a display ask during a wake round a display round after it. A first frame that shows another display (`onCaptureMismatch`) is ignored, neither asking nor counted, when that capture is going to be made again anyway (`VirtualDisplays.willRestart`: its own join's ask is still due, or the hub's `_roundWillRestart`: a round asked for or queued that will take it as a target (`_wakeRoundWaiting` is a wake's round handed to the queue and not yet run, as `_displayRoundWaiting` is a display round's: `_rebuild` clears `_wantAll` before the queue, which can be busy with another tablet's start, gets to the round), or a round under way that has not yet started it again, `_roundStartsLeft`). On the device a joiner's first frame showed the other tablet's display while its join's round was stopping the other tablet (whose `removeVirtualDisplay` can take a second), so it asked for a second full round and used up one of its two retries. Otherwise it asks for the same round through `VirtualDisplays.requestRebuild()`, only while another session holds a display and at most twice in a row per session (`_wrongDisplayRebuilds`, `_maxWrongDisplayRebuilds`), and `onCaptureMatched` (a first frame that fills its frame) sets the count back to 0; past that, or with no other display, the session only sets `notice` to `error_extend_wrong_display`, as before.

**Captures of the main display beside virtual displays.** The same bug can hand a stream of the main display (Mirror: Extended screen under the Mirror display mode, and every remote-control session whose tablet drives the Mac) a virtual display instead, so the tablet shows another tablet's extended desktop; that is the mixed setup phase 3 is for (one tablet driving the Mac while another extends), proven with fakes only so far. Three things guard it. A wake starts its Mirror targets before any display is made again (above). Swift checks a Mirror start's first frame against the main display's shape (the `ScreenCapturePlugin.swift` row) and reports `onCaptureMismatch` or `onCaptureMatched` as for an Extend one. And `HostSession.captureMismatch()` tells the two apart by what its last capture start asked for (`_capturedMode`, the config's mode, not the live settings): for a Mirror capture, while any session holds a virtual display or a round that leaves this capture alone has one down for a moment (`VirtualDisplays.besideDisplays`: `sharedWith`, or the hub's `_roundHasDisplaysDown`. Between a round's last stop and its first `adding()`, which waits behind `requestPermission`, nobody holds a display, and a first frame heard just then of a capture made beside them used to be only said. The hub keeps the round's targets, `_roundTargets`, and those whose display it took down until its start of each has returned, `_roundDisplaysDown`; a target of the round does not count, since its capture is one the round made, or will make, with no display there) and it has asked fewer than twice in a row (the same `_wrongDisplayRebuilds`, reset by `onCaptureMatched`), it asks `VirtualDisplays.requestMirrorRepair(this)`, the hub's `_mirrorNeedsRepair`: the session goes into `_repairs` and a display round is asked for as any other (`_displaysNeedRebuild`, from a `Timer.run`; several asks make one round). That round, taking its targets, adds the sessions in `_repairs` that are still the hub's and still capture the main display (`repairsMirror`) to the Extend ones: a repair round. Everything stops in key order, the displays of sessions on their way out go too, so no virtual display exists; then the repaired Mirror captures start, in key order, then the Extend ones in key order. Restarting the Mirror capture alone would make its stream beside the same displays and likely get the same picture. Other Mirror sessions are not touched, and a tablet the Mac controls (reverse remote) has no capture and is never a target of any round. A mismatch is ignored, neither asking nor counted, while that capture is going to be made again anyway, by the same `willRestart` rule: `_roundWillRestart` also answers for a session in `_repairs` while a display round is asked for or queued, a wake asked for or queued covers every capturing session, and `_roundStartsLeft` a round under way. A wake's round takes the asks of the sessions it restarts off `_repairs` (it starts them first anyway), and `_endSession` takes an ended session's off at once. A display round asked for by repairs alone does nothing when none of them is left or still valid as it takes its targets (it used to stop and start every Extend tablet for nothing); it runs whenever the display set itself asked (`_displaySetAsked`), and an Extend session whose own mismatch `_roundWillRestart` answered with that round sets the same flag, so a round it counts on is never the one skipped. Past two repairs in a row, or with no virtual display to be mistaken for the Mac's screen, the session only sets `notice` to `error_mirror_wrong_display`. What stays unguarded: a main display with the same aspect ratio as a virtual display (a 16:10 Mac beside a 16:10 tablet's display) passes the check whatever it shows, and each repair blips every Extend tablet for about a second.

### Key settings (`lib/shared/services/settings_service.dart`)

Persisted via `shared_preferences`: session mode and remote direction (on the host, `nextChoice`: the role a new device gets when nothing else says, the last one picked in Home's role chooser; on the client, what the host's `0xF9` said), link type (`link_type`, per device) and the client's typed Mac address (`wifi_host_address`), display mode, last paired device serial and model name, the client's panel size and top refresh rate (from its HELLO, so presets stay correct across launches: per tablet as `client_panel.<key>` ("width,height,maxHz"), and the last Android one reported in the global `client_panel_w/h/max_hz`), the reverse-remote screen-off choice per tablet (`tablet_screen_off.<serial>`), the tablets the host has had a live USB session with (`known_devices`, a JSON list of `KnownDevice`: serial, model, `vdSerial`, `installId`, and optionally the mode it is remembered in, `mode` and `direction` as enum names, written only when one is set; malformed JSON reads as none, while a `mode` this build cannot read is only no mode, since the entry's `vdSerial` has to survive; whatever a build cannot read of an entry, a key it does not know or a `mode` or `direction` that is no name it knows, it writes back as it came, see below), and the cap on tablets at once (`max_tablets`, `maxTabletsRx`, default 4, clamped to 1..8; set on Settings → Tablets with no reconnect, and read by the hub's `cap` over USB, in every mode, within the encoder estimate's `tabletCap`), Accept devices over Wi-Fi (`wifi_listen`, `wifiListenRx`, default off), the client's install id (`install_id`, 16 random bytes made once, sent in HELLO's identity tail), each device's own settings (`device_profile.<key>`, see *A device's own settings*), and the mode of a new device that joins that way (`wifi_listen_mode`/`wifi_listen_direction`, `wifiListenChoice`, written by `setWifiListenChoice`, synchronous like `setKnownChoice`), and what the host learned of its encoder's capacity per chip and codec (`encoder_capacity.<chip slug>.<codec>`, Mpx/s, never from a synthetic tablet). `SettingsService.init()` migrates once (`_migrateToPerTablet`): the global panel and the old global `tablet_screen_off` become the saved last-used device's own, and the old screen-off key is removed; and while `known_devices` is absent (its presence is the run-once marker), a saved `last_device`, read raw, never through `lastDeviceSerial` and its baked-in fallback, becomes the one known device with `vdSerial` 1, the serial every virtual display had before, so macOS keeps its arrangement. Nothing falls back to the global values by the current last-used device, or a tablet that became last-used later would inherit another's choice. `vdSerialFor(key, taken:)` is a known device's own `vdSerial`, else `fnv1a32(key) | 0x10000`, stepped past 1, `taken` and every stored one (it saves nothing); `vdNameFor` is `Extended Screen` for serial 1 and `Extended Screen – <model, _ as spaces>` otherwise when a model is known; `rememberDevice` upserts a known device (keeping its `vdSerial` and `installId`) and still writes `last_device`/`last_device_name`, which the first-run auto-connect reads, and Settings' Target device row when no session is live (it lists the live sessions' models, joined, else the focused device's, else `last_device_name`). The hub calls `vdSerialFor` and `vdNameFor` when it makes a session, and a USB session calls `rememberDevice` once it is live (see *Hub and sessions*). A mode and direction together are a `SessionChoice` (`lib/shared/models/session_choice.dart`, pure): the choice as picked, whose `effective(link:, android:)` is what a session really runs (over Wi-Fi, or for a device that is not Android, the tablet drives the Mac, whatever the mode), with `sameEffect` (the direction means nothing to an Extended screen), `label`, `all` (the three a picker offers) and `fromNames`. `SettingsService.nextChoice` is the saved session mode and remote direction as one (the direction kept for Extended screen too), and `SessionSpec.of(settings, link)` is `SessionSpec.from(nextChoice, link, displayMode:)`, which applies `effective` and mirrors for remote control. A known device's remembered mode is `KnownDevice.choice`: `knownChoice(serial)` reads it, `rememberDevice(…, choice:)` saves one when given and keeps the stored one otherwise, and `setKnownChoice(serial, choice)` changes a known, non-synthetic tablet's (it is not async: `knownChoice` reads the new value as soon as it returns, because `SharedPreferences` updates its cache inside the call, and the write follows unawaited, a failure only logged). Every USB session passes its own `choice` each time it goes live, and the hub's `changeMode` calls `setKnownChoice` in the step that begins the change, so a known tablet's entry holds the mode it last ran in, or was last asked to. The auto-connect policy and the hub's own connects read it (`knownChoice`, else `nextChoice`), and so does the user's Connect on a remembered device's row in Home's Add a device panel, whose role fits the encoder; a new device (or a remembered one whose role has no room) connects in the role picked in Home's role chooser, which for a new device is saved as `nextChoice`. Entries written before modes were remembered carry none, so those tablets are new to the chooser once (it preselects `nextChoice`), and are remembered from then on. Every save rewrites the whole list (`rememberDevice` each time a USB session goes live, `setKnownChoice`), so `KnownDevice.fromJson` keeps what it could not read of an entry (`_unread`: keys this build does not know, and a `mode` or `direction` whose value is no name it knows) and `toJson` writes it back; a choice saved for that tablet itself (`copyWith(choice:)`) replaces an unread mode and direction. A field a later build adds to an entry therefore survives this build, for the tablets it does not connect itself. The builds from before modes were remembered have no such thing, and they share the preferences file when run on the same Mac (same bundle id): one live USB session there rewrites `known_devices` without any tablet's `mode`/`direction` (`vdSerial` and model are kept), so the next launch of this build brings every known tablet back in `nextChoice` once; and such a build reads `session_mode`/`remote_direction`, here only `nextChoice`, as the mode of its one session, so a role chooser pick of The Mac controls this device makes it start its tablet that way. Synthetic tablets (`synth-*` serials, `SettingsService.isSyntheticKey`, `DeviceModel.isSynthetic`) are never persisted: `setClientPanelFor` (the global last panel included), `rememberDevice`, `setLastDevice` and `setTabletScreenOffFor` do nothing for one; `setLastDeviceName` takes a model name, so only `rememberDevice` guards it. Also persisted: encode preset (plus custom width/height/bitrate/refresh for the `custom` preset), codec (`h264`/`h265`; with none saved, `init()` resolves it once at launch via `SettingsService.defaultCodecFor` — H.265 for `max`, H.264 otherwise — and it does not follow later preset changes, except that selecting `max` in the picker sets and saves H.265), UI locale (`en`/`th`), performance/HUD overlay toggles, and "keep the Mac cursor in place" (`keep_mac_cursor`, default on; host only). A build-time `--dart-define=DEVICE_SERIAL=<serial>` (a default is baked in) does not pin the target device: it is only what `lastDeviceSerial` returns when no serial has been saved, and the hub reads that getter only when `connect()` is called without a serial and with no session to retry (Home's Add a device rows and the single-device auto-connect always pass one). If that device isn't attached, the first ADB device is used; once a session exists, its retries stay on its own device. `crypto` is a direct dependency for the USB handshake's HMAC-SHA256. `flutter_secure_storage`, `permission_handler`, `protobuf` and `async` are declared in `pubspec.yaml` but not imported anywhere yet (`flutter_secure_storage_macos` is the plugin behind the "do not support Swift Package Manager" warning on every macOS build).

### Encode presets (`lib/shared/models/display_config_model.dart`)

`EncodePreset` bundles resolution + scale factor + bitrate + refresh rate into five presets: `max` (the default), `quality`, `balanced`, `performance`, and `custom` (user-adjustable values persisted in settings); there is no separate frame-rate setting. `max` is native resolution at the client panel's top refresh rate (`clientMaxRefreshHz`, from the HELLO); its bitrate is `_qualityBitsPerPixel` (Quality's 20 Mbps at a fixed 2960×1848 @ 60 Hz reference) × panel pixels × top rate, clamped to 8 to 50 Mbps, so on a smaller panel it can be below Quality's fixed 20 Mbps. It passes `adaptiveFps` to the Swift encoder, which adapts over the ladder 30/45/60/90/120 plus the start rate, never above it. A saturated VideoToolbox session doesn't skip frames — `VTCompressionSessionEncodeFrame` blocks the timer thread once ~8 frames are in flight — so overload is detected as the encode queue pinned near that cap or the timer falling under 90% of its rate. After 3 s of that it drops straight to the highest rate that fits in 95% of the achieved throughput (e.g. an M3 Pro's H.264 session saturates near 50 fps at 2960×1848, so it lands on 45; HEVC sustains ~2× that), and steps back up one notch after `stepUpDelay` healthy seconds (10 s, doubling up to 5 min whenever a step-up fails within 30 s). Each change is reported via `onFrameRateChanged` so the host re-announces `0xFB`; an overload step-down also carries `achieved` (the ticks/s it managed), from which the hub's budget learns (see *Hub and sessions*). Keyframes stay at most a second apart at any rate (`MaxKeyFrameIntervalDuration`). While capturing, the plugin holds a `ProcessInfo` activity (`userInitiatedAllowingIdleSystemSleep` + `latencyCritical`) so App Nap can't throttle the usually-hidden host and stall encoding. In reverse remote (tablet encodes), `max` falls back to native @ 60 Hz / 20 Mbps. Fixed-preset resolutions are **relative to the connected client's panel** (read from `SettingsService.clientPanelWidth/Height`): logical size is always panel ÷ 2; `scaleFactor` 2.0 (quality/balanced) encodes at native panel resolution, 1.0 (performance) at half. Custom's width is the **physical encode width** (the picker labels each option as physical W×H): the desktop stays at panel ÷ 2 logical like the fixed presets, and `SettingsService.captureScaleFactor` becomes `customWidth ÷ (panel width ÷ 2)`. `customHeight` is only persisted and displayed, never used for capture: the encoded height is (panel height ÷ 2) × that scale, so it follows the panel's aspect ratio (the 1920×1200 option encodes at 1920×1198 on a 2960×1848 panel). The Swift `startCapture` multiplies logical × `scaleFactor` (clamped to even dims); `CGVirtualDisplay` is always created at logical × 2 (HiDPI). `HostSession._startCapture()` takes its config from `SettingsService.captureConfigFor(panel, spec)`, which feeds the settings to `EncodePresetX.configFor(panel, custom:, mode:, codec:)` (no settings read there; custom's scale clamped to 0.5..2.0; `known_devices_test.dart` checks it against the `capture…For(panel)` getters for every preset), and then from what the encode budget grants. `DisplayConfigModel.encodedWidth/Height/Pixels` round as the Swift side does, and its `fpsCeiling` (sent in `toMap` only when set) is the rate cap `EncodeBudget` (`lib/shared/connection/encode_budget.dart`, pure; its class comment is the reference) grants a session sharing the encoder with others: demand is encoded pixels × fps over the chip's estimate (`EncoderEstimate.forChip`: 274/550 Mpx/s per engine for H.264/H.265, 1 engine for a base or Pro chip, 2 for Max, 4 for Ultra; anything else 140 and at most 2 tablets) or what was learned of this Mac's encoder when that is more (see *Hub and sessions*), 85% usable; a tablet alone gets its config unchanged, a newcomer may get a lower resolution (native, 1920 wide, scale 1) if its 30 fps floor doesn't fit, and running tablets only change their ceiling (the largest demand steps down the 120/90/60/45/30 ladder). A refusal is `CaptureLimit` (`error_encode_limit`). The Swift side honours the ceiling (`startCapture`'s `fpsCeiling`, `setFrameRateCeiling`; see the `ScreenCapturePlugin.swift` row); how the sessions use the budget is under *Hub and sessions*.
